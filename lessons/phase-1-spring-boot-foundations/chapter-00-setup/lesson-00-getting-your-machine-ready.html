Getting Your Machine Ready

Four tools. Four commands that prove they work. One folder that Git keeps a history of. No Spring yet. This lesson clears away the wall that stops most beginners before they ever reach Spring.

Files created: learning/.gitignore, learning/.gitattributes · Prerequisites: none (this is lesson zero) · Pinned: Java 21 LTS · Maven 3.9.16 · Spring Boot 4.1.1

  • What the four tools are (the JDK, Maven, an IDE and Git), and why you need each one.
  • How Java turns the text you type into a program your computer can run.
  • How to install each tool, prove it works with one command, and start your project's history.

1The Problem

Imagine you sit down tomorrow to build our online store. You know Java. You can write a class, a loop and a method. You open a blank file and type a good Product class. You save it. And then you stop, because there is nothing to press.

Right now, your laptop does not know what to do with a file full of Java. It cannot turn your typing into a running program. It cannot fetch the huge amount of ready-made code that Spring is built from. It cannot keep yesterday's version of your work when you break something today. The file just sits there, as useless as a shopping list.

This is the wall. No clever idea hides behind it. But it ends more attempts at programming than any hard idea does. People give up during setup, before they write one real line of code. Setup fails in silent, confusing ways:

  • A command "is not recognized".
  • A download page offers five options, and you pick the wrong one.
  • An error message names something you have never heard of.

None of this means your thinking is wrong. Your machine just is not ready yet.

So we will get it ready on purpose, one tool at a time. And we will do the part most tutorials skip. We will prove each tool works before we move on. By the end, you will type four commands and see four answers. Then you will know everything is in place. You will not just hope.

Have you installed these tools before? Do not skip the lesson. Jump to section 5 and run the four check commands anyway. Checking takes ninety seconds. Fixing a half-installed setup three lessons from now takes a whole evening.

Think about a restaurant kitchen on its first morning, before it serves any food. The chef is skilled. But skill alone cooks nothing. The kitchen needs four things in place first:

The kitchen teaches one more thing. A chef does not install a new stove every time they cook. They install it once, carefully. Then it is there for years. This lesson is the same. You spend one careful morning, and then setup is behind you.

3The Concept Explained

Before you install anything, it helps to know what each tool is. Some people install tools they cannot describe. They end up with three versions of Java and no idea which one is running. We will avoid that.

3.1 Your computer cannot read Java

Start with what you already do. You write Java into a file. That text is called source code. We call it "source" because everything else is made from it. It is just text. You could read it aloud.

Inside your computer is a processor. The processor is the chip that does the real work. It is also called the CPU (Central Processing Unit). The processor cannot read Java. It understands only machine code. Machine code is a list of raw numbers. Each number means a tiny job, like "add these two values" or "copy this small piece of data over there".

So something must turn "a Java class about products" into "numbers a chip can run". That something is a compiler. A compiler is a program whose only job is translation. Text goes in. Instructions a machine can run come out. Java's compiler is a command called javac (short for "java compile").

3.2 Java's unusual trick: bytecode and the JVM

Here Java does something unusual. It is the most important idea in how Java runs.

javac does not make machine code for your laptop. It makes an in-between format called bytecode. Bytecode lives in files that end in .class. It is a set of instructions for an imaginary computer. That computer does not really exist.

A real program then pretends to be that imaginary computer. This program is called the JVM, the Java Virtual Machine. "Virtual" here means "pretend". The JVM reads bytecode and carries it out on your real processor. It translates as it goes.

So running a Java program takes these steps:

  1. You write Product.java. This is source code.
  2. javac reads it and writes Product.class. This is bytecode.
  3. The JVM reads Product.class.
  4. The JVM turns each bytecode instruction into machine code, and your processor runs it.

3.3 Why Java was designed this way

Look at the other choice. Suppose javac made Windows machine code. That file would not work on a Mac. It would not work on a Linux server. (A server is a computer that runs your app all day, so other people can use it. Lesson 01 explains servers fully.) It would not work on a friend's different computer. You would have to compile your program again for every kind of machine.

Windows, macOS and Linux are operating systems. An operating system is the main program that runs a computer. Every other program runs on top of it. Each operating system needs different machine code. Bytecode avoids that problem.

The bytecode-and-JVM design costs a little speed. In return, the compiled file works everywhere. In Phase 3 we will send this app to a cloud computer you will never see. This choice, made in 1995, is why that will be easy.

3.4 JDK, JRE, JVM: three names, one set of nesting dolls

People mix up these three names all the time. The mix-up causes real problems. So let us be exact. They fit inside each other, like nesting dolls. Here they are, smallest first:

NameStands forWhat is in itLets you…
JVMJava Virtual MachineThe engine that runs bytecoderun bytecode
JREJava Runtime EnvironmentThe JVM plus the standard library. The standard library is thousands of ready-made classes that come with Java, like String and Listrun finished Java programs
JDKJava Development KitThe JRE plus the tools for writing Java. The most important tool is javac, the compilerwrite and compile your own Java

"Runtime" means "while a program is running". So a Runtime Environment is everything a program needs while it runs.

The word that matters most is Kit. A JRE is for someone who only runs Java that another person compiled. You are going to write Java. So you need the compiler. So you need the JDK.

What if you install a JRE by mistake? You get one of the most confusing beginner errors there is. Java is clearly installed, yet nothing you write will compile.

Check yourself: a friend says "Java is installed. I can run programs. But javac says command not found." What happened?

They almost certainly have a JRE, not a JDK. The JRE contains the JVM, so it can run compiled programs. But it has no compiler. javac is a tool for writing Java. Those tools come only in the Kit. The fix is to install a JDK. (A broken PATH can also cause this. Section 3.6 covers PATH. But if java works and javac does not, a JRE is by far the most likely cause.)

3.5 Why Java 21, and what "LTS" means

A new version of Java comes out every six months. Most versions get fixes for only six months. That is long enough to try them. It is too short to build a business on.

Every few years, the Java team marks one version as LTS. LTS stands for Long Term Support. An LTS version keeps getting security fixes for years.

Companies build on LTS versions. So most tutorials, tools and answers to your questions are about them. We pin Java 21. It is an LTS version, and a huge number of tools support it. Java 21 also added "virtual threads". They let one program do many jobs at the same time, very cheaply. We study them properly in Phase 3.

Spring Boot 4 needs at least Java 17. It recommends the newest LTS. Java 21 fits well within that.

3.6 The terminal, and the setting that breaks everything

A terminal is a window where you talk to your computer by typing instead of clicking. On Windows it is PowerShell or Windows Terminal. On macOS and Linux it is called Terminal. You will use nearly every tool in this course from the terminal. Why? A typed command is exact. You can repeat it. And it is easy to paste into a lesson.

Your computer keeps some named settings that every program can read. Each one is an environment variable. The name comes from the idea that these settings are part of the "environment" your programs run in. Think of a notice board in an office. Anyone who walks in can read it.

The best-known environment variable is PATH. Here is why it matters. When you type java and press Enter, your computer must find a program with that name. It does not search your whole hard disk. That would take forever. Instead it follows these steps:

  1. It reads PATH. PATH holds a list of folders.
  2. It looks in the first folder for a program called java.
  3. If it is not there, it tries the next folder, and the next.
  4. If no folder on the list has it, it gives up and shows an error.

That error is the most common setup error there is. On Windows it looks like this:

java : The term 'java' is not recognized as the name of a cmdlet, function,
script file, or operable program.

The word "cmdlet" just means a built-in PowerShell command. Now read the message again with what you know. It stops being scary. It does not mean Java failed. It does not mean Java is broken. It means: "I looked in every folder on my PATH list. None of them had a program called java." Either Java is not installed, or it sits in a folder that is not on the list. That is all the message says.

Many Java tools also read a second environment variable, JAVA_HOME. It holds the folder where your JDK is installed. Maven uses it to decide which Java to use. You will see it again in section 5.

We meet environment variables again in Lesson 39, for a different reason. There, they become the safe place to keep passwords and secret keys, so those never go into your code.

3.7 Libraries, and the mess they cause without help

Say you have your JDK and you write one file. You can compile it by hand: javac Product.java. Fine. Now let us grow it into something real. Watch the by-hand method fall apart, one problem at a time.

Problem one: many files. Real projects have hundreds of files in many folders. The files depend on each other. So you must compile them in the right order. By hand, that means typing every path, every time.

Problem two: other people's code. You will not write everything yourself. Nobody does. You will use libraries. A library is a bundle of ready-made code that someone else wrote to solve a common problem. Think of it as a box of parts you can use in your own work. Spring Boot is built from dozens of libraries.

A library comes as a JAR file. JAR stands for Java ARchive. It is one file that holds many compiled classes, a bit like a zip file. To use a library by hand, you must:

  1. find the right website,
  2. download the right JAR,
  3. put it somewhere sensible,
  4. and tell javac where it is.

Problem three, the one that really breaks people: libraries use other libraries. Here is an example. You want library A. The people who wrote A used libraries B and C. C, in turn, needs D and E. So to use A, you really need A, B, C, D and E.

  • Miss one, and your program crashes while it runs. Often this happens long after it started. The error names a class you have never heard of.
  • Get two different versions of the same library, and you get a harder, nastier failure.

Chasing these down by hand is called "JAR hell". Before build tools existed, it could easily eat a week.

3.8 What a build tool is, and how Maven solves the mess

A build tool takes over all of that work. You write down what you want. It works out how. The build tool we use is called Maven. Here is how Maven works:

  1. You list what your project needs in a file called pom.xml. Each item on the list is a dependency: a library your project depends on.
  2. Maven reads the list. It downloads each item from Maven Central. Maven Central is a huge, free, public store of Java libraries on the internet.
  3. For each library, Maven reads that library's own list of needs. It downloads those too. It keeps going down the chain until nothing is missing. This automatic chasing is called transitive dependency resolution. "Transitive" means "passed along the chain". This is the feature that ended JAR hell.
  4. It saves everything in a local folder called .m2, inside your home folder. So the next build does not download it all again.
  5. It compiles your code in the right order.
  6. It runs your tests. A test is a small piece of code that checks your real code still does what it should. We write our first tests in Lesson 02.
  7. It packages the result into one file, a JAR, that you can run or hand to someone.

This is why one line in a file can give you a whole web server. It is also why Lesson 02 spends its time on pom.xml, not on javac.

3.9 The IDE

An IDE is a text editor that understands the language you write. IDE stands for Integrated Development Environment. It helps you in many ways:

  • It underlines a typo before you compile.
  • It jumps to the place where you defined a method.
  • It suggests how to finish what you are typing.
  • It can safely rename something everywhere in a project at once.

You could do this course in Notepad. You would just be slower. You would also make more mistakes that a machine could have caught for free.

3.10 Git and GitHub: two different things with similar names

Git is a program on your machine. It records the history of your files. GitHub is a website. It keeps a copy of that history online. Git is the tool. GitHub is one place to keep a copy. You can use Git with no GitHub account at all.

A few words cover almost all of Git. Each one is worth getting clear:

  • A repository (or "repo") is a folder that Git is watching. Ours will be the learning folder.
  • A commit is one saved snapshot of the whole project. It comes with a message that says what changed and why. It is not a backup of one file. It is a photo of everything, at that moment.
  • To stage a file means to choose it for the next commit. Think of putting items in a box before you seal it.
  • A branch is a named line of commits, one after another. Our main line will be called main.
  • A remote is a copy of the repository kept somewhere else. Ours will be on GitHub. By habit, people name it origin.
  • To push means to send your new commits up to the remote.

3.11 Why Git matters on day one

Why set up Git now, before there is anything to lose? Because of what it does to your nerve.

With a history, breaking things costs nothing. The last working version is one command away. So you can try ideas freely. Without a history, every change is a small gamble. Beginners react by not changing anything. And that is exactly how you stop learning. Git is not just record-keeping. It gives you permission to be brave.

For a self-taught developer, a public GitHub repository with real commits works like a CV. An interviewer can see what you built and how you work. They can see you stuck with something for months. By the end of this course, yours will hold a complete microservices system with an AI assistant in it. (Microservices means one big app split into several small programs that work together. You build that in Phase 2.) When someone says "show me something you built", that beats a certificate.

3.12 Pinning versions, and why this course does it out loud

To pin a version means to choose one on purpose and write it down. You do not just take whatever is newest that day. This course pins Java 21, Maven 3.9.16 and Spring Boot 4.1.1.

Pinning matters even more than usual here. Why? All through this course, you will see predicted output. That is exactly what a command or a request should print. Then you compare it with what your machine really prints. That comparison only works if we both use the same versions.

A version number like 4.1.1 has three parts. The first number (4) is the major version. A new major version can change how things behave and what they print. With a different major version, your output could differ for harmless reasons. Then you could not tell a real mistake from a version difference.

Here is a promise for every lesson. This course is built on Spring Boot 4. But nearly everything online was written for Spring Boot 2 or 3. That includes tutorials, books, videos and Stack Overflow answers. (Stack Overflow is a big question-and-answer website for programmers.) The Spring team renamed several things since then. Here is the first renamed thing you will meet, in Lesson 02:

spring-boot-starter-web spring-boot-starter-webmvc

Say you copy the old name from a 2024 tutorial. It still works for now. But it is deprecated. That means it is marked as old, and a later version will remove it. It also no longer matches the rest of this course. Other renamed things simply break, and the error does not say why.

So whenever Boot 4 differs from the rest of the internet, a card like this one appears right there. It tells you three things: what changed, why it changed, and how to read the older material. You will not have to find out alone.

Check yourself: why not just teach Spring Boot 3, since most tutorials use it?

Because free support for Spring Boot 3 ended on 30 June 2026. It gets no more security fixes. If you learned it, you would have to move to version 4 straight away. It is better to learn the current version, with the differences taught clearly. That way you get the modern skill and you can still read the older material.

4The Wrong Way

Wrong approach — "I'll install things when something breaks"

The tempting shortcut is to skip ahead. You grab a Spring Boot project from somewhere. You only install what the errors ask for. Here is what that really looks like, step by step.

4.1 Attempt 1: nothing installed

You download a project and try to build it.

PS D:\Projects\store> mvn spring-boot:run

Predicted output:

mvn : The term 'mvn' is not recognized as the name of a cmdlet, function, script
file, or operable program. Check the spelling of the name, or if a path was
included, verify that the path is correct and try again.

Nothing in that message says "install Maven". It talks about cmdlets and spelling. So a beginner thinks they made a typo. They try again, more carefully. They get the same result.

4.2 Attempt 2: Maven installed, but only a JRE

You install Maven. Then you install "Java" by clicking the first big download button you see. On many sites, that button gives you a JRE, not a JDK.

Predicted output:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ store ---
[ERROR] No compiler is provided in this environment. Perhaps you are running
on a JRE rather than a JDK?
[INFO] BUILD FAILURE

The first line names maven-compiler-plugin. A plugin is an add-on that does one job for Maven. This one runs the compiler. It found no compiler to run.

This message is unusually kind. It names the real problem. Most error messages do not. But you have now spent an hour learning what the table in section 3.4 already told you.

4.3 Attempt 3: the wrong JDK version

You install the first JDK you find. It is an older Java 11. Then you build a Spring Boot 4 project.

Predicted output:

[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

"Target release" means the Java version the compiler is asked to produce. So the message says: "You asked me for Java 21 output. I am an older compiler. I have never heard of 21." Once you know how the pieces fit, you can read it. Before that, it means nothing.

4.4 The failure with no error message at all

You get everything working, and you build for a week. On Friday you break something badly. Then you find there is no history to go back to. You left Git as "something to set up later". There is no red text for this one. There is just lost work.

4.5 What all four failures share

Each failure is cheap to prevent and costly to track down. That is the whole reason to do setup on purpose, in order, and to check as you go.

5The Right Way

Correct approach — install in dependency order, and prove each step before the next

The order below matters. Maven needs a JDK to run, so the JDK comes first. Git comes before the project folder. That way, the first file the folder ever holds is a .gitignore. Follow the steps from top to bottom.

5.1 Step one: install the JDK (Java 21 LTS)

Several companies publish their own copy of Java 21. The language is the same in every one. They differ only in packaging and support. Any of these is fine. Eclipse Temurin is the common choice, and it needs no account:

  • Eclipse Temurin 21 (LTS) — adoptium.net
  • Microsoft Build of OpenJDK 21 — handy on Windows
  • Amazon Corretto 21, Azul Zulu 21 — also fine

Now follow these steps:

  1. Download the JDK (not the JRE) for Java 21, for your operating system.
  2. Run the installer.
  3. On Windows, the installer may show a checkbox like "Set JAVA_HOME variable" or "Add to PATH". Tick both. They fill in the two environment variables from section 3.6 for you.

Prove it works. Open a brand-new terminal window. (A window that was already open still has the old PATH.) Run both of these:

java -version
javac -version

Predicted output (your exact version number and wording will differ a little; that is fine):

openjdk version "21.0.9" 2026-10-20
OpenJDK Runtime Environment Temurin-21.0.9+7 (build 21.0.9+7)
OpenJDK 64-Bit Server VM Temurin-21.0.9+7 (build 21.0.9+7, mixed mode, sharing)

javac 21.0.9

You can ignore the middle lines. They name the exact build. Check these three things, most important first:

  1. Both commands answered at all. So both are on your PATH.
  2. Both say 21. If java says 21 and javac says something else, two JDKs are fighting. See section 7.
  3. javac answered. So you have a JDK, not a JRE.

5.2 Step two: install Maven 3.9.16

Maven has no installer. It is just a folder of files, plus an entry in PATH. On Windows:

  1. Download apache-maven-3.9.16-bin.zip from maven.apache.org/download.cgi.
  2. Unzip it somewhere permanent, in a path with no spaces. For example: C:\tools\apache-maven-3.9.16. (Some older tools still get confused by spaces in folder names.)
  3. Add C:\tools\apache-maven-3.9.16\bin to your PATH:
    1. Press Start and type "environment variables".
    2. Open Edit the system environment variables, then click Environment Variables…
    3. Select Path, then click Edit, then New.
    4. Paste the path. Click OK in all three windows.
  4. Close every terminal window and open a new one. A terminal reads PATH only when it starts. Windows that are already open will not see the change.

On a Mac, you can use Homebrew. Homebrew is a free tool that installs programs from the terminal. Type brew install maven. On Debian or Ubuntu (two common kinds of Linux), type sudo apt install maven. Here apt is Linux's installer, and sudo runs the command with administrator rights. Afterwards, check which version you got.

Prove it works. In a new terminal:

mvn -version

Predicted output:

Apache Maven 3.9.16 (a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0)
Maven home: C:\tools\apache-maven-3.9.16
Java version: 21.0.9, vendor: Eclipse Adoptium, runtime: C:\Program Files\Eclipse Adoptium\jdk-21.0.9-hotspot
Default locale: en_GB, platform encoding: UTF-8
OS name: "windows 11", version: "10.0", arch: "amd64", family: "windows"

Look at the third line. mvn -version tells you which Java Maven found. That is the most useful thing on the screen. It shows you when Maven uses a different JDK from the one you expect. It must say 21.

5.3 Step three: install an IDE

Here are two good choices. Both are free:

IntelliJ IDEA Community EditionVisual Studio Code
Best atJava. It has the strongest Java tools there areBeing light, and handling every other kind of file well
SetupInstall it and open the project. It understands Maven by itselfInstall it, then add the Extension Pack for Java (an add-on that teaches VS Code about Java)

If you have no preference, choose IntelliJ IDEA Community Edition. It points out things about Java as you type, so it teaches you as you go. This step has no check command. If it opens, it works.

5.4 Step four: install Git and create a GitHub account

Download Git from git-scm.com and install it. On Windows, the installer asks a long list of questions. The default answers are fine. Only one needs a thought: the default editor. Git opens this editor when it wants you to type a message. Pick one you know how to close, such as Notepad++ or VS Code. Avoid Vim for now. Vim is a powerful editor, but it is famously hard to close if you have never used it.

Next, create a free account at github.com. Then create a new, completely empty repository:

  • Name it something like spring-boot-learning.
  • Public or private are both fine. Public is nice later, for the reason in the "In the real world" card above.
  • Do not tick "Add a README", "Add .gitignore" or "Choose a license". We want it truly empty. If the repository already has commits in it, the next step gets more awkward.

Prove it works, and tell Git who you are. Git writes this name and email on every commit. So set them once, now. The --global part means "for every repository on this computer".

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Predicted output. The first command answers. The other two print nothing at all. That is Git's way of saying "done":

git version 2.51.0.windows.1

It takes time to get used to silence meaning success. Many terminal tools print nothing when they work. They only speak up when something is wrong.

5.5 Check all four tools at once

All four tools at once. Run these four lines in one new terminal. You want four answers and no "not recognized". That means your machine is ready. This is the goal of the whole lesson.

java -version
javac -version
mvn -version
git --version

Compare each answer with the predictions above. Does one differ in a way you did not expect? Then the machine is right and the lesson is wrong. Tell me exactly what you saw, and we will work out why.

6Applied to Our Project

This lesson teaches no Spring Boot feature. There is no annotation to write and no code to run. Twenty minutes ago, the tools to run code did not even exist. So there is no project code here. That is correct, not a shortcut.

What we can do now is create the folder where everything else will live. And we put it under Git before it holds anything worth losing.

6.1 Why the first file must be a .gitignore

The order here matters more than it seems. Git only tracks the files you tell it to. But the usual first command tells it to track everything in the folder. If an unwanted file is in the folder at that moment, it goes into the history.

Git keeps its history forever, on purpose. So taking a file out later is hard. That is why you write the ignore list before the first git add, never after. A .gitignore file is that ignore list. It tells Git which files to leave alone.

6.2 Write the .gitignore

Create a folder called learning wherever you keep projects. Inside it, create a file named exactly .gitignore. The name starts with a dot and has no extension. Put this in it:

# Local-only course control files - never commit these
CLAUDE.md
curriculum.md
progress-tracker.md

# Maven / Java build output - generated, never stored
target/
*.class

# IDEs - personal to your machine, not to the project
.idea/
*.iml
.vscode/

# Local Claude Code settings - machine-specific
.claude/

# Real secrets - never commit; application.yml + .env.example are the templates
**/application-local.yml
.env

Every line is there for a reason:

  • The three course files are your local control files. They belong to you, not to the project.
  • target/ and *.class are what Maven produces. They hold compiled bytecode, made fresh from your source on every build. Storing them in Git makes the history huge and causes pointless clashes. A simple rule: if a build can make it again, do not store it.
  • IDE folders hold your personal window layout and preferences. Another developer's copy would clash with yours. Neither is part of the program.
  • application-local.yml and .env will hold real passwords and API keys from Lesson 39 onwards. (An API key is a secret code that lets your app use an online service, often a paid one.) This line goes in now, months early. Then a secret can never land in the history by accident later. Remember: Git history lasts forever. A leaked key stays leaked, even if the next commit deletes it.

6.3 Write the .gitattributes

Add one more file next to it, called .gitattributes:

# Normalise line endings so the repo behaves identically on Windows and Linux
* text=auto eol=lf

Why? Windows and Linux end a line of text differently. Windows uses two hidden characters. Linux uses one. Without this file, Git may say every line of a file changed, even when you changed nothing. That is maddening. This one line fixes it for good. It tells Git to always store line endings the Linux way.

6.4 Put it under version control

Now, and only now, run these commands from inside the learning folder:

# 1. Start tracking this folder. This creates the hidden .git folder, which IS the history.
git init

# 2. Stage every file that .gitignore does not exclude, ready for the first snapshot.
git add .

# 3. Take the snapshot, with a message that explains it.
git commit -m "chore: initial course setup"

# 4. Name the main branch 'main' (the modern default).
git branch -M main

# 5. Save the address of the online copy. Use YOUR repository URL from GitHub.
git remote add origin https://github.com/your-username/your-repo.git

# 6. Send the commit up, and remember this destination for later pushes (-u).
git push -u origin main

6.5 What happens, step by step

  1. git init creates a hidden folder called .git. That folder is the repository. Delete it, and you have plain files again, with no history.
  2. git add . goes through the folder and checks .gitignore. It stages every file that is not ignored. You wrote the ignore list first. So Git skips your three local-only files. You never have to remember to leave them out.
  3. git commit saves the staged snapshot for good. It labels the snapshot with your message.
  4. git branch -M main renames your main branch to main. That matches GitHub's default name.
  5. git remote add origin … just saves an address under the nickname origin. It sends nothing yet.
  6. git push -u origin main uploads the commit. The -u also links your local main to the one on GitHub. After this, a plain git push is enough. The first time, a browser window or a login box may appear. That is GitHub checking it is really you.

On branch main

nothing to commit, working tree clean

Second, and this is the one that matters: refresh your repository page on GitHub. You should see .gitattributes and .gitignore. You should not see CLAUDE.md, curriculum.md or progress-tracker.md. Are those three on your disk but not on GitHub? Then the ignore list did its job.

Check yourself: why write .gitignore before git add ., and not after?

Because git add . stages every file that is not ignored, and a commit is permanent. Say a secret or a local-only file is in the folder the first time you run git add .. Git saves it into the history. Deleting it in a later commit does not remove it from the earlier one. Anyone with the repository can still read it there. If you write the ignore list first, Git never stages the unwanted files at all. It is much easier to keep something out than to get it back out.

7Gotchas and Common Mistakes

  • Changing PATH and leaving the terminal open. A terminal reads PATH once, when it starts. So after you change PATH, the old window still says mvn does not exist. The fix: close it and open a new one. On Windows, signing out and back in sometimes helps too. People reinstall Maven three times because of this.
  • Two JDKs, and the wrong one in charge. The sign: java -version and mvn -version show different Java versions. Or javac shows a different version from java. The cause: an old JDK is still on the machine, and PATH finds it first. The fix: set JAVA_HOME to your Java 21 folder, and remove the old entry from PATH. Always trust the Java line in mvn -version over what you think you installed.
  • Installing a JRE instead of a JDK. Download pages often push the JRE, because most visitors only want to run Java. Then java works and javac does not. The build error you get later talks about a compiler, not a download. Always check with javac -version, not just java -version.
  • Committing something that should have stayed local. This usually happens when you run git add . before you write .gitignore. It also happens if you force a file in with git add -f (the -f means "force"). Never use -f on the three course files. If a real secret does get committed, treat it as leaked. Change the key first. Worry about cleaning the history after that.
  • Spaces and non-English letters in folder paths. Some tools still get confused by a path with spaces or accented letters. Their error messages then point far away from the real cause. Keep the paths to your tools and projects plain.
  • Thinking the IDE uses the same JDK as your terminal. IntelliJ can download and use its own JDK. So the IDE may compile fine while mvn fails in a terminal. They are using different Javas. In this course, trust the terminal. You run every command in these lessons there.

8Tradeoffs and When Not to Use This

8.1 Maven or Gradle?

Gradle is the main other build tool. Its build files are shorter. It is usually faster on big projects. That is because you write a Gradle build file in a programming language, not a fixed format.

But that freedom has a cost. A Gradle build can turn into a program of its own. Then someone has to fix its bugs. Maven is strict, so every Maven project looks like every other one. That is dull. But it helps a lot when you learn: a tutorial's project looks just like yours.

Pick Gradle when a build is truly complex, or if you know it from Android work. For learning, Maven's predictability wins.

8.2 Install by hand, or use a version manager?

We installed everything by hand, so you could see every piece. That is worth doing once. A version manager is a tool that installs Java for you. It can also switch between several versions. Examples are SDKMAN! (macOS and Linux), and winget or Chocolatey (Windows). They are better once you need several Java versions side by side.

So why not start with one? Because they hide exactly the PATH details that cause the errors in section 7. Then, when something breaks, you have no idea what happened.

8.3 Pin, or always take the newest?

Pinning means you get the same results every time. The cost: a pinned project slowly falls behind. One day it needs a planned upgrade. In this course, the predicted output must match your screen. So the same results matter far more. Real teams think the same way. They pin, and they plan their upgrades. They do not let upgrades happen by accident.

8.4 When this lesson does not apply

Some workplaces give you a ready-made coding setup. Tools like Dev Containers and GitHub Codespaces do the same. They give you a coding machine in a box, or in your browser, with every tool already installed. Then this setup is done for you.

That is a real option, and more and more common. It uses the same idea as Docker. Docker is a tool that runs programs inside sealed boxes called containers. We meet it properly in Lesson 122. Even then, you should know what is inside the box. That knowledge is what lets you fix the box when something in it goes wrong.

9Challenge

No code for this one. Think it through on paper, then check your answer.

A friend has just set up their machine. They send you this terminal session. They say: "I think something's wrong, but I don't know what."

PS C:\Users\sam> java -version
openjdk version "17.0.11" 2024-04-16
OpenJDK Runtime Environment Temurin-17.0.11+9 (build 17.0.11+9)

PS C:\Users\sam> javac -version
javac 21.0.9

PS C:\Users\sam> mvn -version
Apache Maven 3.9.16
Maven home: C:\tools\apache-maven-3.9.16
Java version: 17.0.11, vendor: Eclipse Adoptium

PS C:\Users\sam> git --version
git version 2.51.0.windows.1
  1. All four commands answered. So is the machine ready? If not, exactly what is wrong?
  2. Which single line in that output is the most alarming, and why?
  3. They build a Spring Boot 4 project pinned to Java 21. Predict what happens. Write the error you expect.
  4. What would you tell them to do, in order?
Click to reveal the answer

1. No, the machine is not ready. Every command answered. But that only proves all four tools are on the PATH. It says nothing about whether they agree with each other. Here, they do not. There are two JDKs installed. java is Java 17, but javac is Java 21. The runtime and the compiler come from different installs.

2. The most alarming line is Java version: 17.0.11 in the mvn -version output. That line decides everything. Maven will build this course's projects. And Maven says it uses Java 17, not 21. Sam might see javac 21.0.9 and think they are on Java 21. But Maven's line tells the truth about what the build will really use. That is why section 5.2 called it the most useful line on the screen.

3. Predicted build error. The project asks for Java 21 output. But Maven uses the Java 17 JDK, which has never heard of version 21:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ ecommerce ---
[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

(Spring Boot 4 works with Java 17 or newer. So Boot is not the one refusing here. The project asks the compiler for a version newer than itself. If the project were pinned to 17, this build would work. That is why this kind of mismatch is so easy to miss.)

4. What to tell them, in order:

  1. Find both JDKs. On Windows, look in C:\Program Files\Eclipse Adoptium\ and similar folders.
  2. Set JAVA_HOME to the Java 21 folder.
  3. Edit PATH. Remove the Java 17 bin entry. Make sure the Java 21 one is there. (If nothing else needs Java 17, think about uninstalling it.)
  4. Close every terminal and open a new one. If they skip this, nothing above seems to work. They will think the fix failed.
  5. Run all four check commands again. Success means java, javac and the Java line of mvn -version all say 21.

The real lesson here: "the command answered" and "the setup is correct" are two different things. To check, you must read what came back, not just see that something came back.

10Key Words

Every new word from this lesson, with a one-line meaning. Come back here whenever a word slips your mind.

Source code
The Java text you write, before any translation.
Processor (CPU)
The chip inside your computer that carries out instructions.
Machine code
Raw number instructions that a processor can run directly.
Compiler
A program that translates source code into something a machine can run.
javac
Java's compiler. It turns .java files into .class files.
Bytecode
Java's in-between format, stored in .class files. Any JVM can run it.
JVM
Java Virtual Machine: the program that reads bytecode and runs it on your real processor.
Operating system
The main program that runs a computer, such as Windows, macOS or Linux.
Server
A computer that runs an app all day so other people can use it.
Standard library
The ready-made classes that come with Java, like String and List.
Runtime
"While a program is running".
JRE
Java Runtime Environment: the JVM plus the standard library. It runs Java but cannot compile it.
JDK
Java Development Kit: the JRE plus tools like javac. You need it to write Java.
LTS
Long Term Support: a version that gets fixes for years, not months.
Terminal
A window where you type commands and the computer answers in text.
Environment variable
A named setting on your computer that every program can read.
PATH
The environment variable that lists the folders your computer searches for commands.
JAVA_HOME
The environment variable that holds the folder where your JDK lives.
Library
Ready-made code that someone else wrote, which your project can use.
JAR
Java ARchive: one file that holds many compiled classes, a bit like a zip file.
Build tool
A program that fetches libraries, compiles, tests and packages your project for you.
Maven
The build tool this course uses.
pom.xml
The file where you tell Maven what your project needs.
Dependency
A library your project needs in order to compile or run.
Maven Central
The big free online store where Maven downloads libraries from.
Transitive dependency resolution
Maven fetching the libraries your libraries need, all the way down the chain.
Plugin
An add-on that does one job for Maven, such as running the compiler.
Test
A small piece of code that checks your real code still works.
IDE
Integrated Development Environment: a code editor that catches mistakes and helps you move around.
Git
A program that keeps a permanent history of your files on your machine.
GitHub
A website that stores a copy of your Git history online.
Repository (repo)
A folder that Git is watching.
Commit
One saved snapshot of the whole project, with a message.
Stage
To choose a file for the next commit.
Branch
A named line of commits. Our main one is called main.
Remote / origin
A copy of the repository somewhere else, such as GitHub. origin is its usual nickname.

A file that lists the files Git must never track.

11Quick Recap

  • javac compiles Java into bytecode, not machine code. The JVM then runs that bytecode on any computer. So one compiled program runs unchanged on Windows, macOS, Linux and inside a container.
  • The JDK contains the JRE, and the JRE contains the JVM. You need the full JDK, because only the JDK has the compiler.
  • Libraries use other libraries. Maven fetches that whole chain for you, from the list in pom.xml.
  • Git keeps a permanent history of your work. So last week's version is always one command away, and you can experiment without fear.
  • You write .gitignore before the first git add. Commits are permanent, so it is far easier to keep a secret out than to get it out.
