Phase 1 · Chapter 0 · Lesson 00

Getting Your Machine Ready

Four tools, four commands that prove they work, and one folder under version control. No Spring yet — this lesson removes the wall that stops most beginners before they ever reach it.

Files created: learning/.gitignore, learning/.gitattributes · Prerequisites: none — this is lesson zero · Pinned: Java 21 LTS · Maven 3.9.16 · Spring Boot 4.1.1

1The Problem

Imagine you sit down tomorrow to build the online store we are going to build together. You know Java. You can write a class, a loop, a method. You open a blank file and type out a perfectly good Product class. You save it. And then you stop, because there is nothing to press.

Your laptop, as it stands, has no idea what to do with a file full of Java. It cannot turn your typing into a running program. It has nothing that fetches the mountain of pre-written code that Spring is made of. It has nothing that remembers yesterday's version of your work when you break something today. The file just sits there, as inert as a shopping list.

This is the wall. It is not an interesting wall — there is no clever concept hiding behind it — but it is the one that ends more programming attempts than any hard idea ever does. People give up during setup, before they have written a single line of anything real, because setup fails silently and confusingly: a command "is not recognized," a download is the wrong one of five options, an error message names a thing they have never heard of. Nothing has gone wrong with their thinking. Their machine simply is not ready.

So we are going to make it ready, deliberately, one tool at a time, and — this is the part most tutorials skip — we are going to prove each one works before moving on. By the end of this lesson you will have typed four commands and seen four answers, and you will know, not hope, that the ground under you is solid.

If you already installed these tools for an earlier run at this course, do not skip the lesson — jump to section 5 and run the four verification commands anyway. Confirming what you have takes ninety seconds; debugging a half-installed toolchain in three lessons' time takes an evening.

2Real World Analogy

Think about a restaurant kitchen on the morning it opens, before a single dish is served. The chef's skill is not in question. But skill alone cooks nothing, because a kitchen needs four things in place first:

In the kitchenWhat it does thereOn your machine
The stove and the knivesTurn raw ingredients into an actual cooked dish. Without them the recipe stays a piece of paper.The JDK — turns your Java text into a running program
The supplierYou do not raise your own cattle. You phone an order and crates arrive at the back door.Maven — fetches the pre-written code your project depends on

The analogy holds in one more way that matters. A chef does not install a stove every time they cook — they do it once, carefully, and then it is simply there for years. That is exactly what this lesson is. One careful morning, and then it is behind you.

3The Concept Explained

Before installing anything, it is worth knowing what each of these things actually is. Installing tools you cannot describe is how people end up with three versions of Java and no idea which one is running.

3.1 What actually happens to Java code

Start with the thing you already do: you write Java into a file. That text is called source code — "source" because everything else is derived from it. It is just text; you could read it aloud.

Your computer's processor cannot read it. A processor understands only machine code: raw numbers that mean things like "add these two values" or "copy this byte over there." The gap between "a Java class about products" and "numbers a chip can execute" has to be crossed by something, and that something is a compiler.

A compiler is simply a program whose job is translation: text in, machine-executable instructions out. Java's compiler is a command called javac ("java compile").

But Java does something unusual, and it is the single most important thing to understand about how Java runs. javac does not produce machine code for your particular laptop. It produces an in-between format called bytecode, saved in files ending in .class. Bytecode is instructions for an imaginary computer that does not physically exist.

That imaginary computer is then impersonated by a real program called the JVM, the Java Virtual Machine. The JVM reads bytecode and performs it on your actual hardware, translating as it goes.

Why design it this way? Because of the alternative. If javac produced Windows machine code, that file would be useless on a Mac, useless on the Linux server you eventually deploy to, and useless to a colleague on different hardware. You would compile your program separately for every machine it might ever touch. The bytecode-plus-JVM design pays a small cost in speed to buy something worth far more: the compiled result is genuinely portable. When we put this application in a container in Phase 3 and ship it to a cloud machine you will never see, this decision from 1995 is what makes that a non-event.

3.2 JDK, JRE, JVM — three names, one set of Russian dolls

These three get confused constantly, and the confusion has a real cost, so let us be exact. They are nested, smallest first:

NameStands forWhat is in itLets you…
JVMJava Virtual MachineThe engine that executes bytecoderun bytecode
JREJava Runtime EnvironmentThe JVM plus the standard library — the thousands of ready-made classes like String and Listrun finished Java programs
JDKJava Development KitThe JRE plus the development tools — above all javac, the compilerwrite and compile your own Java

The word that matters is Kit. A JRE is for someone who only ever runs Java that somebody else compiled. You are going to write Java, so you need the compiler, so you need the JDK. Installing a JRE by mistake produces one of the most baffling beginner errors there is: Java is clearly installed, yet nothing you write will compile.

Check yourself: a colleague says "Java is definitely installed, I can run programs, but javac says command not found." What happened?

They almost certainly have a JRE rather than a JDK. The JRE contains the JVM and can therefore run compiled programs perfectly well, but it ships no compiler — javac is a development tool, and development tools live only in the Kit. The fix is to install a JDK. (The other possible cause is a broken PATH, which section 3.4 covers — but if java works and javac does not, a JRE is the overwhelming favourite.)

3.3 Why Java 21, and what "LTS" means

Java releases a new version every six months. Most of those are supported for only six months — long enough to try, too short to build a business on. Every few years one release is designated LTS, Long Term Support, meaning it keeps receiving security fixes for years.

Companies build on LTS releases, so tutorials, libraries and answers to your questions cluster around them. We pin Java 21, an LTS with an enormous ecosystem, which is also the release that introduced virtual threads — a feature we study properly in Phase 3.

Spring Boot 4 requires Java 17 as an absolute minimum and encourages the latest LTS, so 21 sits comfortably inside what the framework supports.

3.4 The terminal, and the one environment variable that breaks everything

A terminal is a window where you talk to your computer by typing instead of clicking. On Windows that is PowerShell or Windows Terminal; on macOS and Linux it is Terminal. Nearly every tool in this course is driven from there, because typing a command is precise, repeatable, and easy to paste into a lesson.

When you type java and press Enter, your computer has to find a program with that name. It does not search your whole hard disk — that would take forever. Instead it consults a list of folders called PATH, and looks in each one, in order, for something called java. If it checks every folder on that list and finds nothing, it gives up with the single most common setup error in existence:

java : The term 'java' is not recognized as the name of a cmdlet, function,
script file, or operable program.

Read that sentence again with what you now know, and it stops being frightening. It does not mean Java failed. It does not mean Java is broken. It means: I looked in every folder on my PATH list and none of them contained a program called java. Either Java is not installed, or it is installed somewhere that is not on the list. That is the whole message.

Why "environment variable"? It is simply a named setting that belongs to your whole computing session rather than to any one program — part of the environment your programs run inside. PATH is the famous one. We will meet environment variables again for a completely different reason in Lesson 39, where they become the correct place to keep passwords and secret keys.

3.5 What a build tool is, and the problem that created it

Suppose you have your JDK and you write one file. You can compile it by hand: javac Product.java. Fine. Now let us grow it into something real, and watch the hand method collapse.

First: real projects have hundreds of files across many folders, and they depend on each other in a specific order. Compiling them by hand means typing out every path, every time.

Second, and far worse: you will not write everything yourself. Nobody does. You will use libraries — bundles of pre-written code that solve problems already solved. Spring Boot is made of dozens of them. A library arrives as a JAR file (Java ARchive: one file containing many compiled classes). Doing this by hand means finding the right website, downloading the right JAR, putting it somewhere sensible, and telling javac where it is.

Third, and this is the part that actually breaks people: libraries have their own libraries. You want library A; A was built using B and C; C needs D and E. Miss one and you get an error at runtime, often long after startup, naming a class you have never heard of. Get two different versions of the same library and you get a subtler, nastier failure. Chasing these by hand is called "JAR hell," and it was a genuine, ordinary, week-consuming part of Java development before build tools existed.

A build tool takes all of that over. You write down what you want; it works out how. Maven, the build tool we use, works like this:

  1. You list what your project needs in a file called pom.xml — each entry is a dependency.
  2. Maven reads the list and downloads each one from Maven Central, a vast public warehouse of published Java libraries.
  3. For each library, it reads that library's own list of needs and downloads those too, and so on down the chain. This automatic chasing is called transitive dependency resolution, and it is the feature that killed JAR hell.
  4. It stores everything in a local folder (.m2 in your home directory) so the second build does not re-download the internet.
  5. Then it compiles your code in the right order, runs your tests, and packages the result.

This is why one line in a file can give you an entire web server, and why Lesson 02 spends its time on pom.xml rather than on javac.

3.6 The IDE

An IDE is a text editor that understands the language you are writing. It underlines a typo before you compile, jumps you to where a method is defined, suggests completions, and renames things safely across an entire project. You could write this course in Notepad; you would simply be slower and make more mistakes that a machine could have caught for free.

3.7 Git and GitHub: two different things with similar names

Git is a program on your machine that records the history of your files. GitHub is a website that stores a copy of that history online. Git is the tool; GitHub is one place to keep a copy. You can use Git with no GitHub account at all.

Four words carry almost all of Git, and each is worth having straight:

  • A repository (or "repo") is a folder whose contents Git is tracking. Ours will be the learning folder.
  • A commit is one saved snapshot of the whole project, with a message saying what changed and why. Not a backup of one file — a photograph of everything, at that instant.
  • A remote is a copy of the repository living somewhere else. Ours will be on GitHub, named origin by convention.
  • To push is to send your new commits to the remote.

Why does this matter on day one, before there is anything to lose? Because of what it does to your nerve. With a history, breaking things costs nothing — last working version is one command away, so you experiment freely. Without one, every change is a small gamble, and beginners respond by not changing anything, which is precisely how you stop learning. Git is not bookkeeping. It is permission to be brave.

A public GitHub repository with real commits is the closest thing a self-taught developer has to a résumé. An interviewer can see what you built, how you work, and that you stuck with something for months. By the end of this course yours will hold a complete microservices system with an AI assistant in it — which is a considerably better answer to "show me something you have built" than a certificate.

3.8 Pinning versions, and why this course does it out loud

To pin a version is to fix it deliberately and write it down, rather than accepting whatever is newest on the day. This course pins Java 21, Maven 3.9.16 and Spring Boot 4.1.1.

Pinning matters here more than usual, for a specific reason: throughout this course you will be shown predicted output — exactly what a command or a request should produce — and asked to compare it against what your machine really does. That comparison is only meaningful if we are both talking about the same versions. On a different major version the output genuinely differs, and you would be left unable to tell a real mistake from a harmless version difference.

One promise, made now and kept in every lesson. This course is built on Spring Boot 4. Nearly everything you will find online — tutorials, books, videos, Stack Overflow answers — was written for Spring Boot 2 or 3, and several things were renamed in between. The very first one you will meet, in Lesson 02:

spring-boot-starter-web spring-boot-starter-webmvc

Copy that line from a 2024 tutorial into our project and it will simply fail to resolve, with an error that explains nothing. So wherever Boot 4 differs from what the rest of the internet says, a card exactly like this one will appear at that moment, telling you what changed, why, and how to translate the older material you are reading. You are not being left to find out alone.

Check yourself: why not simply teach Spring Boot 3, since that is what most tutorials use?

Because Spring Boot 3 reached open-source end of life on 30 June 2026. Learning it would mean learning a version that receives no more security fixes, and then immediately needing to migrate. The better trade is to learn the current version and be taught the differences explicitly — which gives you both the modern skill and the ability to read the older material, rather than one or the other.

4The Wrong Way

Wrong approach — "I'll install things when something breaks"

The tempting shortcut is to skip ahead, grab a Spring Boot project from somewhere, and start installing only what the errors demand. Here is what that actually looks like, step by step.

Attempt 1 — nothing installed. You download a project and try to build it.

PS D:\Projects\store> mvn spring-boot:run

Predicted output:

mvn : The term 'mvn' is not recognized as the name of a cmdlet, function, script
file, or operable program. Check the spelling of the name, or if a path was
included, verify that the path is correct and try again.

Nothing about that message says "install Maven." It talks about cmdlets and spelling. A beginner reasonably concludes they typed something wrong and tries again, more carefully, with the same result.

Attempt 2 — Maven installed, but only a JRE. You install Maven, and you install "Java" by clicking the first big download button you find, which on many sites gives you a JRE.

Predicted output:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ store ---
[ERROR] No compiler is provided in this environment. Perhaps you are running
on a JRE rather than a JDK?
[INFO] BUILD FAILURE

This one is unusually kind — it names the actual problem. Most do not. And notice you have now burned an hour discovering a fact that section 3.2 gave you in a table.

Attempt 3 — JDK installed, but the wrong version. You install whatever JDK came up first, an older Java 11, and build a Spring Boot 4 project.

Predicted output:

[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

"Invalid target release" means: you asked me to produce Java 21 output, and I am an older compiler that has never heard of 21. Again — decipherable once you know the model, opaque before.

And the failure that has no error message at all: you get everything working, spend a week building, break something badly on a Friday, and discover there is no history to go back to because Git was "something to set up later." There is no red text for this one. There is just lost work.

The pattern across all four: each failure is cheap to prevent and expensive to diagnose. That asymmetry is the entire argument for doing setup deliberately, in order, verifying as you go.

5The Right Way

Correct approach — install in dependency order, and prove each step before the next

The order below is not arbitrary. Maven needs a JDK to run, so the JDK comes first. Git should exist before we create the project folder, so that the very first thing that folder ever contains is a .gitignore. Follow it top to bottom.

5.1 Step one: install the JDK (Java 21 LTS)

Several organisations publish builds of Java 21. They are all the same language; they differ in packaging and support. Any of these is fine — Eclipse Temurin is the common, no-account-required choice:

  • Eclipse Temurin 21 (LTS) — adoptium.net
  • Microsoft Build of OpenJDK 21 — convenient on Windows
  • Amazon Corretto 21, Azul Zulu 21 — also fine

Download the JDK (not the JRE) for Java 21, for your operating system, and run the installer. On Windows, if the installer offers a checkbox along the lines of "Set JAVA_HOME variable" or "Add to PATH", tick it — that is section 3.4's problem being solved for you.

Prove it works. Open a brand-new terminal window (an already-open one still has the old PATH) and run both of these:

java -version
javac -version

Predicted output (your exact patch number and vendor wording will differ — that is fine):

openjdk version "21.0.9" 2026-10-20
OpenJDK Runtime Environment Temurin-21.0.9+7 (build 21.0.9+7)
OpenJDK 64-Bit Server VM Temurin-21.0.9+7 (build 21.0.9+7, mixed mode, sharing)

javac 21.0.9

What to actually check, in order of importance:

  1. Both commands answered at all — so they are on your PATH.
  2. Both say 21. If java says 21 and javac says something else, you have two JDKs fighting; see section 7.
  3. javac answered — so you have a JDK, not a JRE.

5.2 Step two: install Maven 3.9.16

Maven is not an installer — it is a folder of files plus a PATH entry. On Windows:

  1. Download apache-maven-3.9.16-bin.zip from maven.apache.org/download.cgi.
  2. Unzip it somewhere permanent and space-free, e.g. C:\tools\apache-maven-3.9.16. (Avoid folder names with spaces; some older tooling still mishandles them.)
  3. Add C:\tools\apache-maven-3.9.16\bin to your PATH: press Start, type "environment variables", open Edit the system environment variables → Environment Variables… → select Path → Edit → New → paste the path → OK out of all three dialogs.
  4. Close every terminal window and open a new one. PATH is read when a terminal starts; existing windows will not see the change.

On macOS with Homebrew: brew install maven. On Debian/Ubuntu: sudo apt install maven (then check the version it gave you).

Prove it works. In a new terminal:

mvn -version

Predicted output:

Apache Maven 3.9.16 (a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0)
Maven home: C:\tools\apache-maven-3.9.16
Java version: 21.0.9, vendor: Eclipse Adoptium, runtime: C:\Program Files\Eclipse Adoptium\jdk-21.0.9-hotspot
Default locale: en_GB, platform encoding: UTF-8
OS name: "windows 11", version: "10.0", arch: "amd64", family: "windows"

Notice the third line. mvn -version reports which Java it found, which is quietly the most useful thing on the screen — it is how you catch Maven running on a different JDK from the one you expect. It must say 21.

5.3 Step three: install an IDE

Two good choices, both free:

IntelliJ IDEA Community EditionVisual Studio Code

If you have no preference, take IntelliJ IDEA Community Edition. Its Java support will teach you things by pointing them out. There is no verification command here — if it opens, it works.

5.4 Step four: install Git and create a GitHub account

Download Git from git-scm.com and install it. On Windows the installer asks a long series of questions; the defaults are sensible, and the only one worth a thought is the default editor — pick one you can actually exit, such as Notepad++ or VS Code, rather than Vim.

Then create a free account at github.com, and create a new, completely empty repository:

  • Name it something like spring-boot-learning.
  • Public or private — both fine. Public is nice later, for the reason in the callout above.
  • Do not tick "Add a README," "Add .gitignore," or "Choose a license." We want it genuinely empty; a repository that already has commits in it makes the next step fiddlier than it needs to be.

Prove it works, and introduce yourself to Git (it stamps every commit with this name and email, so do it once, now):

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Predicted output — the first command answers, the other two print nothing at all, which is Git's way of saying "done":

git version 2.51.0.windows.1

Silence as success takes getting used to. Many command-line tools print nothing when they succeed and speak only when something is wrong.

All four tools at once. Run these four lines in one new terminal. Four answers, no "not recognized" — that is a ready machine, and it is the checkpoint this whole lesson exists to reach.

java -version
javac -version
mvn -version
git --version

Compare each against the predictions above. If any of them differs in a way you did not expect, the machine is right and the lesson is wrong — bring me exactly what you saw and we will work out why.

6Applied to Our Project

This lesson teaches no Spring Boot feature — there is no annotation to write and no code to run, because the tools that would run it did not exist twenty minutes ago. So there is no project code here, and that is correct rather than a shortcut. What we can do now is create the home everything else will live in, and put it under version control before it contains anything worth losing.

6.1 Create the folder and make the first file a .gitignore

Order matters here in a way that is easy to underestimate. Git only tracks what you tell it to, but the usual first command tells it to track everything. If a file you never wanted stored is present at that moment, it goes in — and Git history is designed to be permanent, so removing it later is genuinely awkward. Therefore: the ignore list is written before the first git add, never after.

Create a folder called learning wherever you keep projects, and inside it create a file named exactly .gitignore (leading dot, no extension) containing:

# Local-only course control files - never commit these
CLAUDE.md
curriculum.md
progress-tracker.md

# Maven / Java build output - generated, never stored
target/
*.class

# IDEs - personal to your machine, not to the project
.idea/
*.iml
.vscode/

# Local Claude Code settings - machine-specific
.claude/

# Real secrets - never commit; application.yml + .env.example are the templates
**/application-local.yml
.env

Every line earns its place:

  • The three course files are your local control files. They are yours, not the project's.
  • target/ and *.class are Maven's output — compiled bytecode, regenerated from source on every build. Committing generated files bloats history and causes pointless conflicts. Rule of thumb: if a build can recreate it, do not store it.
  • IDE folders hold your personal layout and preferences. Another developer's copy would conflict with yours, and neither is part of the program.
  • application-local.yml and .env are where real passwords and API keys will live from Lesson 39 onwards. This line is in place now, months early, precisely so that a secret can never accidentally land in history later. Git history is forever; a leaked key is leaked permanently, even if the next commit deletes it.

Add one more file next to it, called .gitattributes:

# Normalise line endings so the repo behaves identically on Windows and Linux
* text=auto eol=lf

Windows and Linux disagree about how a line ends — Windows uses two invisible characters, Linux one. Left alone, this produces the maddening experience of Git reporting that every line of a file changed when you altered none of them. This one line settles it permanently.

6.2 Put it under version control

Now, and only now, from inside the learning folder:

# 1. Start tracking this folder. Creates the hidden .git directory that IS the history.
git init

# 2. Stage everything not excluded by .gitignore, ready for the first snapshot.
git add .

# 3. Take the snapshot, with a message explaining it.
git commit -m "chore: initial course setup"

# 4. Name the main line of development 'main' (the modern default).
git branch -M main

# 5. Record where the online copy lives. Use YOUR repository URL from GitHub.
git remote add origin https://github.com/your-username/your-repo.git

# 6. Send the commit up, and remember this destination for future pushes (-u).
git push -u origin main

6.3 What would happen, step by step

  1. git init creates a hidden .git folder. That folder is the repository — delete it and you have plain files again, with no history.
  2. git add . walks the folder, consults .gitignore, and stages everything not excluded. Because you wrote the ignore list first, your three local-only files are skipped automatically — you never have to remember to avoid them.
  3. git commit writes the staged snapshot permanently and labels it with your message.
  4. git branch -M main renames the default line of work to main, matching GitHub's default.
  5. git remote add origin … just saves an address under the nickname origin. Nothing is sent yet.
  6. git push -u origin main uploads the commit and links your local main to the remote one, so future pushes need only git push. A browser or credential prompt may appear the first time so GitHub can confirm it is you.

Predicted output of the commit and the push:

$ git commit -m "chore: initial course setup"
[main (root-commit) a1b2c3d] chore: initial course setup
 2 files changed, 21 insertions(+)
 create mode 100644 .gitattributes
 create mode 100644 .gitignore

$ git push -u origin main
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Writing objects: 100% (4/4), 412 bytes | 412.00 KiB/s, done.
To https://github.com/your-username/your-repo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

Run it, then check two things. First, git status should report a clean tree:

git status

Predicted:

On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

Second — and this is the one that matters — refresh your repository page on GitHub. You should see .gitattributes and .gitignore, and you should not see CLAUDE.md, curriculum.md or progress-tracker.md. If those three are missing from GitHub but present on your disk, the ignore list did its job exactly as designed.

Check yourself: why write .gitignore before git add . rather than after?

Because git add . stages everything that is not already excluded, and a commit is permanent. If a secret or a local-only file is present when you first run git add ., it is captured into history — and deleting it in a later commit does not remove it from the earlier one, which anyone with the repository can still read. Writing the ignore list first means the unwanted files are never staged in the first place. It is the difference between not letting something in and trying to get it back out.

7Gotchas and Common Mistakes

  • Changing PATH and leaving the terminal open. A terminal reads PATH once, when it starts. Update PATH and your existing window keeps insisting mvn does not exist — the fix is to close it and open a new one. On Windows a full sign-out occasionally helps. People reinstall Maven three times over this.
  • Two JDKs, and the wrong one in charge. Symptom: java -version and mvn -version disagree about Java, or javac reports a different version from java. Cause: an old JDK left on the machine, and PATH finds it first. Fix: set JAVA_HOME to your Java 21 folder explicitly, and remove the old entry from PATH. Always trust the version line in mvn -version over what you believe is installed.
  • Installing a JRE instead of a JDK. Download pages often push the runtime, because most visitors only want to run Java. java works, javac does not, and the eventual build error mentions a compiler rather than a download. Verify with javac -version every time, not just java -version.
  • Committing something that should have stayed local. Usually from running git add . before writing .gitignore, or from forcing a file in with git add -f. Never use -f on the three course files. If a real secret does get committed, treat it as leaked: rotate the key first, then worry about the history.
  • Spaces and non-English characters in folder paths. Unzipping Maven under a path containing spaces, or a project under a path with accented characters, still confuses some tooling in ways whose error messages point nowhere near the real cause. Keep tool and project paths plain.
  • Assuming an IDE's bundled JDK is the one your terminal uses. IntelliJ can ship and manage its own JDK. It is entirely possible for the IDE to compile happily while mvn in a terminal fails, because they are using different Javas. The terminal is the source of truth in this course, since that is where every command in these lessons is run.

8Tradeoffs and When Not to Use This

Maven versus Gradle. Gradle is the main alternative build tool. Its build files are shorter and it is usually faster on large projects, because it is a programming language rather than a fixed structure. That flexibility is also its cost: a Gradle build can become a program in its own right, which someone then has to debug. Maven's rigidity means every Maven project looks like every other Maven project — dull, and enormously helpful when you are learning, because a tutorial's structure matches yours. Pick Gradle when builds are genuinely complex or you have Android habits; for learning, Maven's predictability wins.

Manual installs versus a version manager. We installed by hand, which makes every piece visible — worth it once. Tools such as SDKMAN! (macOS/Linux) or winget/Chocolatey (Windows) automate it, and are genuinely better once you need several Java versions side by side. The reason not to start there: they hide exactly the PATH mechanics that cause the errors in section 7, so when something breaks you have no model of what happened.

Pinning versus always taking the latest. Pinning buys reproducibility and costs currency — a pinned project drifts behind and eventually needs a deliberate upgrade. For a course where predicted output must match your screen, reproducibility is worth far more. On a real team the same logic applies with a twist: pin, and schedule the upgrades rather than absorbing them by accident.

When this lesson does not apply. If you work somewhere with a managed development image, or you use a Dev Container or GitHub Codespaces, the whole toolchain arrives pre-built and this setup is done for you. That is a real and increasingly common option — and it is precisely the idea behind Docker, which we meet properly in Lesson 120. Even then, knowing what is inside the box is what lets you fix it when the box is wrong.

9Key Takeaways

  • Java code is compiled by javac into portable bytecode rather than machine code, and the JVM then executes that bytecode on whatever hardware it finds itself on, which is why one compiled program runs unchanged on Windows, macOS, Linux and inside a container.
  • The JDK contains the JRE, which contains the JVM; you need the full JDK because only it ships the compiler, and installing a JRE by mistake produces the confusing situation where Java clearly runs yet nothing you write will build.
  • A build tool exists because real projects depend on libraries that depend on other libraries, and Maven resolves that entire chain automatically from a list you write in pom.xml — which is why a single dependency line can hand you a complete web server.
  • Git gives you a permanent, versioned history of your work, and its real value on day one is psychological: with last week's version always one command away, you can experiment freely instead of treating every change as a gamble.
  • Writing .gitignore before the first git add is a deliberate ordering, not a formality, because commits are permanent and it is far easier to never admit a secret into history than to remove one afterwards.

10Challenge

No code for this one — reason it through on paper, then check yourself against the answer.

A friend has just set up their machine and sends you this terminal session, saying "I think something's wrong but I don't know what."

PS C:\Users\sam> java -version
openjdk version "17.0.11" 2024-04-16
OpenJDK Runtime Environment Temurin-17.0.11+9 (build 17.0.11+9)

PS C:\Users\sam> javac -version
javac 21.0.9

PS C:\Users\sam> mvn -version
Apache Maven 3.9.16
Maven home: C:\tools\apache-maven-3.9.16
Java version: 17.0.11, vendor: Eclipse Adoptium

PS C:\Users\sam> git --version
git version 2.51.0.windows.1
  1. All four commands answered. So is the machine ready? If not, exactly what is wrong?
  2. Which single line in that output is the most alarming, and why?
  3. Predict what happens when they build a Spring Boot 4 project pinned to Java 21, and write the error you would expect.
  4. What would you tell them to do, in order?
Click to reveal the answer

1. No, the machine is not ready. Every command answering only proves all four tools are on the PATH. It says nothing about whether they agree with each other — and here they do not. There are two JDKs installed: java is Java 17, while javac is Java 21. The runtime and the compiler are from different installations.

2. The most alarming line is Java version: 17.0.11 in the mvn -version output. That is the decisive one, because Maven is what will actually build this course's projects, and it reports that it is running on Java 17, not 21. Sam might reasonably look at javac 21.0.9 and conclude they are on Java 21; Maven's line tells the truth about what the build will really use. This is exactly why section 5.2 called that line the most useful thing on the screen.

3. Predicted build error. The project asks for Java 21 output, and the JDK Maven is using is 17, which has never heard of release 21:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ ecommerce ---
[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

(Spring Boot 4 requires Java 17 as a minimum, so the failure here is not Boot refusing 17 — it is the compiler being asked for a release newer than itself. Had the project been pinned to 17, this particular build would have succeeded, which is what makes the mismatch so easy to leave lurking.)

4. What to tell them, in order:

  1. Find both JDKs — on Windows, look in C:\Program Files\Eclipse Adoptium\ and similar folders.
  2. Set JAVA_HOME explicitly to the Java 21 folder.
  3. Edit PATH: remove the Java 17 bin entry, and make sure the Java 21 one is present. (Consider uninstalling 17 entirely if nothing else needs it.)
  4. Close every terminal and open a new one — otherwise nothing above appears to have worked, and they will conclude the fix failed.
  5. Re-run all four verification commands. Success is java, javac and the Java line of mvn -version all saying 21.

The lesson underneath the puzzle: "the command answered" and "the setup is correct" are different claims. Verification means reading what came back, not just noting that something came back.
