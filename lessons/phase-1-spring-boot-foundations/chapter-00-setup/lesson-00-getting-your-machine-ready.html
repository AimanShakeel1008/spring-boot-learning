Getting Your Machine Ready

Four tools, four commands that prove they work, and one folder that Git keeps a history of. No Spring yet. This lesson removes the wall that stops most beginners before they ever get to Spring.

Files created: learning/.gitignore, learning/.gitattributes · Prerequisites: none (this is lesson zero) · Pinned: Java 21 LTS · Maven 3.9.16 · Spring Boot 4.1.1

1The Problem

Imagine you sit down tomorrow to build the online store we are going to build together. You know Java. You can write a class, a loop, a method. You open a blank file and type out a perfectly good Product class. You save it. And then you stop, because there is nothing to press.

Right now, your laptop has no idea what to do with a file full of Java. It cannot turn your typing into a running program. It has nothing to fetch the huge amount of ready-made code that Spring is made of. It has nothing to remember yesterday's version of your work when you break something today. The file just sits there, as useless as a shopping list.

This is the wall. There is no clever idea hiding behind it. But it ends more attempts at programming than any hard idea does. People give up during setup, before they have written one real line of code. Setup fails in silent, confusing ways. A command "is not recognized". A download page offers five options and you pick the wrong one. An error message names something you have never heard of. Nothing is wrong with your thinking. Your machine just is not ready yet.

So we will get it ready on purpose, one tool at a time. And we will do the part most tutorials skip: we will prove each tool works before moving on. By the end of this lesson you will have typed four commands and seen four answers. You will know, not just hope, that everything is in place.

Already installed these tools before? Do not skip the lesson. Jump to section 5 and run the four check commands anyway. Checking takes ninety seconds. Fixing a half-installed setup three lessons from now takes a whole evening.

2Real World Analogy

Think about a restaurant kitchen on the morning it opens, before any food is served. The chef is skilled. But skill alone cooks nothing. A kitchen needs four things in place first:

In the kitchenWhat it does thereOn your machine
The stove and the knivesTurn raw ingredients into a cooked dish. Without them, the recipe stays a piece of paper.The JDK: turns your Java text into a running program
The supplierYou do not grow your own vegetables. You phone in an order, and boxes arrive at the back door.Maven: fetches the ready-made code your project needs

The kitchen teaches one more thing. A chef does not install a new stove every time they cook. They install it once, carefully, and then it is there for years. This lesson is the same. One careful morning, and then setup is behind you.

3The Concept Explained

Before installing anything, it helps to know what each tool actually is. People who install tools they cannot describe end up with three versions of Java and no idea which one is running.

3.1 What actually happens to Java code

Start with what you already do: you write Java into a file. That text is called source code. It is called "source" because everything else is made from it. It is just text. You could read it aloud.

Your computer's processor cannot read it. A processor understands only machine code. Machine code is raw numbers that mean things like "add these two values" or "copy this byte over there". Something has to turn "a Java class about products" into "numbers a chip can run". That something is a compiler.

A compiler is a program whose job is translation. Text goes in, and instructions a machine can run come out. Java's compiler is a command called javac (short for "java compile").

But Java does something unusual here. It is the most important thing to understand about how Java runs. javac does not produce machine code for your laptop. It produces an in-between format called bytecode. Bytecode is saved in files ending in .class. It is a set of instructions for an imaginary computer that does not really exist.

A real program then pretends to be that imaginary computer. This program is called the JVM, the Java Virtual Machine. The JVM reads bytecode and carries it out on your real hardware, translating as it goes.

Why design it this way? Look at the other choice. Suppose javac produced Windows machine code. That file would not work on a Mac. It would not work on the Linux server you later put your app on. It would not work on a colleague's different computer. You would have to compile your program again for every kind of machine. The bytecode-and-JVM design costs a little speed. In return, the compiled file works everywhere. In Phase 3 we will send this application to a cloud machine you will never see. This choice, made in 1995, is why that will be easy.

3.2 JDK, JRE, JVM — three names, one set of nesting dolls

People mix these three up all the time, and the mix-up causes real problems. So let us be exact. They fit inside each other, smallest first:

NameStands forWhat is in itLets you…
JVMJava Virtual MachineThe engine that runs bytecoderun bytecode
JREJava Runtime EnvironmentThe JVM plus the standard library: thousands of ready-made classes like String and Listrun finished Java programs
JDKJava Development KitThe JRE plus the tools for writing Java. The most important one is javac, the compilerwrite and compile your own Java

The word that matters is Kit. A JRE is for someone who only ever runs Java that someone else compiled. You are going to write Java. So you need the compiler, and so you need the JDK. If you install a JRE by mistake, you get one of the most confusing beginner errors there is. Java is clearly installed, yet nothing you write will compile.

Check yourself: a colleague says "Java is definitely installed, I can run programs, but javac says command not found." What happened?

They almost certainly have a JRE, not a JDK. The JRE contains the JVM, so it can run compiled programs. But it has no compiler. javac is a tool for writing Java, and those tools come only in the Kit. The fix is to install a JDK. (A broken PATH can also cause this; section 3.4 covers it. But if java works and javac does not, a JRE is by far the most likely cause.)

3.3 Why Java 21, and what "LTS" means

A new version of Java comes out every six months. Most versions get fixes for only six months. That is long enough to try them, but too short to build a business on. Every few years, one version is marked LTS, which stands for Long Term Support. An LTS version keeps getting security fixes for years.

Companies build on LTS versions. So most tutorials, libraries and answers to your questions are about them. We pin Java 21. It is an LTS version, and a huge number of tools support it. It is also the version that added virtual threads, a feature we study properly in Phase 3.

Spring Boot 4 needs at least Java 17, and it recommends the newest LTS. Java 21 is well within what it supports.

3.4 The terminal, and the one environment variable that breaks everything

A terminal is a window where you talk to your computer by typing instead of clicking. On Windows it is PowerShell or Windows Terminal. On macOS and Linux it is Terminal. Nearly every tool in this course is used from the terminal. A typed command is exact, you can repeat it, and it is easy to paste into a lesson.

When you type java and press Enter, your computer has to find a program with that name. It does not search your whole hard disk; that would take forever. Instead it checks a list of folders called PATH. It looks in each folder, in order, for something called java. If no folder on the list has it, it gives up. This is the most common setup error there is:

java : The term 'java' is not recognized as the name of a cmdlet, function,
script file, or operable program.

Read that message again with what you now know, and it stops being scary. It does not mean Java failed. It does not mean Java is broken. It means: I looked in every folder on my PATH list, and none of them had a program called java. Either Java is not installed, or it is installed in a folder that is not on the list. That is all the message says.

Why "environment variable"? It is a named setting that belongs to your whole computer session, not to one program. It is part of the "environment" your programs run in. PATH is the best-known one. We meet environment variables again in Lesson 39, for a different reason. There, they become the right place to keep passwords and secret keys.

3.5 What a build tool is, and the problem that created it

Say you have your JDK and you write one file. You can compile it by hand: javac Product.java. Fine. Now let us grow it into something real, and watch the by-hand method fall apart.

First: real projects have hundreds of files in many folders. The files depend on each other, so they must be compiled in the right order. Compiling them by hand means typing out every path, every time.

Second, and much worse: you will not write everything yourself. Nobody does. You will use libraries. A library is a bundle of ready-made code that someone else wrote to solve a common problem. Spring Boot is made of dozens of them. A library comes as a JAR file. JAR stands for Java ARchive: one file holding many compiled classes. To use a library by hand, you find the right website and download the right JAR. Then you put it somewhere sensible and tell javac where it is.

Third, and this is what really breaks people: libraries use other libraries. You want library A. A was built using B and C. C needs D and E. Miss one, and you get an error while the program runs, often long after it started. The error names a class you have never heard of. Get two different versions of the same library, and you get a harder, nastier failure. Chasing these down by hand is called "JAR hell". Before build tools existed, it could easily eat a week.

A build tool takes all of that over. You write down what you want, and it works out how. Maven, the build tool we use, works like this:

  1. You list what your project needs in a file called pom.xml. Each item on the list is a dependency.
  2. Maven reads the list and downloads each item from Maven Central. Maven Central is a huge public store of Java libraries.
  3. For each library, Maven reads that library's own list of needs and downloads those too. It keeps going down the chain until nothing is missing. This automatic chasing is called transitive dependency resolution. It is the feature that ended JAR hell.
  4. It saves everything in a local folder (.m2 in your home folder). So the second build does not download it all again.
  5. Then it compiles your code in the right order, runs your tests, and packages the result.

This is why one line in a file can give you a whole web server. It is also why Lesson 02 spends its time on pom.xml, not on javac.

3.6 The IDE

An IDE is a text editor that understands the language you are writing. It underlines a typo before you compile. It jumps to where a method is defined. It suggests how to finish what you are typing. It can safely rename something everywhere in a project. You could do this course in Notepad. You would just be slower, and make more mistakes that a machine could have caught for free.

3.7 Git and GitHub: two different things with similar names

Git is a program on your machine that records the history of your files. GitHub is a website that keeps a copy of that history online. Git is the tool. GitHub is one place to keep a copy. You can use Git without a GitHub account at all.

Four words cover almost all of Git. Each is worth getting clear:

  • A repository (or "repo") is a folder whose contents Git is tracking. Ours will be the learning folder.
  • A commit is one saved snapshot of the whole project, with a message saying what changed and why. It is not a backup of one file. It is a photo of everything, at that moment.
  • A remote is a copy of the repository kept somewhere else. Ours will be on GitHub. By habit, it is named origin.
  • To push is to send your new commits to the remote.

Why does this matter on day one, before there is anything to lose? Because of what it does to your nerve. With a history, breaking things costs nothing. The last working version is one command away, so you can experiment freely. Without a history, every change is a small gamble. Beginners react by not changing anything, and that is exactly how you stop learning. Git is not just record-keeping. It gives you permission to be brave.

A public GitHub repository with real commits is the closest thing a self-taught developer has to a CV. An interviewer can see what you built and how you work. They can see you stuck with something for months. By the end of this course, yours will hold a complete microservices system with an AI assistant in it. When someone says "show me something you have built", that is a much better answer than a certificate.

3.8 Pinning versions, and why this course does it out loud

To pin a version means to choose one on purpose and write it down. You do not just take whatever is newest that day. This course pins Java 21, Maven 3.9.16 and Spring Boot 4.1.1.

Pinning matters more than usual here, for one reason. All through this course, you will see predicted output: exactly what a command or a request should print. Then you will compare it with what your machine really prints. That comparison only works if we both use the same versions. With a different major version, the output really does change. Then you could not tell a real mistake from a harmless version difference.

Here is a promise, made now and kept in every lesson. This course is built on Spring Boot 4. Nearly everything you will find online was written for Spring Boot 2 or 3. That includes tutorials, books, videos and Stack Overflow answers. Several things were renamed since then. Here is the first one you will meet, in Lesson 02:

spring-boot-starter-web spring-boot-starter-webmvc

If you copy the old name from a 2024 tutorial, it still works for now. But it is deprecated: marked as old, and due to be removed in a later version. It also no longer matches the rest of this course. Other renamed things simply break, with an error that does not say why. So when Boot 4 differs from the rest of the internet, a card like this one will appear right there. It will tell you what changed, why it changed, and how to translate the older material you are reading. You will not be left to find out alone.

Check yourself: why not just teach Spring Boot 3, since that is what most tutorials use?

Because free support for Spring Boot 3 ended on 30 June 2026. It gets no more security fixes. If you learned it, you would have to move to version 4 straight away. It is better to learn the current version and be taught the differences clearly. That way you get the modern skill and you can still read the older material.

4The Wrong Way

Wrong approach — "I'll install things when something breaks"

The tempting shortcut is to skip ahead. You grab a Spring Boot project from somewhere and only install what the errors ask for. Here is what that really looks like, step by step.

Attempt 1 — nothing installed. You download a project and try to build it.

PS D:\Projects\store> mvn spring-boot:run

Predicted output:

mvn : The term 'mvn' is not recognized as the name of a cmdlet, function, script
file, or operable program. Check the spelling of the name, or if a path was
included, verify that the path is correct and try again.

Nothing in that message says "install Maven". It talks about cmdlets and spelling. So a beginner thinks they made a typo. They try again, more carefully, and get the same result.

Attempt 2 — Maven installed, but only a JRE. You install Maven. Then you install "Java" by clicking the first big download button you see. On many sites, that button gives you a JRE.

Predicted output:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ store ---
[ERROR] No compiler is provided in this environment. Perhaps you are running
on a JRE rather than a JDK?
[INFO] BUILD FAILURE

This message is unusually kind. It names the real problem. Most error messages do not. And you have now spent an hour finding out something that section 3.2 told you in a table.

Attempt 3 — JDK installed, but the wrong version. You install the first JDK you find, an older Java 11. Then you build a Spring Boot 4 project.

Predicted output:

[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

"Invalid target release" means: "You asked me to produce Java 21 output. I am an older compiler, and I have never heard of 21." Once you know how the pieces fit, you can read it. Before that, it means nothing.

And the failure with no error message at all: you get everything working and build for a week. On Friday you break something badly. Then you find there is no history to go back to, because Git was "something to set up later". There is no red text for this one. There is just lost work.

All four failures have the same pattern. Each one is cheap to prevent and costly to track down. That is the whole reason to do setup on purpose, in order, checking as you go.

5The Right Way

Correct approach — install in dependency order, and prove each step before the next

The order below matters. Maven needs a JDK to run, so the JDK comes first. Git comes before the project folder. That way, the very first file the folder ever holds is a .gitignore. Follow the steps from top to bottom.

5.1 Step one: install the JDK (Java 21 LTS)

Several companies publish their own build of Java 21. It is the same language in every one. They differ only in packaging and support. Any of these is fine. Eclipse Temurin is the common choice, and it needs no account:

  • Eclipse Temurin 21 (LTS) — adoptium.net
  • Microsoft Build of OpenJDK 21 — handy on Windows
  • Amazon Corretto 21, Azul Zulu 21 — also fine

Download the JDK (not the JRE) for Java 21, for your operating system. Run the installer. On Windows, the installer may offer a checkbox like "Set JAVA_HOME variable" or "Add to PATH". Tick it. That solves the PATH problem from section 3.4 for you.

Prove it works. Open a brand-new terminal window. (A window that was already open still has the old PATH.) Run both of these:

java -version
javac -version

Predicted output (your exact version number and wording will differ a little; that is fine):

openjdk version "21.0.9" 2026-10-20
OpenJDK Runtime Environment Temurin-21.0.9+7 (build 21.0.9+7)
OpenJDK 64-Bit Server VM Temurin-21.0.9+7 (build 21.0.9+7, mixed mode, sharing)

javac 21.0.9

What to check, most important first:

  1. Both commands answered at all. So both are on your PATH.
  2. Both say 21. If java says 21 and javac says something else, you have two JDKs fighting. See section 7.
  3. javac answered. So you have a JDK, not a JRE.

5.2 Step two: install Maven 3.9.16

Maven has no installer. It is just a folder of files plus a PATH entry. On Windows:

  1. Download apache-maven-3.9.16-bin.zip from maven.apache.org/download.cgi.
  2. Unzip it somewhere permanent, in a path with no spaces. For example: C:\tools\apache-maven-3.9.16. (Some older tools still get confused by spaces in folder names.)
  3. Add C:\tools\apache-maven-3.9.16\bin to your PATH. Press Start and type "environment variables". Open Edit the system environment variables → Environment Variables… → select Path → Edit → New. Paste the path, then click OK in all three windows.
  4. Close every terminal window and open a new one. A terminal reads PATH only when it starts. Windows that are already open will not see the change.

On macOS with Homebrew: brew install maven. On Debian or Ubuntu: sudo apt install maven. Then check which version it gave you.

Prove it works. In a new terminal:

mvn -version

Predicted output:

Apache Maven 3.9.16 (a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0)
Maven home: C:\tools\apache-maven-3.9.16
Java version: 21.0.9, vendor: Eclipse Adoptium, runtime: C:\Program Files\Eclipse Adoptium\jdk-21.0.9-hotspot
Default locale: en_GB, platform encoding: UTF-8
OS name: "windows 11", version: "10.0", arch: "amd64", family: "windows"

Look at the third line. mvn -version tells you which Java Maven found. That is the most useful thing on the screen. It is how you catch Maven using a different JDK from the one you expect. It must say 21.

5.3 Step three: install an IDE

Two good choices, both free:

IntelliJ IDEA Community EditionVisual Studio Code

If you have no preference, choose IntelliJ IDEA Community Edition. It will teach you things about Java by pointing them out as you type. There is no check command for this step. If it opens, it works.

5.4 Step four: install Git and create a GitHub account

Download Git from git-scm.com and install it. On Windows, the installer asks a long list of questions. The default answers are fine. Only one is worth a thought: the default editor. Pick one you know how to close, such as Notepad++ or VS Code. Avoid Vim for now.

Then create a free account at github.com. Create a new, completely empty repository:

  • Name it something like spring-boot-learning.
  • Public or private are both fine. Public is nice later, for the reason in the "In the real world" card above.
  • Do not tick "Add a README", "Add .gitignore" or "Choose a license". We want it truly empty. If the repository already has commits in it, the next step gets more awkward.

Prove it works, and tell Git who you are. Git puts this name and email on every commit, so set them once, now:

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Predicted output. The first command answers. The other two print nothing at all. That is Git's way of saying "done":

git version 2.51.0.windows.1

It takes time to get used to silence meaning success. Many terminal tools print nothing when they work. They only speak up when something is wrong.

All four tools at once. Run these four lines in one new terminal. You want four answers and no "not recognized". That means your machine is ready. This is the goal of the whole lesson.

java -version
javac -version
mvn -version
git --version

Compare each answer with the predictions above. If one differs in a way you did not expect, the machine is right and the lesson is wrong. Tell me exactly what you saw, and we will work out why.

6Applied to Our Project

This lesson teaches no Spring Boot feature. There is no annotation to write and no code to run. Twenty minutes ago, the tools to run it did not even exist. So there is no project code here. That is correct, not a shortcut. What we can do now is create the folder everything else will live in. And we put it under Git before it holds anything worth losing.

6.1 Create the folder and make the first file a .gitignore

The order here matters more than it seems. Git only tracks the files you tell it to. But the usual first command tells it to track everything. If an unwanted file is in the folder at that moment, it goes in. Git history is built to be permanent, so taking that file out later is hard. So the ignore list is written before the first git add, never after.

Create a folder called learning wherever you keep projects. Inside it, create a file named exactly .gitignore. It starts with a dot and has no extension. Put this in it:

# Local-only course control files - never commit these
CLAUDE.md
curriculum.md
progress-tracker.md

# Maven / Java build output - generated, never stored
target/
*.class

# IDEs - personal to your machine, not to the project
.idea/
*.iml
.vscode/

# Local Claude Code settings - machine-specific
.claude/

# Real secrets - never commit; application.yml + .env.example are the templates
**/application-local.yml
.env

Every line is there for a reason:

  • The three course files are your local control files. They belong to you, not to the project.
  • target/ and *.class are what Maven produces: compiled bytecode, made fresh from your source on every build. Storing these in Git makes the history huge and causes pointless clashes. A simple rule: if a build can make it again, do not store it.
  • IDE folders hold your personal window layout and preferences. Another developer's copy would clash with yours. Neither is part of the program.
  • application-local.yml and .env are where real passwords and API keys will live, from Lesson 39 onwards. This line goes in now, months early, so a secret can never land in the history by accident later. Git history lasts forever. A leaked key stays leaked, even if the next commit deletes it.

Add one more file next to it, called .gitattributes:

# Normalise line endings so the repo behaves identically on Windows and Linux
* text=auto eol=lf

Windows and Linux end a line of text differently. Windows uses two invisible characters; Linux uses one. If you ignore this, Git may say that every line of a file changed, even when you changed nothing. That is maddening. This one line fixes it for good.

6.2 Put it under version control

Now, and only now, from inside the learning folder:

# 1. Start tracking this folder. Creates the hidden .git directory that IS the history.
git init

# 2. Stage everything not excluded by .gitignore, ready for the first snapshot.
git add .

# 3. Take the snapshot, with a message explaining it.
git commit -m "chore: initial course setup"

# 4. Name the main line of development 'main' (the modern default).
git branch -M main

# 5. Record where the online copy lives. Use YOUR repository URL from GitHub.
git remote add origin https://github.com/your-username/your-repo.git

# 6. Send the commit up, and remember this destination for future pushes (-u).
git push -u origin main

6.3 What would happen, step by step

  1. git init creates a hidden .git folder. That folder is the repository. Delete it and you have plain files again, with no history.
  2. git add . goes through the folder and checks .gitignore. It gets every file that is not ignored ready for the snapshot. This is called "staging". You wrote the ignore list first, so your three local-only files are skipped. You never have to remember to leave them out.
  3. git commit saves the staged snapshot for good, and labels it with your message.
  4. git branch -M main renames your main line of work to main. That matches GitHub's default name.
  5. git remote add origin … just saves an address under the nickname origin. Nothing is sent yet.
  6. git push -u origin main uploads the commit. It also links your local main to the one on GitHub. After this, a plain git push is enough. The first time, a browser window or a login prompt may appear, so GitHub can check it is you.

Predicted output of the commit and the push:

$ git commit -m "chore: initial course setup"
[main (root-commit) a1b2c3d] chore: initial course setup
 2 files changed, 21 insertions(+)
 create mode 100644 .gitattributes
 create mode 100644 .gitignore

$ git push -u origin main
Enumerating objects: 4, done.
Counting objects: 100% (4/4), done.
Writing objects: 100% (4/4), 412 bytes | 412.00 KiB/s, done.
To https://github.com/your-username/your-repo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

Run it, then check two things. First, git status should report a clean tree:

git status

Predicted:

On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

Second, and this is the one that matters: refresh your repository page on GitHub. You should see .gitattributes and .gitignore. You should not see CLAUDE.md, curriculum.md or progress-tracker.md. If those three are on your disk but not on GitHub, the ignore list did its job.

Check yourself: why write .gitignore before git add . and not after?

Because git add . stages every file that is not ignored, and a commit is permanent. Say a secret or a local-only file is in the folder the first time you run git add .. It gets saved into the history. Deleting it in a later commit does not remove it from the earlier one. Anyone with the repository can still read it there. If you write the ignore list first, the unwanted files are never staged at all. It is much easier to keep something out than to get it back out.

7Gotchas and Common Mistakes

  • Changing PATH and leaving the terminal open. A terminal reads PATH once, when it starts. If you change PATH, the window you already had open still says mvn does not exist. The fix is to close it and open a new one. On Windows, signing out and back in sometimes helps too. People reinstall Maven three times because of this.
  • Two JDKs, and the wrong one in charge. The sign: java -version and mvn -version show different Java versions. Or javac shows a different version from java. The cause: an old JDK is still on the machine, and PATH finds it first. The fix: set JAVA_HOME to your Java 21 folder, and remove the old entry from PATH. Always trust the version line in mvn -version over what you think is installed.
  • Installing a JRE instead of a JDK. Download pages often push the JRE, because most visitors only want to run Java. Then java works and javac does not. The build error you get later talks about a compiler, not a download. Always check with javac -version, not just java -version.
  • Committing something that should have stayed local. This usually happens when you run git add . before writing .gitignore. It also happens if you force a file in with git add -f. Never use -f on the three course files. If a real secret does get committed, treat it as leaked. Change the key first. Worry about cleaning the history after that.
  • Spaces and non-English characters in folder paths. Some tools still get confused by a path with spaces or accented letters. Their error messages then point somewhere far from the real cause. Keep the paths to your tools and projects plain.
  • Thinking the IDE uses the same JDK as your terminal. IntelliJ can download and use its own JDK. So the IDE may compile fine while mvn in a terminal fails, because they are using different Javas. In this course, trust the terminal. That is where every command in these lessons is run.

8Tradeoffs and When Not to Use This

Maven versus Gradle. Gradle is the main other build tool. Its build files are shorter, and it is usually faster on big projects. That is because a Gradle build file is written in a programming language, not a fixed format. But that freedom has a cost. A Gradle build can turn into a program of its own, and someone then has to fix its bugs. Maven is strict, so every Maven project looks like every other one. That is dull, but it helps a lot when you are learning: a tutorial's project looks just like yours. Pick Gradle when a build is truly complex, or if you are used to it from Android work. For learning, Maven's predictability wins.

Installing by hand versus a version manager. We installed everything by hand, so you could see every piece. That is worth doing once. Tools such as SDKMAN! (macOS and Linux) or winget and Chocolatey (Windows) can do it for you. They are better once you need several Java versions side by side. So why not start with them? They hide exactly the PATH details that cause the errors in section 7. Then, when something breaks, you have no idea what happened.

Pinning versus always taking the newest. Pinning means you get the same results every time. The cost is that a pinned project slowly falls behind, and one day needs a planned upgrade. In this course, the predicted output must match your screen, so getting the same results matters far more. Real teams think the same way, with one addition: they pin, and they plan their upgrades instead of letting them happen by accident.

When this lesson does not apply. Some workplaces give you a ready-made development setup. Tools like Dev Containers and GitHub Codespaces do the same. In those cases, every tool arrives already installed, and this setup is done for you. That is a real option, and more and more common. It is the same idea behind Docker, which we meet properly in Lesson 120. Even then, knowing what is inside the box is what lets you fix it when something in the box is wrong.

9Key Takeaways

  • javac compiles Java into bytecode, not machine code. The JVM then runs that bytecode on whatever computer it is on. That is why one compiled program runs unchanged on Windows, macOS, Linux and inside a container.
  • The JDK contains the JRE, and the JRE contains the JVM. You need the full JDK, because only the JDK has the compiler. If you install a JRE by mistake, Java runs but nothing you write will build.
  • Real projects use libraries, and those libraries use other libraries. Maven fetches that whole chain for you, from a list you write in pom.xml. That is why one dependency line can give you a complete web server.
  • Git keeps a permanent history of every version of your work. On day one, its real value is courage. Last week's version is always one command away, so you can experiment freely instead of fearing every change.
  • You write .gitignore before the first git add on purpose. Commits are permanent. It is far easier to keep a secret out of the history than to remove it afterwards.

10Challenge

No code for this one. Think it through on paper, then check your answer.

A friend has just set up their machine. They send you this terminal session and say: "I think something's wrong, but I don't know what."

PS C:\Users\sam> java -version
openjdk version "17.0.11" 2024-04-16
OpenJDK Runtime Environment Temurin-17.0.11+9 (build 17.0.11+9)

PS C:\Users\sam> javac -version
javac 21.0.9

PS C:\Users\sam> mvn -version
Apache Maven 3.9.16
Maven home: C:\tools\apache-maven-3.9.16
Java version: 17.0.11, vendor: Eclipse Adoptium

PS C:\Users\sam> git --version
git version 2.51.0.windows.1
  1. All four commands answered. So is the machine ready? If not, exactly what is wrong?
  2. Which single line in that output is the most alarming, and why?
  3. Predict what happens when they build a Spring Boot 4 project pinned to Java 21, and write the error you would expect.
  4. What would you tell them to do, in order?
Click to reveal the answer

1. No, the machine is not ready. Every command answered, but that only proves all four tools are on the PATH. It says nothing about whether they agree with each other. Here, they do not. There are two JDKs installed. java is Java 17, but javac is Java 21. The runtime and the compiler come from different installs.

2. The most alarming line is Java version: 17.0.11 in the mvn -version output. That line decides everything. Maven is what will build this course's projects, and it says it is using Java 17, not 21. Sam might see javac 21.0.9 and think they are on Java 21. Maven's line tells the truth about what the build will really use. That is why section 5.2 called it the most useful line on the screen.

3. Predicted build error. The project asks for Java 21 output. But Maven is using the Java 17 JDK, which has never heard of version 21:

[INFO] --- maven-compiler-plugin:3.13.0:compile (default-compile) @ ecommerce ---
[ERROR] Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE

(Spring Boot 4 works with Java 17 or newer. So Boot is not the one refusing here. The compiler is being asked for a version newer than itself. If the project had been pinned to 17, this build would have worked. That is why this kind of mismatch is so easy to miss.)

4. What to tell them, in order:

  1. Find both JDKs. On Windows, look in C:\Program Files\Eclipse Adoptium\ and similar folders.
  2. Set JAVA_HOME to the Java 21 folder.
  3. Edit PATH. Remove the Java 17 bin entry, and make sure the Java 21 one is there. (If nothing else needs Java 17, think about uninstalling it.)
  4. Close every terminal and open a new one. If they skip this, nothing above seems to work, and they will think the fix failed.
  5. Run all four check commands again. Success means java, javac and the Java line of mvn -version all say 21.

The real lesson here: "the command answered" and "the setup is correct" are two different things. Checking means reading what came back, not just seeing that something came back.
