1The Problem

You have an empty folder. You want it to become a running web app. Let us be very exact about what stands in the way. A build tool exists to remove every problem we are about to meet.

1.1 Compiling one file is easy

Your Java source code is text. The machine cannot run text. Something has to turn EcommerceApplication.java into EcommerceApplication.class. That .class file holds bytecode: the compact instructions the JVM runs (Lesson 00). The compiler, javac, does this job, and you can run it yourself. Fine. One file, one command.

1.2 Then you need other people's code

Now your code says import org.springframework.boot.SpringApplication;. The compiler stops. It has never heard of that class. The class is not part of Java. It lives in a file called spring-boot-4.1.1.jar, on a computer somewhere on the internet.

So you must do this by hand:

  1. Go to a website and search for the JAR.
  2. Download it.
  3. Tell the compiler where it is.

And the compiler stops again. SpringApplication uses classes from four other JARs. Those use classes from eleven more. A full Spring Boot web app needs about forty separate JAR files. All of them must be there at once. And all of them must be versions that work together.

1.3 When the versions do not fit

That last part is where it goes from boring to truly dangerous. Here is an example.

  1. You download Spring Framework 7.0.9.
  2. Separately, you download a Tomcat 10.1 JAR from an old tutorial.
  3. Everything compiles. The app starts.
  4. Forty minutes into a demo, one request calls a method. Spring 7 expects Tomcat to have that method. Tomcat 10.1 does not.

The program does not fail at startup, where you would notice. It fails right then, with a NoSuchMethodError. That error means "Java tried to call a method, and the class it found does not have it". The error names a method you have never heard of, in a class you did not write. The list of method calls it prints (the stack trace, from Lesson 01) is fifty lines deep. Nothing in it tells you the real cause: two of your forty JARs were never built to work together.

Java developers have a name for this mess, and it is not a kind one: JAR hell.

1.4 And then a colleague copies your project

Say you solve it. You find forty JARs that really do work together. Now a colleague copies your project. Do they get the same forty? Only if you wrote the list down in a form a program can read. Then their machine can fetch exactly those. Otherwise the phrase from Lesson 01 is back: it works on my machine.

1.5 The real questions

So the problem is not "how do I compile Java?". The real questions are these:

  • Who keeps the list of what this project needs?
  • Who fetches it?
  • Who makes sure the pieces fit?
  • Who turns the result into one runnable thing?
  • And who does all that the same way, on every machine, every time?

The answer to all five is a build tool. Ours is Maven.

2Real World Analogy

You are cooking dinner for eight people tonight, and your kitchen is empty.

The hard way: invent the meal and write down every ingredient. Walk the supermarket aisles, guessing amounts. Hope the curry paste you grabbed is as hot as the recipe meant. If you get it wrong, you find out at 7pm, with your guests already there.

The easy way has three parts:

  1. You write a shopping list. It is not the food itself, just the names.
  2. Someone else does the shopping. They read your list, go to the shop, and bring everything back. If an item on your list is a meal kit, they bring the whole box, with everything inside it. You do not have to list each thing in the box.
  3. You buy those kits from a brand you trust. That brand has already tested that its sauce, spices and noodles go well together. You do not have to check that the chilli and the coconut milk get along. Someone already did that, and put their name on it.

3The Concept Explained

3.1 What a build tool is

Lesson 00 gave you a short meaning. A build tool is a program that turns your source code into a finished program you can run. It does it the same way every time, on every machine.

"Build" sounds vague. So here is exactly what it means for a Java project. A build tool must:

  1. Read a written list of the libraries the project needs.
  2. Download each one, plus everything they need.
  3. Compile every .java file into .class bytecode, with all those libraries visible to the compiler.
  4. Copy non-code files, such as settings, into the right place.
  5. Compile the test code too.
  6. Run every test, and stop the whole build if any test fails.
  7. Finally, bundle the result into one file you can hand to others.

You could do all of that by hand. People did, for years, with an older tool called Ant. In Ant, you wrote out each of those steps yourself, in XML.

Then came a simple idea that replaced it. Almost every Java project does these steps in the same order. So stop describing the steps. Start describing the project. Tell the tool the project's name and what it needs. The tool already knows what building means. That is Maven's whole idea.

It is the same convention over configuration idea that Spring Boot uses for setup (Lesson 01). That is no accident. Maven's success is what made Boot's approach feel natural.

3.2 Coordinates: how any library in the world is named

Before Maven can fetch anything, it needs a clear name for it, with no chance of a mix-up. Maven uses three values. Together, they are called the coordinates of an artifact. An artifact is just "a thing a build produces". In practice, it is almost always a JAR file.

CoordinateWhat it identifiesOur example
groupIdWho published it. Written as a web address, backwards.org.springframework.boot
artifactIdWhich of that publisher's things it is.spring-boot-starter-webmvc
versionWhich release of it.4.1.1

Why write the group as a web address backwards? The name part of a web address, like springframework.org, is called a domain. Only one organisation can own each domain. So the internet already solved the problem of "two organisations must never pick the same name". Reusing that answer costs nothing.

  • Spring owns springframework.org, so nobody else can claim org.springframework.
  • Amazon publishes under software.amazon.awssdk.
  • Your own company would use something like com.yourcompany.

Java uses the same habit for package names, for the same reason.

3.3 How coordinates become a web address

Those three values turn straight into a folder path on a web server. The coordinates org.springframework.boot : spring-boot-starter-webmvc : 4.1.1 become:

https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-starter-webmvc/4.1.1/
                              └─────── groupId ───────┘└──── artifactId ────┘└version┘

That is not a search. There is no lookup service and no index. Maven works out the address from the three values. It replaces every dot in the groupId with a slash, and adds the other two parts.

That is why one typo in a coordinate gives a blunt "could not resolve dependency" error. You do not get a helpful "did you mean…?". Maven asked for a web address that does not exist. A web server has nothing clever to say about that.

3.4 The repository, and why the second build is fast

A repository is a place where artifacts are stored. Two of them matter to you.

Maven Central is the public one. It is one free, huge store of open-source Java libraries. It is the first place Maven looks. To publish to it, you must fill in paperwork and prove you own the domain in your groupId. That is exactly why Maven can trust it by default.

Your local repository is a folder on your own machine:

  • On macOS and Linux it is ~/.m2/repository. The ~ sign is short for "my home folder".
  • On Windows it is C:\Users\YourName\.m2\repository.

Maven stores every JAR it ever downloads there, in a folder path made from its coordinates. Before it fetches anything from the internet, Maven checks here first.

This is why your very first Spring Boot build takes two or three minutes. It prints a long stream of "Downloading from central…" lines. Your second build takes eight seconds and prints almost nothing. Nothing got faster. The second build just found all forty JARs already in the cupboard. It also means you can build with no internet at all, as long as you built once before. That is handy the first time you try to work on a train.

Sometimes a download gets cut off. Then the local repository may hold a half-written file. Every later build fails on it, in a confusing way. The fix is simple and safe. Delete the broken folder inside ~/.m2/repository and build again. Maven downloads it again. Deleting the whole ~/.m2/repository folder is safe too. It only costs you one slow build. Nothing you cannot replace lives there.

3.5 Transitive dependencies: the thing that does the real work

A dependency is a library your project needs. A transitive dependency is a library that your dependency needs. Maven follows that chain all the way down, by itself. This is the feature that turns forty downloads by hand into two lines of text.

Let us follow it for real, using what is actually in the files. These are not made-up numbers. They are what spring-boot-starter-webmvc version 4.1.1 really lists.

The diagram names several libraries. You do not need to learn them now. Here is what each one does, in one line:

  • Logback and SLF4J write log lines, like the startup log you saw in Lesson 01.
  • snakeyaml reads YAML files. YAML is a settings-file format. It groups related settings by indenting them with spaces. Our application.yml is a YAML file.
  • Jackson turns Java objects into JSON and back.
  • tomcat-embed-core is Tomcat itself: the embedded web server.
  • spring-boot-autoconfigure holds core auto-configuration recipes (Lesson 01).

3.6 When two versions of one library clash

Now the obvious question, and it is a good one. Maven pulls in dozens of things by itself. What happens when two branches of that tree ask for different versions of the same library?

Say Spring MVC wants SLF4J 2.0.18, and some other library wants SLF4J 1.7.36. Both cannot be on the classpath (the list of code your program can use, from Lesson 01). The JVM will load exactly one org.slf4j.Logger class and ignore the other. If it loads the wrong one, methods go missing while the program runs.

Maven's built-in answer is a rule called nearest wins. Of the clashing versions, it uses the one that is fewest steps away from your pom.xml. That is predictable, which is good. But it is also random in a way. It picks by place in the tree, not by whether the result actually works. That is not good enough for a framework made of forty pieces that must work together. So the Spring team adds a better solution on top. That is the next section.

A command worth learning now and using forever: mvn dependency:tree prints your project's whole tree of dependencies, indented. It marks every version Maven replaced. When a library acts strangely, run this first. Try it after the build in section 5, and you will see the ≈40 JARs above with your own eyes.

3.7 The parent POM

pom.xml stands for "Project Object Model". A POM is Maven's description of one project: its name, what it needs, and how to build it.

In the shopping example, the parent POM is the brand that promises its ingredients go together. Here is what it actually is.

Our pom.xml names a <parent>. The parent is just another pom.xml, published on Maven Central. Our file inherits from it. That works like a Java class that extends a superclass:

  • Anything the parent says, we get for free.
  • Anything we say ourselves replaces it.

Our parent is spring-boot-starter-parent. It has a parent of its own, too: spring-boot-dependencies.

3.8 Dependency management and the BOM

That grandparent file is the interesting one. It has a section called <dependencyManagement>. It differs from a normal <dependencies> section. That difference is the most useful thing to understand about Maven:

  • <dependencies> means "fetch this." Maven downloads the library and puts it on the classpath.
  • <dependencyManagement> means "if anyone asks for this, use this version." Maven downloads nothing. It is a price list, not an order.

spring-boot-dependencies is a price list for about four hundred libraries. The Spring team built and tested every one of them together, as a set. A file whose only job is to set versions for a matching set of libraries has a name. It is a BOM, short for Bill of Materials. The term comes from factories. There, a bill of materials lists every part that goes into a product.

Here are real lines from the 4.1.1 BOM, checked on Maven Central on 2026-09-30:

<!-- inside spring-boot-dependencies 4.1.1 -->
<spring-framework.version>7.0.9</spring-framework.version>
<tomcat.version>11.0.24</tomcat.version>
<jackson-bom.version>3.1.5</jackson-bom.version>
<logback.version>1.5.38</logback.version>
<junit-jupiter.version>6.0.3</junit-jupiter.version>
<assertj.version>3.27.7</assertj.version>
<mockito.version>5.23.0</mockito.version>
<h2.version>2.4.240</h2.version>
<postgresql.version>42.7.13</postgresql.version>
<hibernate.version>7.4.5.Final</hibernate.version>

This is why our pom.xml has no version numbers in it. We write two dependencies and no versions. The result is forty JARs that a team of people spent months testing against each other. Change our one <version>4.1.1</version> on the parent, and all forty move together. That is the whole trick. It cures the JAR hell from section 1.

3.9 What else the parent sets up

A POM can hold properties: named values, like java.version, that other parts of the build read. spring-boot-starter-parent adds a few things on top of the BOM. I checked these in the published file:

  • It sets the property java.version to 17 by default. It makes maven.compiler.release follow it. So one property in our file decides which Java version the compiler produces.
  • It makes source files and build output use UTF-8. UTF-8 is the standard way to store letters as bytes, so accented letters like "é" survive.
  • It pins the version of every build plugin (the add-ons that do Maven's jobs, from Lesson 00).
  • It sets resource.delimiter to @. This detail is a famous trap. We meet it again in section 7.
Check yourself: our pom.xml lists two dependencies, yet about forty JARs end up on the classpath. Where did the other thirty-eight come from, and who chose their versions?

They came from transitive resolution. Each of our two dependencies lists its own dependencies. Those list theirs. Maven walks the whole tree until nothing is left to fetch.

The BOM inside spring-boot-dependencies chose their versions, and our parent inherits from it. If nobody had decided, Maven's own "nearest wins" rule would apply. But the BOM's <dependencyManagement> section overrides that rule for every library Spring looks after, which is almost all of them. So: Maven fetched them, but the Spring team picked them.

3.10 What a starter actually is

Lesson 01 defined a starter as "a ready-made group of libraries for one job". Now that you know what a POM is, we can be exact. The truth is funnier than that definition suggests.

A starter is an empty JAR. Really. Download spring-boot-starter-webmvc-4.1.1.jar and open it. There are no classes inside. All its value is in the POM file published next to it. That file lists five dependencies and nothing else. A starter is a shopping list pretending to be a product.

This is on purpose. A starter just states what you want: "I am building a Spring MVC web app". It is kept completely separate from the code that does the work. Then Boot's auto-configuration reads the classpath that the starter filled. It draws conclusions from it, just as Lesson 01's simulation showed. The starter provides the clues. Auto-configuration is the detective.

Here is what is really in our two starters, taken from their published POMs:

spring-boot-starter-webmvc  (no classes of its own)
 ├── spring-boot-starter              core Boot: autoconfigure, logging, snakeyaml, jakarta.annotation
 ├── spring-boot-starter-jackson      Jackson 3 — Java objects to and from JSON
 ├── spring-boot-starter-tomcat       the embedded server, plus spring-boot-tomcat
 ├── spring-boot-http-converter       reading and writing HTTP message bodies
 └── spring-boot-webmvc               Spring MVC itself, plus its auto-configuration

spring-boot-starter-webmvc-test  (no classes of its own, scope: test)
 ├── spring-boot-starter-test         JUnit 5 · AssertJ · Mockito · Hamcrest · JSONPath · spring-test
 ├── spring-boot-starter-jackson-test JSON assertions
 ├── spring-boot-starter-webmvc       the web starter again, so tests see the same classes
 ├── spring-boot-webmvc-test          MockMvc — call a controller without a real server
 └── spring-boot-resttestclient       RestTestClient — Boot 4's HTTP test client

The second starter has scope: test. A dependency's scope tells Maven when it is needed. test means "only for running tests". So none of it goes into the finished app.

The test starter names several testing tools. Here is what each one does:

  • JUnit 5 finds your test methods and runs them.
  • AssertJ and Hamcrest let you write checks, like "this value must equal 5". A check like that is called an assertion.
  • Mockito makes fake objects for tests, so you can test one class on its own.
  • JSONPath picks single values out of a JSON response in a test.
  • spring-test is Spring's own support for tests.
  • MockMvc sends pretend requests to your web code without a real server.
  • RestTestClient is new in Boot 4. It sends HTTP requests to your app from a test.

You will use all of these in later lessons. For now, just know they arrive with one line.

3.11 Starter names that changed in Spring Boot 4

The starter rename you will trip over within a week. Every Spring Boot tutorial, book, video and Stack Overflow answer from before 2026 starts a web project with this:

spring-boot-starter-web spring-boot-starter-webmvc

What 3.x did: one starter named spring-boot-starter-web. It brought in one giant auto-configuration JAR. That JAR grew from 182 KiB in 2014 to about 2 MiB by Boot 3.5. It held the setup recipes for every technology Spring supports. Every app got all of it, whether it used that technology or not.

What 4.x does: the Spring team split that giant JAR into small spring-boot-<technology> modules. They renamed the starters to match the module each one brings in. "web" was unclear, because Spring has two completely different ways to build web apps. So the servlet way became webmvc. That matches webflux, the other (reactive) way, which was already named after its technology.

Two more renames happened at the same time:

  • spring-boot-starter-web-services became spring-boot-starter-webservices.
  • The three OAuth2 starters got a security- prefix. (OAuth2 is a standard way to log in through another service, like "Sign in with Google".) For example, spring-boot-starter-oauth2-client became spring-boot-starter-security-oauth2-client.

Why it changed: three reasons. A smaller classpath. Fewer useless classes for Boot's rule engine to check at startup. And a name that tells you what you get. There is a fourth, quieter benefit. With one module per technology, your list of dependencies honestly shows what your app uses. That matters for security checks, and for native images later in Phase 3.

What this means for you: type spring-boot-starter-webmvc in our project. When you read an older tutorial, translate -web to -webmvc on sight. The old name still works today. It is deprecated (marked as old, and due to be removed), not deleted. So a copied tutorial will seem to work. That is exactly why it is worth knowing about now.

One real difference in behaviour: the new starter brings in spring-boot-starter-tomcat by itself. Older tutorials add a separate Tomcat dependency. You no longer need it.

The test starter changed too. This one catches people out, because the old name still works.

spring-boot-starter-test spring-boot-starter-webmvc-test

What 3.x did: one test starter for everything. spring-boot-starter-test brought JUnit, Mockito, AssertJ and all the web testing helpers, whether your project had a web part or not.

What 4.x does: the same split into modules, applied to testing. spring-boot-starter-test still exists. It still holds the general testing tools that work for any technology: JUnit Jupiter, AssertJ, Mockito, Hamcrest, JSONPath and spring-test. The web testing helpers moved into spring-boot-starter-webmvc-test. That starter contains spring-boot-starter-test. So asking for the webmvc one gets you both.

Why it changed: the same reason as the main starters. You should only carry testing tools for the technologies you actually use. It also gives a natural home to Boot 4's new RestTestClient.

What this means for you: in a web project, use spring-boot-starter-webmvc-test. That is what Spring Initializr now creates. Say you copy spring-boot-starter-test from a 3.x tutorial. Your project still compiles. But a test that uses MockMvc then fails with "cannot find symbol". That is the compiler saying "I do not know this name". The cause is not obvious.

There is a related Boot 4 change. You meet it properly in the testing chapter. @SpringBootTest is the annotation that starts the whole app inside a test (you see it in section 6). In 3.x it gave you MockMvc and TestRestTemplate (an older tool for sending requests in tests) automatically. In 4.x it no longer does.

The emergency exit: good to know about, but do not use it.

spring-boot-starter-classic

What it is: a starter that brings in all of Boot's modules. So every auto-configuration class is there, just like in the old single JAR before 4.0. (It leaves out their own dependencies.) The official guide for moving up to Boot 4 calls it a bridge. Here is how the bridge works:

  1. You swap spring-boot-starter for spring-boot-starter-classic, and spring-boot-starter-test for spring-boot-starter-test-classic.
  2. Your existing 3.x app now compiles and runs on Boot 4 quickly.
  3. After that, you move to the proper module-by-module starters.

Why a new project must not use it: it exists only to make an upgrade less painful. On a fresh project, it brings back the exact problem the split was meant to solve. You get a bloated classpath, full of auto-configurations you will never use. The official advice is clearly to move away from it. We are starting fresh, so we start with modules.

3.12 The folder layout, and why you cannot change it

You never told Maven where your source code is. It found it anyway. That is because the folder layout is a convention. Maven assumes it, and so does nearly every other Java tool today.

Here is each folder, and what breaks if you get it wrong.

src/main/java holds the Java source for the real app. Maven compiles everything in here. The folders inside must exactly match the package lines. package com.ecommerce; means the file must sit in src/main/java/com/ecommerce/. Put the file one folder off, and the compiler rejects it before it even reads the code.

src/main/resources holds files that are not code but must travel with the app. Today that is application.yml. Later it will include SQL scripts (SQL is the language for talking to databases), message files and page templates. Maven copies everything here, with the same folder layout, to the top level of the built JAR. That is exactly why Boot finds application.yml without you telling it where. When the app runs, the file sits at the top level of the JAR, which is where Boot looks.

src/test/java holds the test source. Maven compiles it completely separately. Tests can use the app's classes, but the app can never see the tests. Maven enforces this rule; it is not just a good habit. It makes sure your test libraries can never end up in the real app by accident. (src/test/resources exists for the same reason. It holds settings used only by tests. We do not need it yet.)

target/ holds everything the build produces: compiled .class files, the JAR, and test reports. Maven creates it. You never edit anything inside it. It is listed in .gitignore and must stay there.

You can delete the whole target/ folder whenever you like. That is exactly what mvn clean does. "Have you tried mvn clean?" is Java's version of "turn it off and on again". It works surprisingly often, because it forces Maven to rebuild every old .class file.

3.13 The build lifecycle: phases always run in order

When you type mvn package, you do not name a single task. You name a phase: one step in a fixed list of steps. Maven runs that phase and every phase before it.

This one fact explains most of the Maven behaviour that confuses newcomers. So let us be concrete. Here are the standard phases for a JAR project, in order:

#PhaseWhat happens
1validateCheck that the POM is written correctly and the project layout makes sense.
2compileCopy src/main/resources into target/classes. Then compile src/main/java into the same place.
3testCompile src/test/java, then run every test. Any failure stops the build here.
4packageZip target/classes into target/ecommerce-0.0.1-SNAPSHOT.jar.
5verifyRun any larger checks that test several parts together.
6installCopy the JAR into your local repository, so other projects on this machine can use it.
7deployUpload it to a shared online repository. A build server usually does this, not a person. (A build server is a computer that builds and tests code automatically each time someone pushes.)

So mvn package also compiles and runs your tests. You never have to ask for those separately. And mvn install does everything package does, plus more.

This "everything before it" rule also explains the most common Maven surprise of all: "I asked it to package, and it said BUILD FAILURE because of a test." Yes. That is on purpose. A build that packages code known to be broken would be worse than useless.

3.14 clean, goals, and the fat JAR

clean is the odd one out. It belongs to a separate list of steps. Its only job is to delete target/. That is why you write mvn clean package: two separate lists, in that order. package alone does not clean first.

mvn spring-boot:run looks different because it is different. Anything with a colon in it is a goal. A goal is one action from one plugin, run directly instead of as part of a phase. Read it as plugin : goal: the spring-boot plugin, and its run goal. It compiles what it needs and starts the app straight from target/classes. It does not build a JAR at all. That is why it is the fast command while you develop.

One more word before the simulation. A normal JAR holds only your own classes. Spring Boot's plugin turns it into a fat JAR: one JAR that holds your classes and every library they need. That is the "one runnable file" from Lesson 01. Maven makes it in a step called repackage, right after package. Section 3.16 shows how it works inside.

Pick a command. Watch which phases actually run, in order, and what appears in target/. Notice this: you only ever name one phase, and you always get every phase before it.

Pick a command, then press “Run it”.

This is a model of the lifecycle, not the real thing. It has five commands and seven phases, not Maven's full set. Your machine has the final say. Run the real commands from phase-1-monolith/ecommerce/ and compare. To see which plugin really runs in each phase, run mvn help:describe -Dcmd=package.

Check yourself: you run mvn package and it prints BUILD FAILURE with a failing test. Is there a JAR in target/?

No. test comes before package, and a failing test stops the build right there. The build never reaches package, so no JAR is made.

But an older JAR from an earlier successful build may still be there. It is untouched, and now it is misleading, because it does not have your latest code. That is one quiet reason to always type mvn clean package. Then a failed build leaves you with no JAR at all. You cannot run an old one by accident and be confused by it.

3.15 Maven versus Gradle: the honest comparison

Maven is not the only Java build tool. Gradle is the other one you will meet. Spring Initializr picks Gradle by default, so you should know why we do not use it.

MavenGradle
Build filepom.xml: XML that only describes the projectbuild.gradle(.kts): real code, in Groovy or Kotlin (two other languages that run on the JVM)
LengthWordy. A dependency takes five lines.Short. A dependency takes one line.
FlexibilityLimited on purpose. You describe the project, not the stepsAlmost unlimited. You can write any logic you like
Speed on big projectsSlower. It does not reuse earlier work by defaultFaster. It rebuilds only what changed, reuses earlier work, and keeps a helper program running in the background
PredictabilityVery high. Every Maven project looks the same.Lower. Every Gradle project can look different.
Learning curveGentle. Learn it once, read any project.Steeper. A custom build can be a small program.

Both are excellent, and both are used everywhere. Neither is out of date. We use Maven for one teaching reason: its strictness helps while you learn.

  • A Maven build cannot hold clever custom logic. So no hidden step ever does something surprising.
  • The layout you learn here is the layout of nearly every Maven project you will ever open.
  • Gradle lets each project be different. That is exactly what you do not want while you are still learning what is normal.

Learn Maven first. When you meet Gradle later, you will understand what its shortcuts are for.

3.18 From a typed command to the first HTTP response

This is where it all comes together. Here is the whole chain, with nothing skipped.

Here are the six stages, step by step, with the details that matter.

Stage 1. You type java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. The -jar part is a flag: an extra instruction added to a command. It tells the JVM: "this file is a program; look inside it to find where to start".

Stage 2. The JVM opens the JAR and reads META-INF/MANIFEST.MF. This is a small text file that every JAR has. It is called the manifest, like a ship's list of cargo. The JVM looks for a line that says Main-Class:. That line names the class whose main method it should call. Without it, you get "no main manifest attribute", and nothing happens.

Stage 3. That line does not name your class. It names org.springframework.boot.loader.launch.JarLauncher. Spring Boot's Maven plugin put it there during the repackage step. Why? Because of a real limit in Java. Follow it step by step:

  1. A class loader is the part of Java that finds and loads classes while a program runs.
  2. The standard class loader can read classes from a JAR.
  3. But it cannot read classes from a JAR that sits inside another JAR.
  4. Our fat JAR holds forty JARs inside it.
  5. So Boot brings its own launcher, with its own class loader that can read them.
  6. Your real main class is written in the manifest separately, on a line called Start-Class:.
  7. Once its class loader is ready, the launcher reads that line and calls your class.

This is what makes "one runnable file" possible at all. It is also why the packaging step is called repackaging. It rewrites an ordinary JAR into this special layout.

Stage 4. SpringApplication.run(EcommerceApplication.class, args) runs. It sees from the classpath that this is a servlet web app. It creates the application context, Spring's container for your beans (Lesson 01). It checks every auto-configuration rule against the classpath, just as Lesson 01's simulation showed. Then it creates the objects those rules call for.

Stage 5. The web auto-configuration matched, so Tomcat starts. It runs inside this same program, as a library, and listens on port 8080. Then SpringApplication.run returns. But the app stays alive. Tomcat started a thread of its own. (A thread is a separate line of work inside the program.) That thread keeps the Java program running. (An earlier version of this lesson said run never returns. That was wrong. Lesson 03, section 3.15 explains what really happens.)

Stage 6. A request arrives. Tomcat accepts the connection. It hands the request to Spring's front door, the DispatcherServlet (Spring's main servlet, from Lesson 01). The DispatcherServlet looks for code that handles that address. We have written none, so there is no match. Boot's default error handling then sends back a 404 Not Found.

3.19 Why a 404 counts as success

That 404 is the goal of this lesson. It is a success, not a letdown. It proves that every link in the chain worked:

  • A network connection was opened and accepted.
  • Tomcat read an HTTP request.
  • Spring's servlet was asked what to do, and it made a decision.
  • A correct HTTP response went back.

The only thing missing is an endpoint. That is Chapter 4's job, not today's.

Three things from this section come up all the time in real work.

The fat JAR is why modern Java runs so well in containers (the sealed boxes from Lesson 00). The Docker setup file for a Spring Boot service is often four lines long. There is no server to install: you copy one file and run it.

The BOM is how real teams stay sane. Picture a company with thirty microservices (small separate programs that work together). It publishes its own parent POM, so every service uses the same tested versions. Then upgrading all of them is a one-number change.

And "can you explain what happens between java -jar and the first response?" is a common interview question. It shows the difference between people who only followed tutorials and people who understand how the pieces connect.

4The Wrong Way

Wrong approach

4.1 Building the project by hand

Let us do exactly what section 1 described: put the project together by hand. This is not a made-up bad example. It really is how people did it. Seeing it fail makes the cure easy to understand.

# Create a folder, write the class, download some jars, compile.
mkdir ecommerce && cd ecommerce
mkdir -p src lib
# ... write src/EcommerceApplication.java ...

# Hunt down jars by hand. The versions are picked by guesswork and
# whatever a blog post from 2023 happened to mention.
curl -O https://repo1.maven.org/maven2/.../spring-boot-4.1.1.jar
curl -O https://repo1.maven.org/maven2/.../spring-core-6.1.2.jar        <-- wrong major version
curl -O https://repo1.maven.org/maven2/.../tomcat-embed-core-10.1.19.jar <-- also wrong
# ...and roughly thirty-seven more...

# Compile, listing every jar by hand on the classpath.
javac -cp "lib/*" -d out src/EcommerceApplication.java

# Run it, listing them again.
java -cp "out:lib/*" EcommerceApplication

Two things in that code need a word. mkdir makes a new folder. -cp is short for "classpath": it tells javac and java where the JARs are.

4.2 What goes wrong

Four separate things go wrong. Each is worse than the one before.

  1. The boredom. You must find forty web addresses by hand, with no list telling you which forty.
  2. No record. Nothing writes down what you downloaded. A colleague cannot rebuild your lib/ folder. Neither can you, in six months.
  3. The classpath, typed twice. You type it once to compile and once to run. Forget one JAR, and the program crashes while it runs.
  4. Nothing checks that these versions belong together. This is the one that really hurts. Spring Boot 4.1.1 is built for Spring Framework 7 and Tomcat 11. We grabbed Spring 6 and Tomcat 10. Nothing complains. It compiles.

Here is what it looks like when the problem finally shows up. Notice when it shows up:

# Compilation: no complaints at all.
$ javac -cp "lib/*" -d out src/EcommerceApplication.java
$ (silence — it worked)

# Startup: still fine for a second and a half...
$ java -cp "out:lib/*" EcommerceApplication

  :: Spring Boot ::                (v4.1.1)

INFO  --- Starting EcommerceApplication using Java 21.0.9
Exception in thread "main" java.lang.NoSuchMethodError:
  'void org.springframework.core.ResolvableType.<init>(java.lang.Class)'
    at org.springframework.boot.SpringApplication.createApplicationContext(SpringApplication.java:451)
    at org.springframework.boot.SpringApplication.run(SpringApplication.java:312)
    at EcommerceApplication.main(EcommerceApplication.java:9)

Read that error the way a beginner would. It names a method you never typed. The method sits in a class you have never heard of. That class comes from a library you did not knowingly download. (The odd name <init> is how Java writes a constructor inside an error.) Nowhere does it mention the real cause: spring-core-6.1.2.jar and spring-boot-4.1.1.jar were never meant to be used together.

NoSuchMethodError is different from the compiler's "cannot find symbol". It always means the same thing: the class was there when you compiled, and a different version of it is there now. That is JAR hell. No amount of reading your own code will fix it.

And this is the best case. This one crashed at startup, where you notice. The really nasty version of this bug hides in a part of the code nobody uses, until a customer does.

Check yourself: the compiler was happy, but the program crashed. How is that possible?

Java checks method calls twice, against two different things.

  • At compile time, javac checks your code against the JARs on the classpath at that moment. It writes the call down as a note: "call a method with this name and these parameters, on this class".
  • At run time, the JVM looks that note up against the class on the classpath now.

If those two classpaths hold different versions of the same class, compiling works and the lookup fails. You get NoSuchMethodError, NoSuchFieldError or NoClassDefFoundError. A build tool makes the compile classpath and the run classpath from the same written list. That is not just handy. It removes a whole kind of bug.

4.3 The modern wrong way: copying from a tutorial

There is a second, much more modern wrong way. You are far more likely to hit this one: copying a dependency from a tutorial.

<!-- Copied from a 2024 blog post into a Spring Boot 4 project -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>   <!-- the 3.x name -->
    <version>3.2.0</version>                          <!-- and a hardcoded version! -->
</dependency>

Two mistakes in five lines:

  • The artifactId is the old, deprecated name. It still works, so nothing warns you. But now your project quietly differs from every other file in it.
  • The <version> is much worse. It overrides the BOM. You have just pulled Spring Framework 6 into a Spring Boot 4 app. That brings back the exact crash above, from inside a POM that looks perfectly fine.

If you remember one rule from this whole lesson, make it this one: never write a <version> on a Spring dependency. The parent has already decided, and it decided better than the blog post did.

5The Right Way

Correct approach

5.1 The POM

Two dependencies, no versions, and a folder layout that every Java tool already understands. Here is the POM, with every part explained. The full file, with a comment on every line, is saved to disk and listed in section 6.

<!-- The parent: inherit ~400 tested library versions and sane defaults. -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>   <!-- the one version number in the project -->
    <relativePath/>    <!-- empty = fetch it, do not look in the folder above -->
</parent>

<!-- Our own coordinates. -->
<groupId>com.ecommerce</groupId>
<artifactId>ecommerce</artifactId>
<version>0.0.1-SNAPSHOT</version>
<packaging>jar</packaging>

<!-- Override the parent's java.version (17) with our pinned 21. -->
<properties>
    <java.version>21</java.version>
</properties>

<dependencies>
    <!-- Makes this a web app. NOTE THE NAME: -webmvc, not -web. -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>

    <!-- Test tooling. scope=test keeps it out of the shipped jar. -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<build><plugins>
    <!-- Repackages the plain jar into an executable fat jar,
         and provides the spring-boot:run goal. -->
    <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
</plugins></build>

The version 0.0.1-SNAPSHOT means "an early version that is still being worked on". Every new project starts like this.

5.2 The main class

And the main class. Only four of its lines really do anything:

import org.springframework.boot.autoconfigure.SpringBootApplication;

5.3 Step by step: what happens when you build and run

  1. Maven reads pom.xml and finds the <parent>. It fetches spring-boot-starter-parent:4.1.1 from Maven Central. Then it fetches its parent, spring-boot-dependencies:4.1.1. (If they are already in ~/.m2, it uses those copies.)
  2. From those parents, Maven now knows the version of every library Spring looks after. It also knows that maven.compiler.release follows ${java.version}, which our <properties> block set to 21.
  3. It reads our two dependencies and looks up their versions in the inherited list (4.1.1 for both). It fetches their POMs. Then it follows every transitive dependency to the end of the chain. That is about forty JARs. It downloads them once and keeps them in ~/.m2/repository for good.
  4. Phase compile: Maven copies application.yml into target/classes/. Then it compiles EcommerceApplication.java to target/classes/com/ecommerce/EcommerceApplication.class, for Java 21. All forty JARs are on the classpath while it compiles.
  5. Phase test: Maven compiles EcommerceApplicationTests.java into target/test-classes/. Then the Surefire plugin, Maven's test runner, runs it. @SpringBootTest starts the whole app in memory. If that works, the test passes.
  6. Phase package: the JAR plugin zips target/classes into ecommerce-0.0.1-SNAPSHOT.jar. This JAR holds only our one class and one YAML file. It is a few kilobytes, and you cannot run it.
  7. Then the spring-boot-maven-plugin's repackage goal rewrites it into a fat JAR:
    • Our classes move to BOOT-INF/classes/.
    • The forty dependency JARs go into BOOT-INF/lib/.
    • The launcher classes are added.
    • The manifest gets two lines: Main-Class: …JarLauncher and Start-Class: com.ecommerce.EcommerceApplication.
    • The original small JAR is kept next to it, as .jar.original.
    The result is about 20 MB and needs nothing else to run.
  8. java -jar then goes through the six stages from section 3.18. It ends with Tomcat listening on port 8080.

6.2 The test

package com.ecommerce;

import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest   // start the WHOLE application before running anything here
class EcommerceApplicationTests {

    @Test
    void contextLoads() {
        // Deliberately empty. A test fails by throwing — and the throwing,
        // if it happens, happens during startup, before this line is reached.
        // So the assertion is: "the application can start at all."
    }
}

Here is what each part does:

  • @SpringBootTest tells the test tools: "before any test in this class runs, start the whole Spring app".
  • @Test marks contextLoads() as a test method. JUnit finds every method marked this way and runs it.
  • The method body is empty on purpose. A test fails when something throws an exception. Here, any exception happens during startup, before the method even runs.

It looks like it tests nothing, but it tests a lot. Each of these makes startup throw an error, and so makes this test fail:

  • a missing dependency;
  • a broken application.yml;
  • an object Spring cannot create;
  • two objects Spring cannot tell apart.

It is the cheapest safety check in the project. From now on, mvn test is the one command that answers "did I just break the app?"

  7. Tomcat sends the response back over the connection, and the browser shows it.

7Gotchas and Common Mistakes

  • Writing a <version> on a Spring dependency. Every tutorial shows versions, because a tutorial snippet has to work on its own, without a parent POM. If you copy one into our project, you override the BOM for that library. That breaks the promise that all forty JARs were tested together. The failure comes later, as a NoSuchMethodError that says nothing about versions. Avoid it by: never typing <version> under <dependencies> for anything Spring looks after. If you really must change one, change the BOM's property in <properties> instead (for example <h2.version>). Then the change is visible in one place.

  • A package name that does not match the folder path. Say you move a file in the file explorer but do not update its package line, or the other way round. The compiler gives an odd-sounding error. It may say "class X is public, should be declared in a file named X.java", or just refuse to find the class. People make this mistake because in most languages, a file's location and its package are unrelated. In Java, they are the same fact, written twice. Avoid it by: moving files with the IDE's refactor command. "Refactor" here means a safe, automatic change that updates every place at once, so it fixes both.

  • Expecting mvn package to skip the tests. Phases include everything before them. So package runs test first, and one failure stops everything. People then add -DskipTests to "just get a JAR". That works, but it is almost always the wrong move. You now have a JAR with no proof that it works. Avoid it by: fixing the test. Keep -DskipTests for the rare case where you need a build of broken code to investigate a problem. Never use it for anything you would ship.

  • Tabs in application.yml. YAML does not allow tab characters for indenting. Full stop. If your editor inserts tabs, a two-line settings file becomes a startup crash. And the error message talks about "scanner exceptions" and character positions. It does not say "you used a tab". Avoid it by: setting your editor to insert spaces for this kind of file. VS Code and IntelliJ both do this by themselves for .yml files. Check, in case you ever changed that setting.

  • The @ trap in application.yml. The Spring Boot parent sets resource.delimiter to @. It also turns on "resource filtering" for application*.yml. That means Maven reads the file during the build. Anything shaped like @name@ gets replaced with a Maven property. So say you write an email address, or a log pattern with an @…@ pair in it. Maven will either turn it into nonsense or fail the build. Avoid it by: knowing it exists. It is really useful on purpose: @project.version@ writes the build version into your settings. It is only baffling if you meet it by accident.

  • Committing target/. Everything in it is generated, and it holds a 20 MB JAR. Committing it makes the repository bigger forever, because deleting the file later does not erase it from Git history. Avoid it by: keeping the target/ line that is already in our .gitignore. Run git status before your first commit. If anything under target/ is listed, stop and fix the ignore file before you commit.

8Tradeoffs and When Not to Use This

8.1 The parent POM costs you some control

Inheriting four hundred version choices is wonderful, until you need a library at a version the BOM does not pin. Say a security fix came out this morning. You can override the version. But then you knowingly step outside the tested set. And the next Boot upgrade may quietly undo your change.

Maven also has a limit: a project can have only one parent. So a company with its own company-wide parent POM cannot also inherit from Spring's. The usual answer works like this:

  1. The company keeps its own parent.
  2. Inside <dependencyManagement>, it imports spring-boot-dependencies as a BOM, instead of inheriting from it.
  3. It still gets Spring's tested versions, and the parent slot stays free.

The cost: you lose the parent's plugin setup, and must write the spring-boot-maven-plugin version yourself. That is the right choice in a large company, and the wrong one for us.

8.2 The fat JAR costs you size and rebuild time

Twenty megabytes for a few kilobytes of your own code is an odd ratio. And every rebuild rewrites all twenty.

For a container this is wasteful. A container image (the saved template a container starts from) is built in layers, stacked like sheets of paper. When one layer changes, it must be rebuilt and sent again. So a one-line code change makes a whole new 20 MB layer.

Spring Boot's answer is layered JARs. They put the libraries and your own code in separate layers. Then only the small layer that changes often is rebuilt. That is a Phase 3 topic. For now, it is enough to know the tradeoff exists.

8.3 Maven's strictness costs you flexibility

Say your build needs to generate code, call an outside tool, or do something truly unusual. Maven makes you write or find a plugin. Gradle would let you write four lines of Kotlin. For a standard Spring Boot service, this never comes up. For a build with real custom logic, Gradle is the better tool, and choosing it there is perfectly fine.

8.4 When you would not build it this way at all

Here are three honest cases:

  • You must deploy into a server your company already runs, and will not change. Then you need war packaging. Boot still supports it.
  • You are writing a library for other projects to use, not an app. Then you want a plain JAR. No repackaging, no embedded server, and no starter parent forcing versions on the people who use it.
  • Your program must start in milliseconds, like a cloud function or a command-line tool. The JVM needs a moment to warm up, and that may rule out this whole approach. Compiling to a native image with a tool called GraalVM solves that. That is also in Phase 3.

For a web service that runs for a long time, this setup is the right default. That is exactly what our E-Commerce platform is. It will stay right for the rest of Phase 1.

9Coding Challenge

A colleague joins the project, opens pom.xml, and "improves" it. Here is their version. Think it through on paper before you run anything.

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
</parent>

<groupId>com.ecommerce</groupId>
<artifactId>ecommerce</artifactId>
<version>0.0.1-SNAPSHOT</version>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <version>3.2.0</version>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-tomcat</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
    </dependency>
</dependencies>

<build><plugins></plugins></build>

Answer these five, in order:

  1. Find every mistake. There are five distinct ones.
  2. Which of them stop the build straight away, and which wait to cause trouble later?
  3. This project is meant to use Java 21. Which Java version will it really compile for, and why?
  4. They ran mvn clean package, and it printed BUILD SUCCESS. Then they ran java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. What happens, exactly?
  5. Rewrite the file correctly.
Click to reveal the answer

1. The five mistakes.

  1. spring-boot-starter-web: the deprecated 3.x name. It still works, so nothing warns you. But now the project does not match the rest of the course, or the module-by-module layout Boot 4 expects.
  2. <version>3.2.0</version> on that dependency. This is the worst one. It overrides the BOM. It pulls the whole Spring Boot 3.2 tree of dependencies, including Spring Framework 6, into an app whose parent is 4.1.1. Now two versions of Spring that do not work together sit on one classpath.
  3. The separate spring-boot-starter-tomcat dependency. Not needed. In Boot 4, the webmvc starter already brings in Tomcat. On its own it would be harmless, but it is a sign of copying from an old tutorial. Here it makes things worse: it adds a 4.1.1 Tomcat next to the 3.2 libraries.
  4. spring-boot-starter-webmvc-test has no <scope>test</scope>. Without it, the scope defaults to compile, which means "needed by the real app". So JUnit, Mockito and AssertJ become part of the real app, and ship inside the deployed JAR. It works, but it is wrong.
  5. The spring-boot-maven-plugin has been deleted. <plugins> is empty. This one has the most surprising result. See question 4.

There is also a sixth, smaller problem: there is no <properties> block. That is question 3.

2. Which fail fast, and which fail late.

Almost none of them fail fast. That is exactly what makes this POM dangerous. Every coordinate here really exists on Maven Central, so Maven fetches everything without complaint. Compiling works too. Our one source file only uses SpringApplication and @SpringBootApplication. Classes with those names exist in both versions of Spring.

The first thing that actually fails is the test phase. @SpringBootTest tries to start the app. Boot 4.1.1 code calls Spring Framework 6 classes, and those classes lack the methods it expects. So the app fails to start. Predicted: a NoSuchMethodError or NoClassDefFoundError, wrapped inside a BeanCreationException (the error Spring throws when it cannot create a bean). The build stops at test with BUILD FAILURE.

Mistake 4 (the missing scope) never shows itself at all. It just quietly makes the JAR bigger. Mistake 1 stays hidden until Spring Boot finally deletes the old starter.

3. Which Java version. Java 17, not 21. Here is the chain:

  1. The <properties> block is gone.
  2. So java.version falls back to the value in spring-boot-starter-parent, which is 17 (checked in the published 4.1.1 parent POM).
  3. The parent makes maven.compiler.release follow ${java.version}.
  4. So the compiler produces Java 17 bytecode.

Our code uses no Java 21 features, so everything still compiles and nothing complains. The proof is in the build log: Compiling 1 source file with javac [debug parameters release 17]. That number is worth a glance after every build.

4. What happens on java -jar. First, the question itself is a bit off. With mistake 2 in place, the build would have stopped at the failing test. There would be no BUILD SUCCESS. So assume they used -DskipTests, because that is exactly what people do when a test is in their way.

Now the interesting part: mistake 5. Without the spring-boot-maven-plugin, the repackage goal never runs. The package phase still makes a JAR, but an ordinary one. It holds our one class, our YAML file, and nothing else. There is no BOOT-INF/lib/, no dependencies inside, no launcher, and no Main-Class line in the manifest.

$ java -jar target/ecommerce-0.0.1-SNAPSHOT.jar
no main manifest attribute, in target/ecommerce-0.0.1-SNAPSHOT.jar

One line. No stack trace, and no hint about the cause. This is a very common real-world error. The cause is almost always one of two things. Either the plugin is missing from the POM, or nobody ran mvn package and the JAR is old. Remember this one, because the message itself tells you nothing.

Also think about what would happen if the manifest were correct. The app would start, then crash while setting itself up, because of the version clash from question 2. That is two separate failures stacked on top of each other. A POM that has been "improved" several times usually looks like that.

5. The corrected file.

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
</parent>

<groupId>com.ecommerce</groupId>
<artifactId>ecommerce</artifactId>
<version>0.0.1-SNAPSHOT</version>
<packaging>jar</packaging>

<properties>
    <java.version>21</java.version>   <!-- the sixth fix (question 3): override the parent's 17 -->
</properties>

<dependencies>
    <!-- fixes 1 + 2: correct Boot 4 name, and NO version -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>

    <!-- fix 3: the explicit tomcat starter is deleted — it comes in
         transitively via spring-boot-starter-webmvc -->

    <!-- fix 4: test scope restored -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<build><plugins>
    <!-- fix 5: the plugin is what makes the jar executable at all -->
    <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
</plugins></build>

This is, of course, the file we wrote in section 5. The point of the exercise is not to write something new. It is to look at a POM someone hands you, and see exactly which lines will hurt you, and when.

Want to watch it break for real? Follow these steps:

  1. Comment out the <plugin> block in your own pom.xml for a moment.
  2. Run mvn clean package, then java -jar target/ecommerce-0.0.1-SNAPSHOT.jar.
  3. You should see the "no main manifest attribute" line above, and nothing else.
  4. Put the block back, rebuild, and check that it runs again.

Breaking something on purpose and watching the predicted failure appear teaches more than reading about it.

11Quick Recap

  • A build tool keeps the list of what your project needs, fetches it all, makes the versions fit, and builds the same way everywhere. Doing that by hand leads to JAR hell.
  • Our pom.xml has one version number, on the parent. The parent's BOM pins about four hundred tested libraries, so never write a <version> on a Spring dependency.
  • A starter is an empty JAR whose POM lists libraries. Auto-configuration then reads the classpath the starter filled.
  • Maven phases run in order, and each includes all the ones before it. So mvn package compiles and tests first. A goal like spring-boot:run runs on its own.
  • In Boot 4, use spring-boot-starter-webmvc and spring-boot-starter-webmvc-test. Translate the old -web and -test names on sight.
