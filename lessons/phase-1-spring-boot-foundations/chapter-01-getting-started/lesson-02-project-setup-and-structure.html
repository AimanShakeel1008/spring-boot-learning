Project Setup and Structure

We build the E-Commerce project for real: what a build tool is, what Maven actually does, every single file and folder accounted for, and the complete journey from typing a command to a live HTTP response.

Files created: phase-1-monolith/ecommerce/pom.xml · EcommerceApplication.java · application.yml · EcommerceApplicationTests.java · api.http · Prerequisites: Lesson 00, Lesson 01 · Pinned: Spring Boot 4.1.1 · Java 21 · Maven 3.9.16

1The Problem

You have an empty folder. You want it to become a running web application. Let us be painfully literal about what stands between those two states, because every single obstacle we are about to meet is one that a build tool was invented to remove.

Your Java source code is text. The machine cannot run text. Something has to turn EcommerceApplication.java into EcommerceApplication.class — a file of bytecode, the compact instruction format the Java runtime actually executes. The program that does that translation is the compiler, javac, and you can run it yourself. Fine. One file, one command.

Now your code says import org.springframework.boot.SpringApplication;. The compiler stops dead: it has never heard of that class. It is not part of Java. It lives in a file called spring-boot-4.1.1.jar, which is sitting on a server somewhere on the internet, and which you must now find, download, and tell the compiler about by hand. So you go to a website, you search, you download a jar, you point the compiler at it. And the compiler stops again — because SpringApplication itself imports classes from four other jars, which import classes from eleven more, and by the time a Spring Boot web application is fully assembled you are looking at roughly forty separate jar files that all have to be present, all at once, all at compatible versions.

That last word is where it stops being tedious and starts being genuinely dangerous. Suppose you download Spring Framework 7.0.9 and, separately, a Tomcat 10.1 jar you found in an old tutorial. Everything compiles. The application starts. And then, forty minutes into a demo, one particular request path calls a method that Spring 7 expects Tomcat to have and Tomcat 10.1 does not. The program does not fail at startup, when you would notice. It fails at that exact moment, with a NoSuchMethodError that names a method you have never heard of, in a class you did not write, called from a stack trace fifty frames deep. Nothing in the message tells you the real cause, which is that two of your forty jars were never built to work together. Java developers have a name for this state of affairs, and the name is not affectionate: jar hell.

And there is a final indignity. Say you solve it — you find forty jars that genuinely agree with each other. Now a colleague clones your project. Do they get the same forty? Only if you wrote the list down somewhere machine-readable and they can fetch exactly those. Otherwise the phrase from Lesson 01 comes back: it works on my machine.

So the problem is not "how do I compile Java." The problem is: who keeps the list of what this project needs, who fetches it, who guarantees the pieces fit, and who turns the result into one runnable thing — reproducibly, on every machine, forever? The answer to all five is a build tool, and ours is Maven.

2Real World Analogy

You are cooking dinner for eight people tonight and you have an empty kitchen.

The hard way is to invent the meal, write down every ingredient, walk the supermarket aisles guessing quantities, and hope that the curry paste you grabbed is the same heat as the one the recipe assumed. Get the quantities wrong and you find out at 7pm, with guests in the room.

The easy way has three parts. First you write a shopping list — not the food itself, just the names. Second, somebody else does the shopping: they read your list, go to the shop, bring everything back, and — crucially — if an item on your list is a meal kit, they bring the whole box with all its contents, without you having to list each contents item separately. Third, you buy those kits from a brand you trust, and that brand has already tested that its sauce works with its spice blend works with its noodles. You do not personally verify that the chilli and the coconut milk get along. Somebody did that for you and put their name on it.

In the kitchenIn our project
The shopping list on the counterpom.xml — names what you need, contains none of it
The person who goes shoppingMaven — reads the list and fetches everything
The supermarketMaven Central — the public repository every library is published to
Your pantry at homeThe local repository, ~/.m2/repository — already-fetched things are never fetched twice
A meal kit boxA starter — one name that brings a whole set of libraries
Opening the kit and finding sauce, spice and noodles insideTransitive dependencies — what your dependencies themselves depend on
The brand guaranteeing its ingredients suit each otherThe parent POM — one tested version for every library at once
"Chop, then fry, then simmer, then serve" — in that order, alwaysThe build lifecycle — fixed phases that always run in order
Everything plated and carried out as one trayThe executable jar — your code and all forty libraries in one runnable file

Hold on to one detail in particular, because it is the single most valuable thing Maven does and it is easy to skate past. You did not choose which brand of coconut milk goes with which brand of chilli. The kit maker did, and they tested it. That is the parent POM, and it is why there is not a single version number next to any library in the file we are about to write.

3The Concept Explained

3.1 What a build tool is

A build tool is a program whose job is to turn your source code into a finished, runnable program — and to do it the same way every time, on every machine.

"Build" sounds vague, so here is the concrete list of what it means for a Java project. A build tool must: read a written list of the libraries the project needs; download each one, plus everything they need; compile every .java file into .class bytecode with all those libraries visible to the compiler; copy non-code files such as settings into the right place; compile the test code too; run every test and stop the whole build if any of them fails; and finally bundle the result into a single distributable file.

You could do all of that by hand. People did, for years, using a tool called Ant where you wrote out each of those steps yourself in XML. The insight that replaced it was simple and slightly bossy: almost every Java project does those steps in the same order, so stop describing the steps and start describing the project. Tell the tool what the project is called and what it needs; the tool already knows what building means. That is Maven's entire philosophy, and it is the same convention over configuration idea Spring Boot applies to configuration — which is not a coincidence. Maven's success is precisely what made Boot's approach feel natural.

3.2 Coordinates: how any library in the world is named

Before Maven can fetch anything, there has to be an unambiguous way to name it. Maven uses three values, and together they are called the coordinates of an artifact. (An artifact is just "a thing a build produces", which in practice almost always means a jar file.)

CoordinateWhat it identifiesOur example
groupIdWho published it. Written in reverse internet-domain order.org.springframework.boot
artifactIdWhich of that publisher's things it is.spring-boot-starter-webmvc
versionWhich release of it.4.1.1

Why reverse domain order for the group? Because the internet already solved the "two organisations must never pick the same name" problem, and reusing the answer is free. Spring owns springframework.org, so nobody else can plausibly claim org.springframework. Amazon publishes under software.amazon.awssdk. Your own company would use something like com.yourcompany. It is the same convention Java itself uses for package names, for exactly the same reason.

Those three values map directly onto a folder path on a web server. The coordinates org.springframework.boot : spring-boot-starter-webmvc : 4.1.1 become:

https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-starter-webmvc/4.1.1/
                              └─────── groupId ───────┘└──── artifactId ────┘└version┘

That is not a search. There is no lookup service, no index to query. The address is computed from the three values by replacing every dot in the groupId with a slash. This is why a single typo in a coordinate produces a blunt "could not resolve dependency" error rather than a helpful "did you mean…?" — Maven asked for a URL that does not exist, and a web server has nothing intelligent to say about that.

3.3 The repository, and why the second build is fast

A repository is a place artifacts live. There are two that matter to you.

Maven Central is the public one — a single, free, enormous store of open-source Java libraries, and the default place Maven looks. Publishing to it is deliberately bureaucratic (you must prove you control the domain in your groupId), which is exactly why it can be trusted as the default.

Your local repository is a folder on your own machine at ~/.m2/repository on macOS and Linux, or C:\Users\YourName\.m2\repository on Windows. Every jar Maven ever downloads is filed there, under a folder path derived from its coordinates. Before fetching anything from the internet, Maven checks here first.

This is why your very first Spring Boot build takes two or three minutes and prints a waterfall of "Downloading from central…" lines, and your second build takes eight seconds in silence. Nothing was optimised. The second build simply found all forty jars already sitting in the pantry. It also means you can build with no internet connection at all, provided you have built once before — which is worth knowing the first time you try to work on a train.

If a download ever gets interrupted, the local repository can be left holding a half-written file, and every later build will fail on it in a confusing way. The fix is blunt and safe: delete the offending folder inside ~/.m2/repository and build again — Maven will simply re-download it. Deleting the entire ~/.m2/repository folder is also safe; it costs you nothing but one slow build. Nothing irreplaceable is ever stored there.

3.4 Transitive dependencies — the thing that does the real work

A dependency is a library your project needs. A transitive dependency is a library that your dependency needs. Maven follows that chain all the way down, automatically, and this is the feature that turns forty manual downloads into two lines of text.

Let us trace it for real, with the actual contents of the actual files — these are not illustrative numbers, they are what spring-boot-starter-webmvc version 4.1.1 genuinely declares.

Now the obvious question, and it is the right one: if Maven is pulling in dozens of things by itself, what happens when two branches of that tree ask for different versions of the same library? Suppose Spring MVC wants SLF4J 2.0.18 and some other library wants SLF4J 1.7.36. Both cannot be on the classpath — the Java runtime will load exactly one org.slf4j.Logger class and ignore the other, and if it loads the wrong one, methods go missing at run time.

Maven's built-in answer is a rule called nearest wins: of the conflicting versions, the one fewest steps away from your pom.xml is used. It is deterministic, which is good. It is also arbitrary — it picks by position in a tree, not by whether the result actually works. That is not good enough for a framework made of forty co-operating pieces, which brings us to the real solution.

A command worth knowing now and using forever: mvn dependency:tree prints the entire resolved tree for your project, indented, with a marker on every version Maven overrode. When a library behaves strangely, this is the first thing to run. Try it after the build in section 5 and you will see the ≈40 jars above with your own eyes.

3.5 The parent POM and dependency management

In the shopping analogy, the parent POM is the brand that guarantees its ingredients suit each other. Mechanically, here is what it is.

Our pom.xml declares a <parent>, which is simply another pom.xml published on Maven Central. Our file inherits from it, exactly the way a Java class inherits from a superclass: anything the parent declares, we get for free, and anything we declare ourselves overrides it. Our parent is spring-boot-starter-parent, and it in turn has a parent of its own, spring-boot-dependencies.

That grandparent file is the interesting one. It contains a section called <dependencyManagement>, and the distinction between that and an ordinary <dependencies> section is the single most useful thing to understand about Maven:

  • <dependencies> means "fetch this." The library is downloaded and put on the classpath.
  • <dependencyManagement> means "if anyone asks for this, use this version." Nothing is downloaded. It is a price list, not an order.

spring-boot-dependencies is a price list covering roughly four hundred libraries, every one of which the Spring team built and tested together as a set. A file whose only job is to declare versions for a coherent set of libraries has a name: it is a BOM, short for Bill of Materials — a term borrowed from manufacturing, where a bill of materials lists every part that goes into a product.

Here are real entries from the 4.1.1 BOM, checked on Maven Central on 2026-09-30:

<!-- inside spring-boot-dependencies 4.1.1 -->
<spring-framework.version>7.0.9</spring-framework.version>
<tomcat.version>11.0.24</tomcat.version>
<jackson-bom.version>3.1.5</jackson-bom.version>
<logback.version>1.5.38</logback.version>
<junit-jupiter.version>6.0.3</junit-jupiter.version>
<assertj.version>3.27.7</assertj.version>
<mockito.version>5.23.0</mockito.version>
<h2.version>2.4.240</h2.version>
<postgresql.version>42.7.13</postgresql.version>
<hibernate.version>7.4.5.Final</hibernate.version>

This is why our pom.xml has no version numbers in it. We write two dependencies and zero versions, and the outcome is forty jars that a team of people spent months verifying against each other. Changing our single <version>4.1.1</version> on the parent moves all of them in lockstep. That is the whole trick, and it is the cure for the jar hell in section 1.

spring-boot-starter-parent adds a few things on top of the BOM. Verified from the published file: it sets java.version to 17 by default and wires maven.compiler.release to follow it (which is why setting one property in our file changes what the compiler targets), it forces UTF-8 encoding for source files and build output, it pins the version of every build plugin, and it sets resource.delimiter to @ — a detail that becomes a famous trap, and which we will meet again in section 7.

Check yourself: our pom.xml lists two dependencies and roughly forty jars end up on the classpath. Where did the other thirty-eight come from, and who chose their versions?

They came from transitive resolution: each of our two dependencies declares its own dependencies, those declare theirs, and Maven walks the whole tree until there is nothing left to fetch.

Their versions were chosen by the BOM inside spring-boot-dependencies, which our parent inherits from. Maven's own "nearest wins" rule is what would apply if nobody had decided — but the BOM's <dependencyManagement> section overrides it for every library Spring manages, which is essentially all of them. So the answer is: Maven fetched them, but the Spring team picked them.

3.6 What a starter actually is

Lesson 01 defined a starter as "a pre-bundled group of libraries for one job". Now that you know what a POM is, we can be exact, because the reality is funnier than the description suggests.

A starter is an empty jar. Genuinely — download spring-boot-starter-webmvc-4.1.1.jar and open it and there are no classes inside. All of its value is in the POM file published alongside it, which lists five dependencies and nothing else. A starter is a shopping list masquerading as a product.

That is a deliberate design. It means a starter is a pure statement of intent — "I am building a Spring MVC web application" — separated completely from the code that implements the intent. Boot's auto-configuration then reads the classpath that the starter produced and draws conclusions from it, exactly as Lesson 01's simulation showed. The starter supplies the evidence; auto-configuration is the detective.

Here is the real content of our two starters, taken from their published POMs:

spring-boot-starter-webmvc  (no classes of its own)
 ├── spring-boot-starter              core Boot: autoconfigure, logging, snakeyaml, jakarta.annotation
 ├── spring-boot-starter-jackson      Jackson 3 — Java objects to and from JSON
 ├── spring-boot-starter-tomcat       the embedded server, plus spring-boot-tomcat
 ├── spring-boot-http-converter       reading and writing HTTP message bodies
 └── spring-boot-webmvc               Spring MVC itself, plus its auto-configuration

spring-boot-starter-webmvc-test  (no classes of its own, scope: test)
 ├── spring-boot-starter-test         JUnit 5 · AssertJ · Mockito · Hamcrest · JSONPath · spring-test
 ├── spring-boot-starter-jackson-test JSON assertions
 ├── spring-boot-starter-webmvc       the web starter again, so tests see the same classes
 ├── spring-boot-webmvc-test          MockMvc — call a controller without a real server
 └── spring-boot-resttestclient       RestTestClient — Boot 4's HTTP test client

The starter rename you will trip over within a week. Every Spring Boot tutorial, book, video and Stack Overflow answer written before 2026 starts a web project with this:

spring-boot-starter-web spring-boot-starter-webmvc

What 3.x did: one starter named spring-boot-starter-web, pulling in a single monolithic auto-configuration jar. That jar grew from 182 KiB in 2014 to about 2 MiB by Boot 3.5 — every auto-configuration for every technology Spring supports, shipped to every application whether it used Kafka or not.

What 4.x does: that monolith was split into focused spring-boot-<technology> modules, and the starters were renamed to match the module each one actually pulls in. "web" was ambiguous — Spring has two completely different web stacks — so the servlet one became webmvc, matching webflux, which was already named after its technology. Two more renames landed at the same time: spring-boot-starter-web-services became spring-boot-starter-webservices, and the three OAuth2 starters gained a security- prefix (for example spring-boot-starter-oauth2-client → spring-boot-starter-security-oauth2-client).

Why it changed: smaller classpath, fewer irrelevant classes for Boot's rule engine to evaluate at startup, and a name that tells you what you are actually getting. There is a second, quieter benefit — with per-technology modules, what you depend on becomes an honest statement of what your application uses, which matters for security scanning and for native images later in Phase 3.

What this means for you: type spring-boot-starter-webmvc in our project. When you read an older tutorial, translate -web to -webmvc on sight. The old name still resolves today — it is deprecated, not deleted — so a copied tutorial will appear to work, which is exactly why this is worth knowing rather than discovering. One genuine behavioural difference: the new starter pulls in spring-boot-starter-tomcat itself, so the separate Tomcat dependency that older tutorials add explicitly is now redundant.

The test starter changed too, and this one catches people out because the old name still works.

spring-boot-starter-test spring-boot-starter-webmvc-test

What 3.x did: one test starter for everything. spring-boot-starter-test brought JUnit, Mockito, AssertJ and all the web testing helpers, whether your project had a web layer or not.

What 4.x does: the same modularization applied to testing. spring-boot-starter-test still exists and still holds the technology-neutral core — JUnit Jupiter, AssertJ, Mockito, Hamcrest, JSONPath, spring-test. The web-specific helpers moved into spring-boot-starter-webmvc-test, which contains spring-boot-starter-test. Asking for the webmvc one gets you both.

Why it changed: the same reason as the main starters — you should only carry the testing tools for the technologies you actually use. It also creates a natural home for Boot 4's new RestTestClient.

What this means for you: in a web project, use spring-boot-starter-webmvc-test — which is what Spring Initializr now generates. If you copy a 3.x tutorial's spring-boot-starter-test line, your project will still compile, and then a test that uses MockMvc will fail with "cannot find symbol", and the cause will not be obvious. There is a related Boot 4 change you will meet properly in the testing chapter: @SpringBootTest no longer hands you MockMvc or TestRestTemplate automatically the way it used to.

The escape hatch you should know about and not use.

spring-boot-starter-classic

What it is: a starter that pulls in all of Boot's modules — so every auto-configuration class is available, exactly as in the pre-4.0 monolith — while excluding their transitive dependencies. The migration guide describes it as a bridge: swap spring-boot-starter for spring-boot-starter-classic (and spring-boot-starter-test for spring-boot-starter-test-classic), get your existing 3.x application compiling and running under Boot 4 quickly, then migrate to the proper modular starters afterwards.

Why a new project must not use it: it exists purely to make an upgrade less painful. Using it on a fresh project re-creates the exact problem modularization was invented to solve — a bloated classpath full of auto-configurations you will never use — and the official guidance is explicitly to migrate away from it. We are starting fresh, so we start modular.

3.7 The folder layout, and why it is not negotiable

You never told Maven where your source code is. It found it anyway, because the layout is a convention that Maven assumes and that essentially every Java tool in existence now also assumes.

Taking each in turn, with what actually breaks if you get it wrong:

  • src/main/java — production Java source. Maven compiles everything under here. The folder structure beneath must exactly mirror the package declarations: package com.ecommerce; requires the file to sit in src/main/java/com/ecommerce/. Put the file one folder out and the compiler rejects it before it even looks at the code.
  • src/main/resources — files that are not code but must travel with the application: application.yml, later on SQL scripts, message files, templates. Everything here is copied, unchanged in structure, to the root of the built jar. That is precisely why Boot finds application.yml with no configuration from you: at run time the file is sitting at the top level of the jar, where Boot looks.
  • src/test/java — test source, a completely separate compilation. Tests may use production classes; production code can never see tests. That separation is enforced, not polite, and it is what guarantees your test libraries cannot accidentally end up in production. (src/test/resources exists for the same reason and holds test-only settings; we have no need for it yet.)
  • target/ — everything the build generates: compiled .class files, the jar, test reports. Maven creates it; you never edit inside it; it is in .gitignore and must stay there. Delete the whole folder any time you like — that is literally what mvn clean does, and "have you tried mvn clean?" is the Java equivalent of turning it off and on again. It works more often than it has any right to, because it forces every stale .class file to be rebuilt.

3.8 The build lifecycle: phases always run in order

When you type mvn package, you are not naming a task. You are naming a phase — a point in a fixed, ordered sequence — and Maven runs that phase and every phase before it.

This single fact explains most of Maven's behaviour that confuses newcomers, and it is worth being concrete. The default lifecycle for a jar project, in order:

#PhaseWhat happens
1validateCheck the POM is well-formed and the project structure makes sense.
2compileCopy src/main/resources into target/classes, then compile src/main/java into the same place.
3testCompile src/test/java, then run every test. Any failure stops the build here.
4packageZip target/classes into target/ecommerce-0.0.1-SNAPSHOT.jar.
5verifyRun any integration checks.
6installCopy the jar into your local repository so other projects on this machine can depend on it.
7deployUpload it to a shared remote repository. Almost always a job for a build server, not a person.

So mvn package compiles and runs your tests too — you never have to ask for those separately. And mvn install does everything package does and then some. The cumulative rule also explains the most common Maven bewilderment of all: "I asked it to package and it said BUILD FAILURE because of a test." Yes. That is the design. A build that packages code known to be broken would be worse than useless.

clean is the odd one out. It belongs to a separate lifecycle whose only job is deleting target/, which is why you write mvn clean package — two lifecycles, in that order — rather than expecting package to imply it.

Finally, mvn spring-boot:run looks different because it is different. Anything with a colon in it is a goal: one specific action from one specific plugin, run directly rather than as part of a phase. Read it as plugin : goal — the spring-boot plugin, its run goal. It compiles what is needed and launches the application straight from target/classes without packaging a jar at all, which is why it is the fast command for development.

Pick a command and watch which phases actually execute, in order, and what appears in target/. The point to feel here: you never name more than one phase, and you always get everything before it.

Pick a command, then press “Run it”.

A model of the lifecycle, not the real thing — five commands and seven phases instead of Maven's full set, and the timings are invented. Your machine is the authority: run the real commands from phase-1-monolith/ecommerce/ and compare. mvn help:describe -Dcmd=package will print the genuine phase-to-plugin bindings if you want to check the middle column for yourself.

Check yourself: you run mvn package and it prints BUILD FAILURE with a failing test. Is there a jar in target/?

No. test comes before package in the lifecycle, and a failing test halts the build at that point. The package phase is never reached, so no jar is produced.

If an older jar is sitting there from a previous successful build, it is still there — untouched and now misleading, because it does not contain your latest code. That is one of the quieter arguments for habitually typing mvn clean package: a failed build then leaves you with no jar at all, rather than a stale one you might accidentally run and be baffled by.

3.9 Maven versus Gradle — the honest comparison

Maven is not the only Java build tool. Gradle is the other one you will meet, and since Spring Initializr defaults to it, you should know why we are not using it.

MavenGradle
Build filepom.xml — XML, purely declarativebuild.gradle(.kts) — Groovy or Kotlin, real code
VerbosityWordy. A dependency is five lines.Terse. A dependency is one line.
FlexibilityDeliberately limited — you describe the project, not the stepsNearly unlimited — you can write arbitrary logic
Speed on big projectsSlower — no build cache by defaultFaster — incremental builds, caching, a resident daemon
PredictabilityVery high. Every Maven project looks the same.Lower. Every Gradle project can look different.
Learning curveShallow. Learn it once, read any project.Steeper. A custom build can be a small program.

Both are excellent and both are everywhere; this is not a case of one being obsolete. We use Maven for a specific teaching reason: its rigidity is a feature while you are learning. Because a Maven build cannot contain clever custom logic, there is never a hidden step doing something surprising — the structure you learn here is the structure of essentially every Maven project you will ever open. Gradle's power to make each project different is exactly what you do not want when you are trying to learn what is normal. Learn Maven first, meet Gradle later and you will understand what its shortcuts are shortcuts for.

3.10 Spring Initializr, option by option

Spring Initializr is a website at start.spring.io that generates a new, correct Spring Boot project as a zip. It is not a toy — it is run by the Spring team, it is how professionals start projects, and both IntelliJ IDEA and VS Code have it built in so you never have to leave the editor.

Every option, and what we choose:

Spring BootThe version. Options ending in -SNAPSHOT, -M or -RC are unfinished — never pick one for real work.4.1.1
GroupThe groupId. Reverse domain.com.ecommerce

Two of those deserve a second look. Package name is the one that silently ruins afternoons: Spring's search for your classes begins at the package of your main class and covers only that package and its sub-packages. Put a controller in a sibling package and Spring will not find it, will report no error at all, and the endpoint will simply 404 — a failure with no message, which is the worst kind. Lesson 03 covers this properly, with a simulation.

And Dependencies: adding a starter here is exactly the same as typing a <dependency> block into pom.xml yourself. The website has no special power. It is a convenience for the first five minutes, and after that you edit the POM directly. You can also start a project entirely from the command line, which is worth seeing once just to demystify the website:

# Generates and unzips exactly what the website would have given you.
curl https://start.spring.io/starter.zip \
  -d type=maven-project -d language=java -d bootVersion=4.1.1 \
  -d groupId=com.ecommerce -d artifactId=ecommerce \
  -d packageName=com.ecommerce -d packaging=jar -d javaVersion=21 \
  -d dependencies=web \
  -o ecommerce.zip

A detail worth catching: notice that the dependency is still requested as web in that command, yet Boot 4.1.1 generates spring-boot-starter-webmvc in the POM. web is Initializr's internal identifier for "the servlet web stack"; it maps that identifier to whichever artifact is correct for the Boot version you selected. Pick Boot 3.x and the very same request yields spring-boot-starter-web. The website is quietly translating for you — which is precisely the translation you now have to do by hand when reading an old tutorial.

3.11 From a typed command to the first HTTP response

This is where all of it comes together. Here is the complete chain, with nothing skipped.

Step by step, with the details that matter:

  1. You type java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. The -jar flag tells the Java runtime: this file is a program, look inside it to find out where to start.
  2. The JVM opens the jar and reads META-INF/MANIFEST.MF, a small text file every jar contains. It looks for a line saying Main-Class:, because that names the class whose main method to call. Without that line you get "no main manifest attribute" and nothing happens.
  3. That line does not name your class. It names org.springframework.boot.loader.launch.JarLauncher, a class Spring Boot's Maven plugin inserted during the repackage step. Why? Because of a real limitation: the standard Java class loader can read classes out of a jar, but it cannot read classes out of a jar that is inside another jar. Our fat jar contains forty nested jars. So Boot supplies its own launcher and its own class loader that can. Your real main class is recorded separately in the manifest as Start-Class:, and the launcher reads it and calls it once the class loader is ready. This is the mechanism that makes "one runnable file" possible at all, and it is why the packaging step is called repackaging — it rewrites an ordinary jar into this special layout.
  4. SpringApplication.run(EcommerceApplication.class, args) executes. It detects from the classpath that this is a servlet web application, creates the application context, evaluates every auto-configuration rule against the classpath exactly as Lesson 01's simulation modelled, and creates the resulting objects.
  5. Because the web auto-configuration matched, Tomcat starts — inside this same process, as a library — and binds to port 8080. SpringApplication.run does not return; the application stays alive.
  6. A request arrives. Tomcat accepts the connection and hands the request to Spring's front door, the DispatcherServlet, which looks for something mapped to that path. We have written nothing, so there is no match — and Boot's default error handling produces a 404 Not Found.

That 404 is the goal of this lesson, and it is worth being clear about why it is a success rather than a disappointment. It proves that a socket was opened, a TCP connection accepted, an HTTP request parsed, Spring's servlet consulted, a decision made, and a correctly-formed HTTP response written back. Every part of the chain worked. The only thing missing is an endpoint — which is Chapter 4's job, not today's.

Three things from this section show up constantly in professional work. The fat jar is why modern Java deploys well to containers: the Dockerfile for a Spring Boot service is often four lines, because there is no server to install — you copy one file and run it. The BOM is how real teams stay sane; a company with thirty microservices publishes its own parent POM so every service uses the same tested versions, and upgrading the whole estate becomes a one-number change. And "can you explain what happens between java -jar and the first response?" is a genuinely common interview question, precisely because it separates people who have only followed tutorials from people who know where the seams are.

4The Wrong Way

Wrong approach

Let us do exactly what section 1 described: assemble the project by hand. Not as a straw man — this is genuinely how it was done, and seeing it fail makes the cure legible.

# Create a folder, write the class, download some jars, compile.
mkdir ecommerce && cd ecommerce
mkdir -p src lib
# ... write src/EcommerceApplication.java ...

# Hunt down jars by hand. The versions are picked by guesswork and
# whatever a blog post from 2023 happened to mention.
curl -O https://repo1.maven.org/maven2/.../spring-boot-4.1.1.jar
curl -O https://repo1.maven.org/maven2/.../spring-core-6.1.2.jar        <-- wrong major version
curl -O https://repo1.maven.org/maven2/.../tomcat-embed-core-10.1.19.jar <-- also wrong
# ...and roughly thirty-seven more...

# Compile, listing every jar by hand on the classpath.
javac -cp "lib/*" -d out src/EcommerceApplication.java

# Run it, listing them again.
java -cp "out:lib/*" EcommerceApplication

What goes wrong. Four separate things, and they get worse as the list goes down.

First, the tedium: forty URLs to find, by hand, with no index telling you which forty. Second, there is no record of what you downloaded, so a colleague cannot reproduce your lib/ folder and neither can you in six months. Third, the classpath must be retyped for both compiling and running, and one forgotten jar is a runtime crash. And fourth — the one that actually hurts — nothing checks that these versions belong together. Spring Boot 4.1.1 is built against Spring Framework 7 and Tomcat 11. We have grabbed Spring 6 and Tomcat 10. Nothing complains. It compiles.

Here is what that looks like when it finally surfaces — and notice when it surfaces:

$ javac -cp "lib/*" -d out src/EcommerceApplication.java
$ (silence — it worked)

# Startup: still fine for a second and a half...
$ java -cp "out:lib/*" EcommerceApplication

INFO  --- Starting EcommerceApplication using Java 21.0.9
Exception in thread "main" java.lang.NoSuchMethodError:
  'void org.springframework.core.ResolvableType.<init>(java.lang.Class)'
    at org.springframework.boot.SpringApplication.createApplicationContext(SpringApplication.java:451)
    at org.springframework.boot.SpringApplication.run(SpringApplication.java:312)
    at EcommerceApplication.main(EcommerceApplication.java:9)

Read that error the way a beginner would. It names a method you have never typed, in a class you have never heard of, from a library you did not knowingly download, and there is no mention anywhere of the actual cause — that spring-core-6.1.2.jar and spring-boot-4.1.1.jar were never meant to be in the same room. NoSuchMethodError (as opposed to the compile-time "cannot find symbol") always means the same thing: the class was there when you compiled and a different version of it is there now. That is jar hell, and no amount of reading your own code will solve it.

It is also the best case. This one crashed at startup, where you notice. The genuinely nasty version of this bug sits quietly on a code path nobody exercises until a customer does.

Check yourself: the compiler was happy but the program crashed. How is that possible?

Java checks method calls twice, against two different things. At compile time javac checks your source against whatever jars are on the classpath then, and records the call as a symbolic reference — "call a method with this name and this signature on this class". At run time the JVM resolves that reference against whatever class is on the classpath now.

If those two classpaths hold different versions of the same class, compilation succeeds and resolution fails — and you get NoSuchMethodError, NoSuchFieldError or NoClassDefFoundError. This is exactly why a build tool that guarantees the compile classpath and the run classpath are derived from the same declared list is not a convenience. It removes an entire category of bug.

There is a second, much more modern wrong way, and you are far likelier to hit this one: copying a dependency from a tutorial.

<!-- Copied from a 2024 blog post into a Spring Boot 4 project -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>   <!-- the 3.x name -->
    <version>3.2.0</version>                          <!-- and a hardcoded version! -->
</dependency>

Two faults in five lines. The artifactId is the deprecated name — which will still resolve, so nothing warns you, and you quietly diverge from every other file in the project. The <version> is far worse: it overrides the BOM. You have just dragged Spring Framework 6 into a Spring Boot 4 application and reinvented the exact crash above, from inside a perfectly valid-looking POM. If you remember one rule from this whole lesson: never write a <version> on a Spring dependency. The parent has already decided, and it decided better than the blog post did.

5The Right Way

Correct approach

Two dependencies, zero versions, and a folder layout that every Java tool already understands. Here is the POM, with every part explained — the full commented file is saved to disk and reproduced in section 6.

<!-- The parent: inherit ~400 tested library versions and sane defaults. -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>   <!-- the one version number in the project -->
    <relativePath/>    <!-- empty = fetch it, do not look in the folder above -->
</parent>

<!-- Our own coordinates. -->
<groupId>com.ecommerce</groupId>
<artifactId>ecommerce</artifactId>
<version>0.0.1-SNAPSHOT</version>
<packaging>jar</packaging>

<!-- Override the parent's java.version (17) with our pinned 21. -->
<properties>
    <java.version>21</java.version>
</properties>

<dependencies>
    <!-- Makes this a web app. NOTE THE NAME: -webmvc, not -web. -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>

    <!-- Test tooling. scope=test keeps it out of the shipped jar. -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<build><plugins>
    <!-- Repackages the plain jar into an executable fat jar,
         and provides the spring-boot:run goal. -->
    <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
</plugins></build>

And the main class, which is four lines of substance:

package com.ecommerce;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication   // unpacked properly in Lesson 03
public class EcommerceApplication {

    public static void main(String[] args) {
        // Start Spring Boot. The class reference tells it where to search;
        // args lets settings be passed on the command line.
        SpringApplication.run(EcommerceApplication.class, args);
    }
}

Step-by-step walkthrough of what happens when you build and run

  1. Maven reads pom.xml and finds the <parent>. It fetches spring-boot-starter-parent:4.1.1, and then its parent spring-boot-dependencies:4.1.1, from Maven Central (or from ~/.m2 if already there).
  2. From that inheritance chain it now knows the version of every library Spring manages, and it knows maven.compiler.release is ${java.version} — which our <properties> block has set to 21.
  3. It reads our two dependencies, looks up their versions in the inherited list (4.1.1 for both), fetches their POMs, and walks every transitive dependency down to the leaves — roughly forty jars, downloaded once, cached in ~/.m2/repository forever.
  4. Phase compile: application.yml is copied into target/classes/, then EcommerceApplication.java is compiled to target/classes/com/ecommerce/EcommerceApplication.class, targeting Java 21, with all forty jars on the compile classpath.
  5. Phase test: EcommerceApplicationTests.java is compiled into target/test-classes/, then the Surefire plugin runs it. @SpringBootTest starts the entire application in memory. If that succeeds, the test passes.
  6. Phase package: the jar plugin zips target/classes into ecommerce-0.0.1-SNAPSHOT.jar. This jar holds only our one class and one YAML file — a few kilobytes, and not runnable.
  7. The spring-boot-maven-plugin's repackage goal then rewrites it: our classes move to BOOT-INF/classes/, the forty dependency jars are placed in BOOT-INF/lib/, the loader classes are added, and the manifest is written with Main-Class: …JarLauncher and Start-Class: com.ecommerce.EcommerceApplication. The original small jar is kept alongside as .jar.original. The result is roughly 20 MB and fully self-contained.
  8. java -jar then follows the six stages of the diagram in section 3.11, ending with Tomcat listening on port 8080.

7Gotchas and Common Mistakes

  • Writing a <version> on a Spring dependency. Every tutorial shows versions, because a tutorial snippet has to stand alone without a parent POM. Copy one into our project and you override the BOM for that library, breaking the guarantee that all forty jars were tested together — and the failure arrives later, as a NoSuchMethodError that says nothing about versions. Avoid it by: never typing <version> under <dependencies> for anything Spring manages. If you genuinely must change one, override the BOM's property in <properties> (for example <h2.version>) so the change is visible in one place.

  • A package name that does not match the folder path. Moving a file in the file explorer without updating its package line — or the reverse — produces a compiler error that reads oddly, along the lines of "class X is public, should be declared in a file named X.java" or a flat refusal to find the class. Developers make this mistake because in most languages a file's location and its namespace are unrelated; in Java they are the same fact stated twice. Avoid it by: moving files with the IDE's refactor command, which updates both.

  • Expecting mvn package to skip the tests. Phases are cumulative, so package runs test first and one failure stops everything. People then reach for -DskipTests to "just get a jar", which works and is almost always the wrong instinct — you have built an artifact you have no evidence about. Avoid it by: fixing the test. Reserve -DskipTests for the rare case where you genuinely need a build of known-broken code for debugging, and never for anything you would deploy.

  • Tabs in application.yml. YAML forbids tab characters for indentation, full stop. Editors that helpfully insert tabs turn a two-line settings file into a startup crash, and the error message talks about scanner exceptions and character positions rather than saying "you used a tab". Avoid it by: configuring the editor to insert spaces for this file type — VS Code and IntelliJ both do this automatically for .yml, but check if you have ever changed the global setting.

  • The @ trap in application.yml. The Spring Boot parent sets resource.delimiter to @ and turns on resource filtering for application*.yml, meaning Maven scans that file at build time and replaces anything of the form @name@ with a Maven property. Write an email address or a Logback pattern containing a bare @…@ pair and Maven will either substitute it into nonsense or fail the build. Avoid it by: knowing it exists — it is genuinely useful (@project.version@ stamps the build version into your config), and mystifying if you meet it by accident.

  • Committing target/. It is 100% generated, it contains a 20 MB jar, and committing it bloats the repository permanently — Git history is not erasable by deleting the file later. Avoid it by: the target/ line already present in our .gitignore. Check with git status before your first commit: if you see anything under target/ listed, stop and fix the ignore file before committing.

8Tradeoffs and When Not to Use This

The parent POM costs you control. Inheriting four hundred version decisions is wonderful until you need a library at a version the BOM does not pin — a security patch released this morning, say. You can override it, but you are then knowingly stepping outside the tested set, and the next Boot upgrade may silently take your override back. There is also a structural limitation: Maven allows exactly one parent, so a company with its own corporate parent POM cannot also inherit from Spring's. The standard answer is to import spring-boot-dependencies as a BOM inside <dependencyManagement> instead of inheriting from it — you get the versions without using up the parent slot, at the cost of losing the plugin configuration and having to declare the spring-boot-maven-plugin version yourself. That is the right choice in a large organisation and the wrong one for us.

The fat jar costs you size and rebuild time. Twenty megabytes for a few kilobytes of your own code is a strange ratio, and every rebuild rewrites all twenty. For a container image that is genuinely wasteful: a one-line code change produces an entirely new 20 MB layer. Spring Boot's answer is layered jars — splitting dependencies and application code into separate image layers so only the small, fast-changing layer is rebuilt. That is a Phase 3 topic, and knowing the tradeoff exists is enough for now.

Maven's rigidity costs you flexibility. If your build needs to generate code, call an external tool, or do anything genuinely unusual, Maven makes you write or find a plugin, where Gradle would let you write four lines of Kotlin. For a standard Spring Boot service this never comes up. For a build with real custom logic, Gradle is the better tool, and preferring it there is not heresy.

When would you not build it this way at all? Three honest cases. If you must deploy into an application server your organisation already runs and will not change, you need war packaging and Boot still supports it. If you are writing a library for other projects to depend on rather than an application, you want a plain jar with no repackaging, no embedded server, and no starter parent forcing versions on your consumers. And if startup time in milliseconds is the requirement — serverless functions, command-line tools — the JVM's warm-up may rule out this whole model, which is what native compilation with GraalVM addresses, again in Phase 3.

For a long-running web service, which is exactly what our E-Commerce platform is, this setup is the right default and will stay right for the rest of Phase 1.

9Key Takeaways

  • Maven exists because a Java project needs someone to keep the list of what it depends on, fetch those things and everything they in turn depend on, guarantee the versions fit together, and build the result identically on every machine — and doing all four by hand produces the class of failure known as jar hell.
  • Our pom.xml contains exactly one version number, on the spring-boot-starter-parent, because that parent inherits a Bill of Materials pinning roughly four hundred libraries that the Spring team tested together — which is why writing your own <version> on a Spring dependency is the fastest way to break a working project.
  • A starter is an empty jar whose entire value is the list of dependencies in its POM; it exists to state an intention, and Spring Boot's auto-configuration then reads the classpath that intention produced and configures accordingly.
  • Maven's phases are cumulative and always run in order, so mvn package compiles and tests first and stops at the first test failure, while anything containing a colon such as spring-boot:run is a plugin goal that runs on its own and drags no phases behind it.
  • In Spring Boot 4 the web starter is spring-boot-starter-webmvc and the web test starter is spring-boot-starter-webmvc-test; the pre-2026 names spring-boot-starter-web and spring-boot-starter-test are what the entire internet still shows you, still resolve today, and are deprecated — so translating them on sight is a skill you now need permanently.

1. The five mistakes.

  2. <version>3.2.0</version> on that dependency. The worst one. It overrides the BOM and drags the entire Spring Boot 3.2 dependency tree — including Spring Framework 6 — into an application whose parent is 4.1.1. Two incompatible generations of Spring are now on one classpath.

Almost none of them fail fast, which is precisely what makes this POM dangerous. Every coordinate here genuinely exists on Maven Central, so dependency resolution succeeds. Compilation succeeds, because our one source file uses only SpringApplication and @SpringBootApplication, and classes by those names exist in both generations.

The first thing that actually fails is the test phase: @SpringBootTest tries to start the application, Boot 4.1.1 code calls into Spring Framework 6 classes that lack the methods it expects, and the context fails to load. Predicted: NoSuchMethodError or NoClassDefFoundError inside a BeanCreationException, and the build stops at test with BUILD FAILURE. Mistake 4 (the missing scope) never announces itself at all — it just silently bloats the jar. Mistake 1 stays invisible until the deprecated starter is eventually deleted from Spring Boot.

3. Which Java version. Java 17, not 21. The <properties> block is gone, so java.version falls back to the value declared in spring-boot-starter-parent, which is 17 (verified in the published 4.1.1 parent POM). The parent wires maven.compiler.release to ${java.version}, so the compiler targets 17. Everything still compiles — our code uses no Java 21 features — so nothing complains. The evidence is right there in the build log: Compiling 1 source file with javac [debug parameters release 17]. The number in that line is worth glancing at after every build.

4. What happens on java -jar. First, note the premise is questionable: with mistake 2 in place the build would have stopped at the failing test, so there would be no BUILD SUCCESS to report. Assume they used -DskipTests, since that is exactly what someone does when a test is in their way.

Now the interesting part — mistake 5. Without the spring-boot-maven-plugin, the repackage goal never runs. The package phase still produces a jar, but it is an ordinary jar: our single class, our YAML file, and nothing else. No BOOT-INF/lib/, no nested dependencies, no loader, and no Main-Class line in the manifest.

$ java -jar target/ecommerce-0.0.1-SNAPSHOT.jar
no main manifest attribute, in target/ecommerce-0.0.1-SNAPSHOT.jar

One line, no stack trace, and no hint about the cause. This is a genuinely common real-world error, and the cause is almost always the same: either the plugin is missing from the POM, or mvn package was never run and the jar is stale. Worth remembering, because the message tells you nothing.

Note also what would happen if the manifest were correct: the application would start and then crash during context creation, for the version-conflict reason in question 2. Two independent failures stacked on top of each other, which is the usual shape of a POM that has been "improved" several times.

5. The corrected file.

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
</parent>

<groupId>com.ecommerce</groupId>
<artifactId>ecommerce</artifactId>
<version>0.0.1-SNAPSHOT</version>
<packaging>jar</packaging>

<properties>
    <java.version>21</java.version>   <!-- fix 3: override the parent's 17 -->
</properties>

<dependencies>
    <!-- fixes 1 + 2: correct Boot 4 name, and NO version -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>

    <!-- fix 3: the explicit tomcat starter is deleted — it comes in
         transitively via spring-boot-starter-webmvc -->

    <!-- fix 4: test scope restored -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<build><plugins>
    <!-- fix 5: the plugin is what makes the jar executable at all -->
    <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
</plugins></build>

Which is, of course, the file we wrote in section 5. The exercise is not to produce something new — it is to be able to look at a POM someone hands you and see exactly which lines will hurt you and when.

Want to watch it break for real? Temporarily comment out the <plugin> block in your own pom.xml, run mvn clean package, then java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. You should see the "no main manifest attribute" line above and nothing else. Put the block back, rebuild, and confirm it runs again. Breaking something deliberately and watching the predicted failure appear is worth more than reading about it.
