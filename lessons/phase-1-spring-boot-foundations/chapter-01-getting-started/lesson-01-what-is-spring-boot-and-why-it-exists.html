What Is Spring Boot and Why It Exists

Three eras of Java web development, and the pain each one left behind. Then Spring Boot's famous "magic", taken apart until no magic is left.

Files created: none. This is a concept lesson; the project is created in Lesson 02 · Prerequisites: Lesson 00 · Pinned: Spring Boot 4.1.1 on Spring Framework 7 · Java 21

  • What a framework, a server and a servlet are, and how Java web apps were built before Spring Boot.
  • What Spring Boot adds on top of Spring Framework: starters, auto-configuration and a server inside your app.
  • How auto-configuration really decides what to set up, step by step, with a simulation you can click.

1The Problem

1.1 The year 2004: a separate server

It is 2004. Your job is to make a Java program answer a web request. Someone visits a web address. Your Java code runs. A page comes back. That is all. Here is what your day really looks like.

First, your program cannot receive web requests. Nothing in Java listens on a network by itself. You need a server. A server is a separate program that keeps running, waits for requests, and hands them to your code. (Section 3.2 explains servers fully.)

So you download a server called Apache Tomcat. You install it as its own application on the machine. It has its own folders, its own setup files, and its own start and stop scripts. It is not part of your project. It is a second program, and you must feed your project into it.

1.2 Every change means the same long routine

Next you write your Java class. Then you write a file called web.xml. It tells the server which web address goes to which class.

That file uses XML. XML is a text format that describes things with tags in angle brackets. For example, <port>8080</port> says "the port is 8080". Each tag has an opening part and a closing part with a slash.

Then the routine goes like this:

  1. You package your compiled code into a WAR file. A WAR is a zip file with a layout the server understands.
  2. You copy that WAR into Tomcat's webapps folder.
  3. You restart Tomcat.
  4. You read Tomcat's log file to see if it worked. A log file is a text file where a program writes down what it is doing.

Change one line of Java, and you do it all again: package, copy, restart, read.

1.3 Then Spring arrives, with piles of XML

Now jump forward a few years. The Spring Framework arrives. It fixes something really important: how a program creates its objects and connects them together. We spend all of Chapter 2 on that idea. It is the best idea in this whole world of tools.

But you set up Spring with XML. By 2010, a normal project has several hundred lines of XML. Those lines say:

  • which classes exist, and how they connect;
  • which database to use (a program that stores your data safely, so it survives a restart);
  • how saving data should behave;
  • and which web address goes where.

None of it is your actual product. And all of it must be right before anything runs at all.

1.4 The failure that really hurt

A new developer joins the team. They spend their first three days not writing features. Instead they install the right Tomcat, match versions, and copy XML from a colleague. Then they hunt down a startup error. It turns out to be a misspelled class name on line 213 of a setup file.

Meanwhile, a project down the hall has slightly different XML and a slightly different Tomcat. Its code mysteriously will not run on your machine. People said "but it works on my machine" all the time. It was not a joke. It was normal.

Every one of those problems is setup. And that setup was the same in almost every Java web app ever written. Yet every team typed it out from scratch, every time. Spring Boot exists because someone finally asked the obvious question. If nearly everyone sets this up the same way, why does everyone still type it out?

2Real World Analogy

Think about the difference between renting an empty apartment and checking into a hotel room.

The empty apartment gives you total freedom. You can choose any furniture, any layout, any appliance. In a way, it can do more than a hotel room. But on your first night there is no bed, no kettle and no towels. So there is no sleep. Before you can do what you came to do, you must make hundreds of choices you do not care about.

The hotel room has already made those choices for you. The bed is made. The kettle is filled. The wifi works. Someone looked at what almost every guest wants, and set it up in advance. And it is not a cage. You can move the chair, ignore the kettle, or bring your own pillow. The defaults are a starting point, not a rule.

In the analogyIn our world
The empty apartmentSpring Framework alone: very powerful, but sets up nothing for you
The furnished hotel roomSpring Boot: the same building, with sensible choices already made
"Most guests want a bed here"Opinionated defaults: the common setup, done in advance

The room has a kettle only in a tea-drinking countryConditional configuration: Boot sets something up only if the signs say you need it
The building itself: walls, plumbing, electricitySpring Framework, still underneath, doing the real work

Remember that last row. It is the most misunderstood thing about Spring Boot. The hotel room is not a different building. It is the same building, with furniture.

3The Concept Explained

3.1 First, what is a framework?

In Lesson 00 we met a library: ready-made code that you call. With a library, you are in charge. You decide when to call it.

A framework flips that around. You do not call the framework. The framework runs, and it calls your code when it decides the time is right. You write the pieces. It decides the order.

Here is a concrete example.

  • With a library, you write: "open the file, read it, close it". Your code calls the library at each step.
  • With a framework, you write a class that says: "when a web request arrives at /products, here is what to do". Then you never call that method yourself. The framework calls it, each time a request comes in.

An everyday version: a library is a recipe book you open when you choose. A framework is a job in a busy kitchen. The head chef calls out orders. You cook what you are told, when you are told. You still do the cooking. But you do not control the timing.

This flip has a name: the Hollywood Principle. It comes from what film studios tell actors: "don't call us, we'll call you". It is so central to Spring that all of Chapter 2 is about it. For now, one sentence is enough: a framework is in charge, and your code fills in the parts it asks for.

3.2 What a server is

A server, here, is a program that keeps running and waits for requests to arrive over the network. It is not a big machine in a data centre. It is a program. (People also call the computer that runs it a "server". The meaning is close, and the context tells you which one.)

A server sits behind a numbered door on your computer, called a port. Ports let many programs share one network connection without mixing things up. Think of a block of flats with one street address. Each flat has its own number, so the post reaches the right person. Web servers in development often use port 8080.

3.3 HTTP: the language of the web

HTTP is the agreed message format for these conversations. Every conversation has two halves:

  • A request: what the caller sends. For example, "give me the product list".
  • A response: what comes back. It has a status code and some data. A status code is a number that says how it went. 200 OK means "it worked". 404 Not Found means "nothing lives at that address".

That is all we need today. Lesson 14 covers HTTP in depth.

3.4 What a servlet and a servlet container are

In Java, the standard way to handle an HTTP request is a servlet. A servlet is a class with a method that receives a request object and fills in a response object.

Servlets cannot run alone. They need a program to host them. That program receives the raw network traffic. Then it calls the right servlet at the right moment. It is called a servlet container, and Tomcat is the most common one. Think of a theatre. The servlets are the actors. The servlet container is the theatre. It opens the doors and lets the audience in. Then it tells each actor when to go on stage.

So the old setup, from the bottom up, was:

  1. Tomcat, installed separately on the machine;
  2. inside it, your WAR file;
  3. inside that, your servlet classes.

Remember the words installed separately. They are about to become the heart of this lesson.

3.6 So what is Spring Boot?

Spring Boot is not a new framework. It does not replace Spring Framework. It is a layer on top of it. Before we list what it does, we need one more word.

The classpath is the full list of code your running program can use. That means your own compiled classes, plus every library Maven downloaded. If a class is on the classpath, your program can use it. If it is not, your program cannot. Think of it as the program's toolbox.

Now, Spring Boot does four things:

  1. Starters. A starter is one dependency that brings in a whole matching set of libraries for one job. Ask for spring-boot-starter-webmvc, and you get the web framework, a JSON converter and a built-in server. Someone has already checked that their versions work together. This cures the JAR hell problem from Lesson 00. (JSON is a simple text format for data, like {"name":"Mug","price":12}. Web apps use it to send data back and forth.)
  2. Auto-configuration. When the app starts, Boot looks at what is on your classpath. Then it sets up the obvious things for you. Section 3.9 takes this apart completely.
  3. An embedded server. "Embedded" means "built in". Tomcat is no longer a program you install. It is a library inside your application. See section 3.7.
  4. Tools for production. Production is the real, live system that real customers use. Every real system needs health checks, measurements, sensible logging, and settings kept outside the code. Boot has these ready to switch on. We meet them properly in Lesson 78 and Chapter 22.

3.7 The flip that changed everything: the embedded server

This is the most visible difference. It is worth a good look.

This has bigger effects than it first seems:

  • One file. Your whole app is a single file you can run. The machine it runs on needs nothing installed except Java.
  • The same version everywhere. The Tomcat you tested with is exactly the Tomcat that runs for real, because it is inside the file. So "works on my machine" mostly stops being a problem.
  • Running is ordinary. Starting your app is just running a Java program. There is no copying files, no restarting a server, and no reading its log.
  • Containers become easy. In Phase 3 we put this app in a container (a sealed box that holds an app and what it needs). The server is inside the file, so the container needs only Java and your JAR. A whole class of deployment problems disappears. Deployment means putting your app onto the machine where it will run for real.

3.8 "Opinionated defaults": what the opinion actually is

People call Spring Boot opinionated. That sounds like marketing until you make it concrete. An "opinion" here is a statement like this: "most apps that have X on the classpath want Y set up. So we will set up Y, unless told otherwise."

Here is an example. You add the web starter. Then Boot's opinions include:

  • run an embedded Tomcat;
  • listen on port 8080;
  • turn the objects your code returns into JSON;
  • show a default error page;
  • serve plain files, like pictures, from a folder called /static.

None of these is a law of nature. They are defaults. The Spring team chose them because most people want them most of the time.

A related slogan is convention over configuration. The tool does not make you spell everything out. It assumes the usual choice. It lets you change it when yours is different. Is port 8080 wrong for you? One line in your settings file changes it. The settings file is called application.yml, and it lives in your project:

# src/main/resources/application.yml
server:
  port: 9000

3.9 Boot steps back when you take over

Here is what makes "opinionated" useful instead of scary: Boot steps back the moment you take over. Say you set up your own database connection. Then Boot's automatic one quietly stands aside. Your own choice always beats Boot's default.

This is not just good manners. It is a rule built into the machinery. To see how, you need two words.

  • An annotation is a marker written with an at-sign, like @Something. You put it on a class or a method. It does nothing by itself. But other code can read it and act on it. Think of a sticky note on a parcel that says "fragile". The note does not protect the parcel. The postal workers who read it do.
  • A bean is an object that Spring creates and looks after for you. Chapter 2 explains beans in full. For now, "an object Spring manages" is enough.

Boot uses an annotation called @ConditionalOnMissingBean. It means: "only set this up if the app does not already have a bean of this kind". So if you make your own, Boot's version is skipped. You will see it work in the next section.

Check yourself: does "opinionated" mean Spring Boot is less flexible than Spring Framework?

No. Anything you can do in Spring Framework, you can still do in Spring Boot. Boot is Spring Framework, with a setup layer on top. What changes is where you start, not how far you can go. Boot gives you a working app before you make any choices. Then it gets out of the way for every choice you do want to make. Instead of "nothing is decided", you get "the usual things are decided, and you can change them". And you can change every one of them.

3.10 How auto-configuration actually works

This is where people say "it's magic". It is not. And if you treat it as magic, you cannot fix it when it goes wrong. Here is how it really works, in four steps.

Step 1: the classpath is a list of clues. Remember, the classpath is everything your running program can use. Boot treats it as a set of clues about what you want. A web framework on the classpath is a strong clue that you want to answer web requests.

Step 2: every starter brings recipes. Inside the JARs is a plain text file. It lists special setup classes called auto-configuration classes. We can call them "recipes". When the app starts, Boot reads those files from every JAR. It builds one long list of possible recipes, often over a hundred. Think of a recipe book where every library you added has written a page.

Step 3: each recipe has conditions. Boot does not use a recipe just because it found it. Each recipe carries conditions, and every condition must be true. The conditions are annotations. The common ones read almost like English:

ConditionMeans
@ConditionalOnClassonly if this class is on the classpath (that is, you added that library)
@ConditionalOnMissingBeanonly if you have not already defined one of these yourself
@ConditionalOnPropertyonly if a named setting has a particular value
@ConditionalOnBeanonly if some other bean already exists

Step 4: check, then use the ones that pass. Boot goes down the list. It checks each recipe's conditions against what is really there. It throws away the ones that fail. It uses the rest. That is the whole trick. Over a hundred possible recipes go in. A few dozen pass. The ones that pass are exactly the ones your dependencies call for.

This is why adding one line to pom.xml can give you a running web server. Just as important, it is why removing that line makes the web server quietly disappear. Nothing random is going on. Boot is acting as a rule engine. A rule engine is a program that checks a list of rules and acts on the ones that are true.

3.11 Try the rule engine yourself

The simulation below has four switches. Here is what each one means:

  • spring-boot-starter-webmvc: the web starter. It brings in the web framework and Tomcat.
  • H2 database driver: H2 is a small database that lives in your program's memory. A driver is a library that knows how to talk to one kind of database.
  • spring-boot-starter-data-jpa: brings in JPA. JPA is a standard way to save Java objects into a database and load them back.
  • I defined my own DataSource bean: a DataSource is the object that hands out connections to a database. This switch means "I made my own, instead of letting Boot make one".

Switch things on and off the classpath. Then start the app and watch the rule engine decide. This is the real logic, made simpler. Boot checks each recipe against its conditions. Only the ones that pass set anything up.

Press “Start the application”.

This is a model of how it works, not the real thing. It has four recipes instead of over a hundred. Your own machine has the final say. From Lesson 02 onwards, you can run mvn spring-boot:run -Dspring-boot.run.arguments=--debug. That prints Spring Boot's real condition report. It shows this exact decision for every recipe, under the headings “Positive matches” and “Negative matches”.

Check yourself: in the simulation, why does turning on “I defined my own DataSource bean” change the result from MATCHED to BACKED OFF, and not to an error?

Because of @ConditionalOnMissingBean. That condition says: "use this recipe only if the app has not already made one of these itself". When you define your own, the condition fails. Boot skips the recipe, and uses your object. Two competing database connections would be an error. Boot avoids that by always giving way to you. This is the promise from section 3.9, built into the machinery.

3.12 Spring Boot versus Spring Framework: the honest difference

People ask about this all the time, usually as if you must pick one. You do not. They are layers, not rivals.

The diagram names three Spring Framework abilities. You will learn each one properly later. Here is a one-line meaning for now:

  • The container is the part of Spring that creates your objects (beans) and keeps them.
  • Dependency injection means handing an object the other objects it needs, instead of letting it build them itself. Chapter 2 covers it.
  • A transaction is a group of database changes that must all succeed together, or all be undone. Think of a bank transfer: money leaves one account and arrives in the other, or neither happens.

3.13 Where Spring Boot 4 sits: the split into modules

We pin Spring Boot 4.1.1, which runs on Spring Framework 7. Two things about this version matter even on day one.

First, the split into modules. For ten years, all of Boot's auto-configuration recipes lived in one JAR, called spring-boot-autoconfigure. Look at how it grew:

  • In 2014 it was about 182 KiB (kilobytes: a small file).
  • By Spring Boot 3.5 it was about 2 MiB (megabytes: about eleven times bigger).

It held every recipe for every technology Boot supports. Every app got all of it, whether it used that technology or not.

Boot 4 split that JAR into small modules, one per technology. A module is a smaller JAR with one clear job. This helps in three ways:

  1. Your app now carries only the recipes for things it really uses.
  2. Your editor stops suggesting classes from libraries you have never heard of.
  3. Boot gets a clearer picture of what you are actually doing.

That split also explains a rename you are about to run into.

The Spring team renamed the modules to match what they contain. So several starters got new names too. You will meet the first one, the web starter, in the very next lesson:

spring-boot-starter-web spring-boot-starter-webmvc

Why: the module behind it is clearly about Spring Web MVC. That is the servlet-based way to build a web app. There is also a "reactive" way, a different style built for handling very many requests at once. We study it in Chapter 28. The old name did not say which one you wanted. The new name does.

What this means for you: in our project, type spring-boot-starter-webmvc. Nearly every tutorial says spring-boot-starter-web, because it was written before 2026. That is not a mistake in the tutorial. It is just the old name. Translate it and carry on.

There is also spring-boot-starter-classic. It keeps the old all-in-one behaviour, for existing projects that move up from 3.x. A new project should not use it.

3.14 Spring Boot 3 is finished

Free support for the 3.x versions ended on 30 June 2026. There are no more free security fixes. That is why this course starts on 4.x, even though most learning material has not caught up. If you learned the old version, you would have to learn everything twice.

"What is the difference between Spring Boot and Spring Framework?" is one of the most common interview questions for Java jobs. Say you answer "Boot is just Spring with less setup". You will get a follow-up question you cannot answer. The strong answer is the one in section 3.12. Boot is a setup layer that depends on the Framework. It works through three things: starters, auto-configuration and the embedded server. Then explain @ConditionalOnMissingBean and why Boot steps back. Now you are clearly ahead of someone who has only followed tutorials.

4The Wrong Way

Wrong approach — configure the plumbing yourself, every time

4.1 The old setup file

Here is roughly what "answer one web address" needed before Boot. First, a setup file. It told the server that Spring should handle requests:

<!-- web.xml — and this is the SHORT version -->
<web-app>
  <servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
  </servlet>
  <servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
  </servlet-mapping>
</web-app>

Here is what those lines say, in plain words:

  • The <servlet> part says: "create a servlet named dispatcher, from the class DispatcherServlet". DispatcherServlet is Spring's one main servlet. It receives every request and passes it to the right piece of your code.
  • load-on-startup says: "create it as soon as the server starts, not on the first request".
  • The <servlet-mapping> part says: "send every web address (/) to that servlet".

Then came a second XML file for the Spring side. It said which folders of code to search, how to build web pages, and where plain files live. If you wanted a database, a third XML file described the connection and how to save data safely. Then you built a WAR, copied it into Tomcat, and restarted.

4.2 What goes wrong

None of that XML is your product. Yet all of it must be exactly right before anything runs. Nothing checks it while you type. A misspelled class name is just text. It looks fine until the app starts. And every project in the company has its own copy. The copies slowly drift apart as each team edits theirs.

If this were misconfigured, the output would be (a prediction):

SEVERE: Servlet [dispatcher] in web application [/store] threw load() exception
java.lang.ClassNotFoundException: org.springframework.web.servlet.DispatchersServlet
        at org.apache.catalina.loader.WebappClassLoaderBase.loadClass(...)
        at org.apache.catalina.core.StandardWrapper.loadServlet(...)
        ... 47 more

How to read it:

  • ClassNotFoundException means "Java looked for a class with this name and could not find it".
  • The lines that start with at are a stack trace. A stack trace is the list of method calls that led to the error, newest first. Here, every line is inside Tomcat.

One extra letter, DispatchersServlet, and the whole app fails to start. The error points at Tomcat's insides, not at your typo. Now imagine that across three XML files, with a new person on the team.

4.3 The other wrong way: fighting auto-configuration

Some people hear "Boot sets things up for me" and do not trust it. So they set up everything by hand anyway, to stay in control. This gives you the worst of both worlds:

  • You get Boot's dependencies and complexity.
  • You also get all the hand-written setup you were trying to avoid.
  • And you get hidden clashes, where your setup and Boot's disagree.

If you do not want one default, change that one default. Do not change all of them just in case.

5The Right Way

Correct approach — declare what you need, let the recipes fire

5.1 One dependency and one class

In Spring Boot, all of that becomes one dependency and one class. Here is the class, with every line explained:

// The package this class belongs to — the folder structure of the project.
package com.ecommerce;

// Pulls in the two Spring Boot types used below, so we can refer to them by
// their short names instead of writing the full package every time.
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

// ONE annotation doing three jobs at once. It marks this class as the
// application's starting point, switches on auto-configuration (section 3.10),
// and tells Spring to look in this package and below for your own classes.
// Lesson 03 takes this annotation apart piece by piece.
@SpringBootApplication
public class EcommerceApplication {

    // The ordinary Java entry point. Nothing framework-specific about main itself:
    // this is the method the JVM calls when you run the program.
    public static void main(String[] args) {

        // Hand control to Spring Boot. This one call creates the container,
        // runs the auto-configuration rule engine, starts the embedded Tomcat,
        // and then returns. Tomcat's own thread keeps the program alive to serve
        // requests (Lesson 03 shows exactly how).
        // We pass our own class so Boot knows where to start looking, and args
        // so settings typed on the command line reach the framework.
        SpringApplication.run(EcommerceApplication.class, args);
    }
}

Eleven lines that matter. No XML. No server to install. No setup file for the server. No packaging steps.

5.2 Step by step: what happens when this runs

  1. The JVM calls main, just as it would for any Java program.
  2. SpringApplication.run takes over. It creates the application context. That is Spring's container: the place that will hold and connect your beans. Chapter 2 is all about it.
  3. Boot reads the recipe lists from every JAR on the classpath. That gives it a hundred or so possible recipes.
  4. It checks each recipe's conditions against what is really there. What is on the classpath? What have you already defined? What do your settings say?
  5. Boot uses the recipes that pass. The web starter is present, so one recipe starts an embedded Tomcat on port 8080.
  6. Boot searches your package for your own classes. It creates the ones it recognises.
  7. Startup finishes, and the program does not exit. Tomcat keeps it running, waiting for requests.

7Gotchas and Common Mistakes

  • Thinking Spring Boot replaced Spring Framework. This is very common, and it makes everything after it confusing. You start looking for "the Boot way" to do dependency injection. But dependency injection is a Framework feature. Boot only switched it on. When you wonder where a feature belongs, ask: is this an ability (Framework) or setup (Boot)?
  • Treating auto-configuration as magic. This causes real problems. Say something is set up in a way you did not expect. If you think it is magic, you have nowhere to look. If you know it is a rule engine, you run the app with --debug and read the condition report. It lists every recipe, and exactly why it matched or did not.
  • Changing defaults just in case. Setting things up by hand "to be safe" causes clashes between your setup and Boot's. Those clashes are much harder to fix than the defaults you were avoiding. Change a default when you have a reason, not in advance.
  • Thinking a starter switches the feature on. A starter only puts libraries on the classpath. Then auto-configuration decides what to do with them, and not every condition may pass. "I added the dependency and it still does not work" nearly always means a condition failed. The condition report tells you which one.
  • Copying Spring Boot 2 or 3 tutorials without translating them. Most material you find is older than Boot 4, and several names changed. spring-boot-starter-web is the first one you will notice. The tutorial is not wrong. It describes an earlier version. Every difference that matters gets a "Changed in Spring Boot 4" card in these lessons, right where it comes up.

8Tradeoffs and When Not to Use This

8.1 Startup work is not free

Checking a hundred or so recipes every time the app starts costs time and memory. For a server that starts once and runs for weeks, this does not matter. But some programs run for only a moment and must start instantly. One example is a cloud function. That is a tiny program that a cloud company runs for you. You pay for it by the millisecond. There, the cost matters.

Lesson 151 covers the tools for that. One is doing the setup work while you build, not while the app starts. Another is a native image: a program compiled straight to machine code, so it starts in milliseconds.

8.2 Convenience can hide things

Boot sets up things you did not write. So when something surprises you, the cause may be in a recipe you have never read. The cure is to understand how it works, and to read the condition report. That is why section 3.10 refused to call it magic. This cost is real. It is the strongest point that Spring Boot's critics make.

8.3 Dependency weight

One starter can bring in dozens of JARs, and you will never use some of them. That is a fair price for a working app in one line. But it means a Boot app is not small. And every JAR could carry a security hole. That is why Lesson 80 sets up automatic checks on your dependencies.

8.4 When not to use Spring Boot

  • Writing a library for other developers? A library should not drag a whole framework along with it.
  • Need a program that starts in a few milliseconds and uses very little memory? Look at a native image, or at a framework built for that, such as Quarkus.
  • Building something truly tiny? Say it has one endpoint (one web address your app answers) and no plans to grow. Boot will work perfectly, but it is a lot of machinery for the job.

Boot is best for real apps that run for a long time and are expected to grow. That is exactly the E-Commerce system we are building.

9Challenge

Think this one through on paper. A colleague shows you a Spring Boot 4 project. Its pom.xml has exactly these dependencies:

spring-boot-starter-webmvc
spring-boot-starter-data-jpa

…and no database driver of any kind. Their app fails to start.

  1. What does the rule engine decide for the web recipe, the database connection recipe, and the JPA recipe?
  2. Why does the app fail, instead of just starting without a database?
  3. Give two different one-line fixes. Say when each is the right choice.
  4. What single command would let them see the engine's reasoning for themselves?
Click to reveal the answer

1. What the engine decides:

  • WebMvcAutoConfiguration: MATCHED. @ConditionalOnClass(DispatcherServlet) passes, because the webmvc starter put that class on the classpath. Boot sets up an embedded Tomcat on port 8080.
  • DataSourceAutoConfiguration: cannot make a working connection. A DataSource is the object that connects to a database. The JPA starter puts the DataSource type on the classpath, so Boot considers this recipe. But there is no driver (the library that talks to one kind of database). There are no connection settings either. So Boot has no idea which database to connect to.
  • HibernateJpaAutoConfiguration: needs a DataSource that does not exist. JPA is on the classpath, so this recipe is a serious candidate. But it needs a working database connection.

2. Why it fails, instead of starting without a database. Asking for JPA clearly says what you want. JPA exists only to talk to a database. Boot takes that seriously. The other choice would be to start an app whose whole data layer is quietly missing. Then the failure would only show up much later, at the first request that touches data. Failing at startup is kinder. And the error message says exactly what is wrong:

***************************
APPLICATION FAILED TO START
***************************

Description:

Failed to configure a DataSource: 'url' attribute is not specified and no
embedded datasource could be configured.

Reason: Failed to determine a suitable driver class

Action:

Consider the following:
        If you want an embedded database (H2, HSQL or Derby), please put it
        on the classpath.
        If you have database settings to be loaded from a particular profile
        you may need to activate it.

See how much better that is than the ClassNotFoundException in section 4. It states the problem, the reason, and what you can do. The "Action:" part comes from Boot's "failure analyser". That is a part of Boot that turns a crash into a plain explanation. It is one of the most underrated parts of the framework.

3. Two one-line fixes:

  • Add an in-memory database driver (the H2 dependency). An in-memory database lives only in the program's memory. This is right when you just want the app running, early in development or for tests. Boot then sets up an in-memory database for you, with no settings at all. Our course does exactly this in Lesson 22.
  • Add a real driver plus connection settings. For example, PostgreSQL, with an address, a username and a password. This is right when the app really needs a real database. We get there in Lesson 35.

There is a third option worth knowing. Maybe they added spring-boot-starter-data-jpa by mistake, and do not want a database at all. Then the right fix is to remove that dependency. Removing a clue works just as well as adding one. The rule engine responds to both.

4. The command:

mvn spring-boot:run -Dspring-boot.run.arguments=--debug

This prints Boot's condition report. It lists every recipe under one of two headings. Positive matches shows the recipes that passed, with their conditions. Negative matches shows the ones that failed, with the exact condition that failed. The report is long. It is also the best answer to "why on earth is it doing that?". It turns a hidden decision into text you can read.

11Quick Recap

  • Spring Boot removes repeated setup work: installed servers, XML files and copying steps. Before 2014, every Java web project typed this out from scratch.
  • Spring Boot does not replace Spring Framework. It is a setup layer on top. The Framework does the real work; Boot makes sure it is already set up.
  • The embedded server turns the old setup inside out. Tomcat is now a library inside your one runnable file, not a program you install.
  • Auto-configuration is a rule engine, not magic. Boot collects about a hundred recipes, checks each one's conditions, and uses only the ones that pass.
  • You can always change Boot's defaults. @ConditionalOnMissingBean makes Boot step aside the moment you define something yourself.
