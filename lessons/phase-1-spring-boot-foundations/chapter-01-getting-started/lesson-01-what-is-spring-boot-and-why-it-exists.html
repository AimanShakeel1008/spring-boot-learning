What Is Spring Boot and Why It Exists

Three eras of Java web development, the specific pain each one left behind, and how Spring Boot's famous "magic" actually works — taken apart until no magic is left.

Files created: none — this is a concept lesson (the project is scaffolded in Lesson 02) · Prerequisites: Lesson 00 · Pinned: Spring Boot 4.1.1 on Spring Framework 7 · Java 21

1The Problem

It is 2004. You have been asked to make a Java program answer a web request — something visits a web address, your Java code runs, a page comes back. That is the whole requirement. Here is what your day actually looks like.

First, your program cannot receive web requests, because nothing in Java listens on a network by itself. You need a server: a separate, long-running program whose entire job is to sit waiting for requests and hand them to your code. So you download one — Apache Tomcat — and install it as its own application on the machine, with its own folders, its own configuration files, its own start and stop scripts. It is not part of your project. It is a second piece of software your project must be fed into.

Next you write your Java class. Then you write an XML file called web.xml telling the server which web addresses map to which classes. Then you package your compiled code into a WAR file — a zip in a particular layout the server understands. Then you copy that WAR into Tomcat's webapps folder. Then you restart Tomcat. Then you read a log file to find out whether any of it worked. Change one line of Java, and you do the package-copy-restart-read dance again.

Now fast-forward. The Spring Framework arrives and fixes something genuinely important about how objects are created and connected — we will spend all of Chapter 2 on that idea, because it is the best idea in this entire ecosystem. But it arrives configured in XML. By 2010 a normal project has several hundred lines of XML describing which classes exist, how they connect, which database to use, how transactions behave, how web addresses are routed. None of it is your product. All of it must be right before anything runs at all.

And here is the failure that really hurt. A new developer joins. They spend their first three days not writing features but installing the right Tomcat, matching versions, copying XML from a colleague, and hunting a startup error that turns out to be a misspelled class name buried on line 213 of a configuration file. Meanwhile a project down the hall has slightly different XML, a slightly different Tomcat, and code that mysteriously will not run on your machine. The phrase "but it works on my machine" was not a joke. It was the normal state of affairs.

Every one of those problems is setup — plumbing that is identical in almost every Java web application ever written, retyped from scratch by every team, every time. Spring Boot exists because somebody finally asked the obvious question: if nearly everyone configures this the same way, why is everyone still typing it out?

2Real World Analogy

Think about the difference between renting an empty apartment and checking into a hotel room.

The empty apartment gives you total freedom. Any furniture, any layout, any appliance. It is genuinely more powerful than a hotel room — you can do things there you could never do in a hotel. But on your first night there is no bed, no kettle, no towels, and no sleep. Before you can do the thing you came to do, you must make several hundred decisions you do not care about.

The hotel room has already made those decisions for you. The bed is made, the kettle is filled, the wifi works. Somebody looked at what almost every guest wants and set it up in advance. Crucially, it is not a cage: you can move the chair, ignore the kettle, bring your own pillow. The defaults are a starting point, not a restriction.

In the analogyIn our world
The empty apartmentSpring Framework alone — enormously capable, configures nothing for you
The furnished hotel roomSpring Boot — the same building, with sensible choices already made
"Most guests want a bed here"Opinionated defaults — the common setup, pre-applied
Moving the chair yourselfOverriding a default — always allowed, and Boot steps aside when you do
The room has a kettle only if it is a tea-drinking countryConditional configuration — Boot sets up a thing only if signs suggest you need it
The building itself: walls, plumbing, electricitySpring Framework, still underneath, doing the actual work

Hold on to that last row, because it is the single most misunderstood thing about Spring Boot. The hotel room is not an alternative to the building. It is the building, furnished.

3The Concept Explained

3.1 First, what is a framework?

In Lesson 00 we defined a library: pre-written code you call. You are in charge; you decide when to call it.

A framework reverses that relationship. You do not call the framework; the framework runs, and calls your code at the moments it decides are right. You write the pieces; it owns the sequence.

A concrete example. With a library you write: "open the file, read it, close it." With a framework you write a class that says "when a web request arrives at /products, here is what to do" — and then you never call that method. Something else does, whenever a request happens.

An everyday version: a library is a recipe book you consult when you choose. A framework is a job in a working kitchen, where the head chef calls out orders and you cook what you are told, when you are told. You still do the cooking. You do not control the timing.

This reversal has a name — the Hollywood Principle, "don't call us, we'll call you" — and it is so central to Spring that Chapter 2 is devoted entirely to it. For now, one sentence is enough: a framework is in charge, and your code fills in the parts it asks for.

3.2 What a server and a servlet actually are

A server, in our sense, is simply a program that keeps running and waits for requests to arrive over the network. Not a machine in a data centre — a program. It occupies a numbered door on your computer called a port, so that many programs can share one network connection without confusion.

HTTP is the agreed message format for these conversations: a request ("give me the product list") and a response (a status such as 200 OK, plus data). That is all we need today — Lesson 14 is devoted entirely to HTTP and goes deep.

Java's standard way of writing code that handles an HTTP request is called a servlet — a class with a method that receives a request object and fills in a response object. Servlets cannot run alone; they need a program to host them, receive the raw network traffic, and call them at the right moment. That host is a servlet container, and Tomcat is the most common one.

So the old stack, bottom to top, was: your servlet classes, hosted by Tomcat, installed separately on the machine. Remember that phrase — installed separately. It is about to become the crux of the whole lesson.

3.3 Three eras, and what each one fixed

EraWhat it gave youWhat it still made you do
Raw servlets
(late 1990s)		 A standard way for Java to answer HTTP at all Install and manage a server yourself; describe every route in XML; create and connect every object by hand; package and redeploy for each change

Notice the shape of that progression. Each era solved a real problem and left a smaller one behind. Spring Boot is not a rejection of Spring Framework — it is the removal of the last big tax that Spring Framework charged, which was configuration.

3.4 So what is Spring Boot?

Spring Boot is not a new framework, and it does not replace Spring Framework. It is a layer on top of it that does four things:

  1. Starters. A starter is one dependency that pulls in a whole compatible set of libraries for one job. Ask for spring-boot-starter-webmvc and you get the web framework, a JSON converter, validation and an embedded server — versions already known to work together. This is the direct cure for the JAR-hell problem from Lesson 00.
  2. Auto-configuration. At startup, Boot looks at what is on your classpath and configures the obvious things for you. Section 3.7 pulls this apart completely.
  3. An embedded server. Tomcat is no longer a program you install; it is a library inside your application. Section 3.5.
  4. Production plumbing. Health checks, metrics, sensible logging, externalised configuration — the things every real system needs, ready to switch on. We meet these properly in Lesson 78 and Chapter 22.

3.5 The flip that changed everything: the embedded server

This is the single most visible difference, and it is worth staring at.

The consequences are larger than they first appear:

  • One artifact. Your whole application is a single runnable file. Nothing has to be installed on the target machine except Java itself.
  • Version certainty. The Tomcat you tested against is literally the Tomcat that runs in production, because it is inside the file. "Works on my machine" loses most of its power.
  • Ordinary running. Starting your app is just running a Java program. No deploy step, no copy, no restart-and-read-the-log.
  • Containers become trivial. In Phase 3 we put this app in a container. Because the server is inside the file, that container needs nothing but Java and your jar. An entire category of deployment complexity evaporates.

3.6 "Opinionated defaults" — what the opinion actually is

People describe Spring Boot as opinionated, which sounds like marketing until you pin it down. An opinion here is a concrete claim of the form: "most applications that have X on the classpath want Y configured, so we will configure Y unless told otherwise."

Worked example. You add the web starter. Boot's opinions then include: run an embedded Tomcat; listen on port 8080; convert returned objects to JSON; show a default error page; serve static files from /static. Not one of those is a law of nature. They are defaults chosen because they are what most people want most of the time.

The related slogan is convention over configuration: rather than making you state something explicitly, the tool assumes the common convention and lets you override when you differ. If port 8080 is wrong for you, one line changes it:

# src/main/resources/application.yml
server:
  port: 9000

And here is the part that turns opinionated from frightening into useful: Boot backs off the moment you take over. If you define your own database connection, Boot's automatic one steps aside silently. This is not politeness, it is a rule written into the machinery — the condition @ConditionalOnMissingBean, which we see working in the next section. Your explicit choice always beats Boot's default.

Check yourself: does "opinionated" mean Spring Boot is less flexible than Spring Framework?

No. Anything you can do in Spring Framework you can still do in Spring Boot, because Boot is Spring Framework with a configuration layer on top. What changes is the starting point, not the ceiling. Boot gives you a working application before you have made any decisions, and then gets out of the way for every decision you actually want to make. You trade "nothing is decided" for "the usual things are decided, revisably" — and you can revise every one of them.

3.7 How auto-configuration actually works

This is where people say "it's magic." It is not, and treating it as magic is how you end up unable to debug it. Here is the real mechanism, in order.

Step 1 — the classpath is a list of evidence. The classpath is simply everything available to your running program: your classes plus every library Maven downloaded. Boot treats it as evidence about intent. A web framework on the classpath is strong evidence you want to serve web requests.

Step 2 — every starter carries recipes. Inside the jars is a plain text file listing auto-configuration classes. At startup Boot reads all of those files, from every jar, and assembles one long list of candidate configurations — over a hundred of them. Think of it as a recipe book contributed to by every library you added.

Step 3 — each recipe carries conditions. A candidate is not applied just because it was found. Each is annotated with conditions that must all hold. The common ones read almost like English:

ConditionMeans
@ConditionalOnClassonly if this class is on the classpath (i.e. you added that library)
@ConditionalOnMissingBeanonly if you have not already defined one of these yourself
@ConditionalOnPropertyonly if a named setting has a particular value
@ConditionalOnBeanonly if some other object was already created

An annotation — anything written with an at-sign — is a marker attached to code that other code can read. These conditions are markers Spring Boot reads at startup and evaluates.

Step 4 — evaluate, then apply the survivors. Boot walks the list, checks each recipe's conditions against reality, discards the ones that fail, and applies the rest. That is the entire trick. Over a hundred candidates, a few dozen survivors, and the survivors are exactly the ones your dependencies imply.

This is why adding one line to pom.xml can produce a running web server, and — just as importantly — why removing it makes the web server silently vanish. Nothing random is happening. A rule engine is running over a list of conditions.

Toggle what is on the classpath, then start the application and watch the rule engine decide. This is the real logic, simplified: each recipe is checked against conditions, and only the survivors configure anything.

Press “Start the application”.

This is a model of the mechanism, not the real thing — four recipes instead of a hundred and something. The real authority is your own machine: from Lesson 02 onwards you can run mvn spring-boot:run --debug and read Spring Boot's actual condition report, which prints exactly this decision for every candidate, under the headings “Positive matches” and “Negative matches”.

Check yourself: in the simulation, why does turning on “I defined my own DataSource bean” change the verdict from MATCHED to BACKED OFF rather than to an error?

Because of @ConditionalOnMissingBean. That condition says "apply this recipe only if the application has not already provided one of these itself." When you define your own, the condition fails, the recipe is skipped, and your bean is the one in use. Two competing database connections would be an error; Boot avoids that by always yielding to you. This is the mechanical form of the promise in section 3.6 — your explicit choice beats the default, and it is enforced by a condition rather than by good manners.

3.8 Spring Boot versus Spring Framework — the honest difference

The question comes up constantly, usually phrased as if you must choose. You do not. They are layers, not alternatives.

Spring FrameworkSpring Boot
What it isThe actual framework — the container, dependency injection, web layer, transactionsA configuration layer on top of it
Gives youCapabilityCapability already switched on
ServerYou install and manage oneBundled inside your application
ConfigurationYou write all of itWritten for you where it is predictable, overridable everywhere
Can you use it alone?Yes — many older systems doNot really; Boot without Framework is meaningless

The sharpest way to say it: Spring Framework does the work; Spring Boot makes sure it is already set up when your code starts running.

3.9 Where Spring Boot 4 sits, and what changed

We pin Spring Boot 4.1.1, which runs on Spring Framework 7. Two things about this generation matter even on day one.

First, the modularization. For a decade, all of Boot's auto-configuration recipes lived in a single jar called spring-boot-autoconfigure. In 2014 it was about 182 KiB. By Spring Boot 3.5 it had grown to roughly 2 MiB — every recipe for every technology Boot supports, shipped to every application whether it used Kafka or not. Boot 4 split it into small, focused modules, one per technology. Your application now carries only the recipes for things it actually uses, your editor stops suggesting classes from libraries you have never heard of, and Boot gets a clearer signal about what you are really doing.

That split is also the reason for a rename you are about to walk straight into.

Because the modules were renamed to match what they contain, several starters were renamed too. The first one you will meet is the web starter, in the very next lesson:

spring-boot-starter-web spring-boot-starter-webmvc

Why: the module behind it is now specifically about Spring Web MVC — the servlet-based web stack — as distinct from the reactive stack we study in Chapter 27. The old name did not say which one you were asking for; the new one does.

What this means for you: in our project, type spring-boot-starter-webmvc. When you find a tutorial saying spring-boot-starter-web — and nearly all of them do, because they were written before 2026 — that is not a mistake in the tutorial, it is the old name. Translate it and carry on. Existing projects migrating from 3.x can also use spring-boot-starter-classic, which keeps the old aggregated behaviour, but a new project should not.

Second, Spring Boot 3 is finished. The 3.x line reached open-source end of life on 30 June 2026 — no more free security fixes. That is why this course starts on 4.x even though most learning material has not caught up: learning the dead version would mean learning it twice.

Being able to explain the difference between Spring Boot and Spring Framework is one of the most common interview questions for Java roles, and "Boot is just Spring with less configuration" is the answer that gets you a follow-up you cannot answer. The strong version is the one in section 3.8: Boot is a configuration layer that depends on Framework, and its three mechanisms are starters, auto-configuration and the embedded server. If you can then describe @ConditionalOnMissingBean and why Boot backs off, you are visibly ahead of someone who has only followed tutorials.

4The Wrong Way

Wrong approach — configure the plumbing yourself, every time

Here is roughly what "serve one web address" required before Boot. First, a deployment descriptor telling the server that Spring should handle requests:

<!-- web.xml — and this is the SHORT version -->
<web-app>
  <servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
  </servlet>
  <servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
  </servlet-mapping>
</web-app>

Then a second XML file describing the Spring side — which packages to scan, how to resolve views, where static files live. Then, if you wanted a database, a third describing the connection, the transaction manager and the session factory. Then you built a WAR, copied it into Tomcat, and restarted.

What goes wrong: none of that XML is your product, yet all of it must be exactly right before anything runs. It is not type-checked — a misspelled class name is a string that looks fine until startup. And it is duplicated in every project in the company, drifting slightly apart as each team edits their copy.

If this were misconfigured, the output would be (a prediction):

SEVERE: Servlet [dispatcher] in web application [/store] threw load() exception
java.lang.ClassNotFoundException: org.springframework.web.servlet.DispatchersServlet
        at org.apache.catalina.loader.WebappClassLoaderBase.loadClass(...)
        at org.apache.catalina.core.StandardWrapper.loadServlet(...)
        ... 47 more

One transposed letter — DispatchersServlet — and the whole application fails to start, with a stack trace pointing at Tomcat's internals rather than at your typo. Now multiply that by three XML files and a new team member.

The other wrong way — fighting auto-configuration. A common reaction to "Boot configures things for me" is distrust: configure everything explicitly anyway, to stay in control. This gives you the worst of both — Boot's dependencies and complexity, plus all the hand-written configuration you were trying to avoid, plus subtle conflicts where your setup and Boot's disagree. If you do not want a default, override that one default. Do not pre-emptively override all of them.

5The Right Way

Correct approach — declare what you need, let the recipes fire

The entire equivalent in Spring Boot is one dependency and one class. Here is the class, with every line explained:

// The package this class belongs to — the folder structure of the project.
package com.ecommerce;

// Pulls in the two Spring Boot types used below, so we can refer to them by
// their short names instead of writing the full package every time.
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

// ONE annotation doing three jobs at once. It marks this class as the
// application's starting point, switches on auto-configuration (section 3.7),
// and tells Spring to look in this package and below for your own classes.
// Lesson 03 takes this annotation apart piece by piece.
@SpringBootApplication
public class EcommerceApplication {

    // The ordinary Java entry point. Nothing framework-specific about main itself:
    // this is the method the JVM calls when you run the program.
    public static void main(String[] args) {

        // Hand control to Spring Boot. This one call creates the container,
        // runs the auto-configuration rule engine, starts the embedded Tomcat,
        // and then blocks — keeping the program alive to serve requests.
        // We pass our own class so Boot knows where to start looking, and args
        // so settings typed on the command line reach the framework.
        SpringApplication.run(EcommerceApplication.class, args);
    }
}

Eleven meaningful lines. No XML, no server installation, no deployment descriptor, no packaging ritual.

Step by step: what happens when this runs

  1. The JVM calls main, exactly as it would for any Java program.
  2. SpringApplication.run takes over and creates the application context — the container that will hold and connect your objects. Chapter 2 is devoted to it.
  3. Boot reads the recipe lists from every jar on the classpath, producing a hundred-odd candidate auto-configurations.
  4. It evaluates each candidate's conditions against reality: what is on the classpath, what you have already defined, what your settings say.
  5. The survivors run. Because the web starter is present, one of them starts an embedded Tomcat on port 8080.
  6. Boot scans your package for your own classes and creates the ones it recognises.
  7. Startup finishes, and the program does not exit — Tomcat holds it open, waiting for requests.

7Gotchas and Common Mistakes

  • Thinking Spring Boot replaced Spring Framework. Extremely common, and it makes everything afterwards confusing — you start looking for "the Boot way" to do dependency injection, when dependency injection is a Framework feature that Boot merely switched on. Whenever you wonder which one a feature belongs to, ask: is this capability (Framework) or configuration (Boot)?
  • Treating auto-configuration as magic. The cost is not philosophical, it is practical: when something is configured in a way you did not expect, someone who thinks it is magic has nowhere to look. Someone who knows it is a conditions engine runs the app with --debug and reads the condition report, which lists every candidate and exactly why it matched or did not.
  • Overriding defaults pre-emptively. Configuring things explicitly "to be safe" produces conflicts between your configuration and Boot's, and those conflicts are much harder to debug than the defaults you were avoiding. Change a default when you have a reason, not in advance.
  • Assuming a starter means the feature is switched on. A starter puts libraries on the classpath; auto-configuration then decides what to do about them, and its conditions may not all pass. "I added the dependency and it still does not work" is nearly always a condition that failed — and the condition report will say which.
  • Copying Spring Boot 2 or 3 tutorials without translating. Most material you find predates Boot 4, and several names changed. spring-boot-starter-web is the one that will bite first. It is not that the tutorial is wrong; it is describing an earlier version. Every difference that matters gets a "Changed in Spring Boot 4" card in these lessons at the point it arises.

8Tradeoffs and When Not to Use This

Startup work is not free. Evaluating a hundred-odd candidate configurations at every startup costs time and memory. For a server that starts once and runs for weeks, this is irrelevant. For a short-lived process that must start instantly — a serverless function billed by the millisecond — it matters, and it is exactly what ahead-of-time processing and native compilation address (Lesson 144).

Convenience can become opacity. Boot configures things you did not write, which means when behaviour surprises you, the cause may be in a recipe you have never read. The mitigation is knowing the mechanism and the condition report — which is why section 3.7 refused to call it magic. This is a real cost, not an imaginary one, and it is the strongest argument the framework's critics make.

Dependency weight. One starter can pull in dozens of jars, some of which you will never use. That is a fair price for a working application in one line, but it means a Boot application is not small, and each jar is a thing that can carry a security vulnerability — which is why Lesson 124 automates dependency scanning.

When not to use Spring Boot. Writing a library for other developers to call? A library should not drag a framework along with it. Need startup measured in single milliseconds and memory in tens of megabytes? Look at a native image, or at a framework built for that shape like Quarkus. Building something genuinely tiny with one endpoint and no growth plans? Boot will work perfectly, but it is a lot of machinery for the job. Boot's sweet spot is applications that are real, long-running, and expected to grow — which is precisely the E-Commerce system we are building.

9Key Takeaways

  • Spring Boot exists to remove the repeated setup work — servers, XML configuration, deployment rituals — that every Java web project used to retype from scratch, and that caused most of the "works on my machine" failures of the pre-2014 era.
  • Spring Boot is not a replacement for Spring Framework but a configuration layer built on top of it, which is why Spring Framework does the actual work while Spring Boot simply ensures it is already set up when your code starts.
  • The embedded server flips the old arrangement inside out: instead of your application being deployed into a separately installed Tomcat, Tomcat becomes an ordinary library inside your single runnable file, which is what later makes containers and cloud deployment straightforward.
  • Auto-configuration is not magic but a rule engine: Boot gathers a hundred-odd candidate recipes from the jars on your classpath, evaluates each one's conditions against what is actually present, and applies only the survivors.
  • Opinionated defaults are always revisable, and Boot enforces that mechanically with conditions like @ConditionalOnMissingBean, which make it step aside automatically the moment you define something yourself.

10Challenge

Reason this one through on paper. A colleague shows you a Spring Boot 4 project whose pom.xml contains exactly these dependencies:

spring-boot-starter-webmvc
spring-boot-starter-data-jpa

…and no database driver of any kind. Their application fails to start.

  1. Walk through what the auto-configuration rule engine decides for the web recipe, the datasource recipe, and the JPA recipe.
  2. Why does the application fail, rather than simply starting without a database?
  3. Give two different one-line fixes, and say when each is the right choice.
  4. What single command would let them see the engine's reasoning for themselves?
Click to reveal the answer

1. What the engine decides:

  • WebMvcAutoConfiguration — MATCHED. @ConditionalOnClass(DispatcherServlet) passes because the webmvc starter put it on the classpath. An embedded Tomcat is configured on port 8080.
  • DataSourceAutoConfiguration — cannot produce a working connection. The JPA starter does bring the DataSource type itself onto the classpath, so the recipe is considered, but there is no driver and no connection settings, so Boot has no idea what database to connect to.
  • HibernateJpaAutoConfiguration — wants a DataSource that does not exist. JPA is on the classpath, so this recipe is a serious candidate, and it depends on a usable datasource.

2. Why it fails rather than starting without a database. Because asking for JPA is an unambiguous statement of intent: JPA exists only to talk to a database. Boot takes that seriously rather than quietly starting an application whose entire persistence layer is silently missing — a failure that would otherwise surface much later, at the first request that touches data. Failing at startup is the kinder choice, and the error message says so directly:

***************************
APPLICATION FAILED TO START
***************************

Description:

Failed to configure a DataSource: 'url' attribute is not specified and no
embedded datasource could be configured.

Reason: Failed to determine a suitable driver class

Action:

Consider the following:
        If you want an embedded database (H2, HSQL or Derby), please put it
        on the classpath.
        If you have database settings to be loaded from a particular profile
        you may need to activate it.

Note how much better that is than the ClassNotFoundException in section 4: it states the problem, the reason, and the available actions. That "Action:" section is Boot's failure analyser, and it is one of the genuinely underrated parts of the framework.

3. Two one-line fixes:

  • Add an in-memory database driver (the H2 dependency). Right when you just want the application running — for early development, or for tests. Boot will then configure an in-memory database for you with no settings at all. This is exactly the path our course takes in Lesson 22.
  • Add a real driver plus connection settings (e.g. PostgreSQL, with a URL, username and password). Right when the application genuinely needs to talk to a real database, which is where we arrive in Lesson 35.

There is a third option worth knowing: if they added spring-boot-starter-data-jpa by accident and do not want a database at all, the correct fix is to remove the dependency. Removing evidence is as valid as adding it — the rule engine responds to both.

4. The command:

mvn spring-boot:run --debug

This prints Boot's condition report: every candidate auto-configuration under Positive matches (with the conditions that passed) and Negative matches (with the exact condition that failed). It is long, and it is the single best answer to "why on earth is it doing that?" — because it turns the invisible decision into text you can read.
