Chapter 1 Summary — Getting Started

Three lessons, one running application. Why Spring Boot exists, what is actually on disk, and what happens between typing a command and getting a 404 back — pulled together into one picture.

Covers: Lesson 01 · Lesson 02 · Lesson 03 · Pinned: Spring Boot 4.1.1 · Java 21 · Maven 3.9.16

1What We Built

At the start of this chapter, phase-1-monolith/ was an empty folder. Now it holds a real Spring Boot 4 application. It builds into one runnable file, starts an embedded web server, answers HTTP requests with a correct 404, shuts down cleanly, and has eleven automatic checks guarding how it starts. It has no features yet. That is deliberate: every piece of plumbing is now understood before any feature leans on it.

3The Story So Far

Lesson 01 was about why. Before Spring Boot, a Java web application was a pile of hand-written setup: install a server, write configuration for every library, copy a WAR file in, and hope the versions agreed. Spring Framework solved the hard part, a container that creates and connects your objects. But it still left you to set it all up by hand. Spring Boot's answer was a rule engine. Every library brings recipes with conditions, Boot reads the classpath as evidence of what you want, and the recipes whose conditions pass do the setup for you. The server moved inside the application. Then Spring Boot 4 split the one giant auto-configuration jar into a module per technology, which is why half the names in older tutorials no longer match ours.

Lesson 02 was about what is actually on disk. We generated the project and read every line of it. Maven turns three coordinates into a URL, follows each dependency's own dependencies down until two starters become about forty jars, and lets the parent POM's BOM pin every version to a tested set. A starter turned out to be an almost empty jar: a shopping list, not a library. The build lifecycle runs its phases in order, which is why mvn package also runs the tests. The executable jar works only because Boot ships its own launcher that can read jars nested inside a jar. We ended with java -jar and a 404, and every step of that chain could be named.

Lesson 03 opened the last black box: the two lines in EcommerceApplication. @SpringBootApplication is a bundle of three annotations. One makes the main class the primary configuration class and a bean. One switches on the Lesson 01 recipe engine by reading every AutoConfiguration.imports file. One draws the scan boundary around the main class's package. SpringApplication.run builds the ApplicationContext, the brain that holds every bean. During refresh it builds Tomcat from an auto-configured factory bean, and then it returns. The program stays alive only because Tomcat's own non-daemon thread does. We also corrected a claim Lesson 02 had made. Then we turned every one of these facts into a test, so the machine checks them, not your memory.

6Concepts That Will Come Back

  • The bean and the ApplicationContext. Lesson 03 used just enough of both to move on. Chapter 2 is entirely about them: how the context creates beans, connects them by dependency injection, scopes them, and runs their lifecycle.
  • The scan boundary. From Lesson 05, every @Service and @RestController you write lives or dies by it. It returns at full strength in Phase 2, when shared code sits in a sibling package tree.
  • @ConditionalOnMissingBean and "your configuration first, recipes last". This is how every customisation in the course works, from defining your own bean in Lesson 07 to writing your own starter and auto-configuration in Chapter 29.
  • The Environment and "the command line beats application.yml". Chapter 6 spells out the full priority order, and profiles. Every --server.port=0 in our tests is already using it.
  • The fat jar. It is the thing Chapter 24 puts into a Docker image and Chapter 25's pipeline builds on every push. "One file, no server to install" is why that is easy.

8Chapter Boss Challenge

The scenario: the Friday pull request

A teammate opens a pull request titled "Tidy up the project". It makes four changes:

  1. Moves the main class into a new package, com.ecommerce.boot, using the IDE's move refactoring. The IDE updates every import in the tests, so everything compiles.
  2. Adds one line after SpringApplication.run(...) in main: 
    System.out.println("Shop ready at http://localhost:8080");
  3. Adds an exclusion to application.yml, copied from a 2023 blog post titled "Take control of your embedded server": 
    spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.web.servlet.ServletWebServerFactoryAutoConfiguration
  4. Deletes the spring-boot-maven-plugin block from pom.xml, with the comment "mvn compile works fine without it".

What to work out

Reason through each one on paper first, using only this chapter.

  1. The teammate presses the IDE's Run button on main. Does the application start? Is Tomcat running? Does the new line print, and when?
  2. mvn test: how many of the 11 tests pass, which ones fail, and with what message? Does "Shop ready…" appear anywhere in the test output?
  3. They run mvn clean package -DskipTests, then java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. What happens?
  4. A reviewer says: "That exclusion uses a 3.x name. Fix it to the correct Boot 4 class for the Tomcat recipe." If the teammate does exactly that, what happens at startup, and why?
  5. Write the review: for each of the four changes, say keep, change or revert, and why. Then give the commands that prove the project is healthy again, and the output you expect.
Click to reveal the answer

a. Run from the IDE: it starts, Tomcat runs, and the line prints once. The move does not affect auto-configuration or Tomcat at all. The exclusion names a class that does not exist in Boot 4, because the core spring-boot-autoconfigure jar no longer contains any web-server recipe. Boot's exclusion check only complains about a class that is on the classpath but is not a recipe. A name that is not on the classpath at all is silently ignored, so the exclusion does nothing. TomcatServletWebServerAutoConfiguration still matches and Tomcat starts on 8080. Because run returns once startup is complete, "Shop ready at http://localhost:8080" prints once, straight after Started EcommerceApplication in … seconds. The application then keeps running on Tomcat's non-daemon container-0 thread. The logger column for our class now reads com.ecommerce.boot.EcommerceApplication.

b. mvn test: 10 pass, 1 fails, BUILD FAILURE.

  • theApplicationPackageIsTheMainClassPackage fails. AssertJ reports that it expected exactly ["com.ecommerce"] and found ["com.ecommerce.boot"]. This is the guard Lesson 03 added for exactly this change.
  • contextLoads() passes. @SpringBootTest searches from com.ecommerce downwards first and finds the one @SpringBootConfiguration in com.ecommerce.boot.
  • The three anatomy tests pass, because the annotation is unchanged. The other three context tests pass, because the bean name and Tomcat do not depend on the package. The three demos pass too. Two of them pass their own spring.autoconfigure.exclude on the command line, which replaces the one in application.yml because the command line outranks it. The third does not set an exclusion, so the YAML one applies, and it does nothing.
  • "Shop ready…" never appears in the test output. No test calls main. They all call SpringApplication.run directly, so the line after it in main never runs. It is a small reminder that tests exercise exactly what they call, and nothing else.
[ERROR] Failures:

    ["com.ecommerce.boot"]

A prediction: AssertJ's exact layout may differ slightly; the test name, the two lists, and Failures: 1 will not.

c. java -jar: no main manifest attribute, in target/ecommerce-0.0.1-SNAPSHOT.jar. -DskipTests got past the failing test, and that alone should worry a reviewer: the jar is now an artifact with no evidence behind it. Without the spring-boot-maven-plugin there is no repackage step. Maven produces a plain jar containing only our own classes, with no dependency jars inside and no Main-Class line in its manifest. "mvn compile works fine without it" was true, but compiling was never the plugin's job.

d. The "fixed" exclusion breaks startup. With org.springframework.boot.tomcat.autoconfigure.servlet.TomcatServletWebServerAutoConfiguration excluded, the one recipe that defines a ServletWebServerFactory is removed before its conditions are checked. Spring MVC is still on the classpath, so this is still a servlet web application. During onRefresh the context asks for exactly one factory, finds zero, and gives up:

***************************
APPLICATION FAILED TO START
***************************

Description:

Web application could not be started as there was no org.springframework.boot.web.server.servlet.ServletWebServerFactory
bean defined in the context.

That is exactly what our demo test excludingTheTomcatRecipeMeansTheWebApplicationCannotStart asserts. The blog post's idea of "taking control of the embedded server" never meant excluding the recipe. It meant defining your own factory bean, so the recipe backs off through @ConditionalOnMissingBean. That is a Lesson 07 skill. The two versions of this exclusion fail in opposite ways: the old name silently does nothing, and the correct name breaks startup loudly.

e. The review.

ChangeVerdictWhy
Main class to com.ecommerce.bootRevertIt moves the scan boundary, so every future class in com.ecommerce.product, .order and so on becomes invisible. The failing test is right.
println after runRevertHarmless, but startup work does not belong in main. It never runs in tests, and Lesson 10 shows the proper tool. Boot already logs the port.
3.x exclusion in application.ymlRevert (do not "fix")As written it does nothing and misleads every reader. Corrected, it breaks the application. Neither is wanted.
Deleting spring-boot-maven-pluginRevertWithout it there is no executable jar, so nothing can be deployed.
