1What We Built

At the start of this chapter, phase-1-monolith/ was an empty folder. Now it holds a real Spring Boot 4 app. Here is what it can do:

  • It builds into one runnable file.
  • It starts an embedded web server (a server that lives inside the app).
  • It answers HTTP requests with a correct 404.
  • It shuts down cleanly.
  • Eleven automatic tests check how it starts.

It has no features yet. That is on purpose. You now understand every piece of the plumbing before any feature depends on it.

3The Story So Far

3.1 Lesson 01: why Spring Boot exists

Lesson 01 was about why. Before Spring Boot, a Java web app was a pile of hand-written setup. You installed a server. You wrote setup files for every library. You copied a WAR file in, and hoped the versions agreed.

Spring Framework solved the hard part: a container that creates and connects your objects. But you still had to set it all up by hand.

Spring Boot's answer was a rule engine. Every library brings recipes with conditions. Boot reads the classpath (the list of code your program can use) as a set of clues about what you want. The recipes whose conditions pass do the setup for you. The server moved inside the app.

Then Spring Boot 4 split the one giant auto-configuration JAR into one module per technology. That is why so many names in older tutorials no longer match ours.

3.2 Lesson 02: what is actually on disk

Lesson 02 was about what is actually on disk. We created the project and read every line of it. Here is what we learned:

  • Maven turns three coordinates into a web address.
  • It follows each dependency's own dependencies, all the way down. So two starters become about forty JARs.
  • The parent POM's BOM pins every version to a tested set.
  • A starter turned out to be an empty JAR: a shopping list, not a library.
  • The build lifecycle runs its phases in order. That is why mvn package also runs the tests.
  • The runnable JAR only works because Boot brings its own launcher, which can read JARs inside a JAR.

We ended with java -jar and a 404, and we could name every step of that chain.

3.3 Lesson 03: how it starts

Lesson 03 opened the last mystery: the two lines in EcommerceApplication. @SpringBootApplication is a bundle of three annotations:

  • One makes the main class the main configuration class, and a bean.
  • One switches on the Lesson 01 recipe engine, by reading every AutoConfiguration.imports file.
  • One draws the search boundary around the main class's package.

SpringApplication.run builds the ApplicationContext, the brain that holds every bean. During refresh, it builds Tomcat from an auto-configured factory bean. Then it returns. The program stays alive only because Tomcat's own non-daemon thread does.

We also fixed a wrong claim from Lesson 02. Then we turned every one of these facts into a test. Now the machine checks them, not your memory.

6Concepts That Will Come Back

  • The bean and the ApplicationContext. Lesson 03 used just enough of both to move on. Chapter 2 is entirely about them. It covers how the context creates beans and connects them by dependency injection. It also covers bean scope: how many copies of a bean exist, and for how long. And it follows each bean's life, from creation to destruction.
  • The scan boundary. From Lesson 05, every @Service and @RestController you write lives or dies by it. It returns at full strength in Phase 2, when shared code sits in a package tree next to yours, not inside it.
  • @ConditionalOnMissingBean and "your configuration first, recipes last". Every change to Boot's defaults in this course works this way. That runs from defining your own bean in Lesson 07, to writing your own starter and auto-configuration in Chapter 29.
  • The Environment and "the command line beats application.yml". Chapter 6 spells out the full priority order, and profiles. Every --server.port=0 in our tests already uses it.
  • The fat JAR. Chapter 24 puts it into a Docker image (the saved template a container starts from). Chapter 25 builds a pipeline: an automatic line that builds, tests and ships the app on every push. "One file, no server to install" is why both are easy.

8Chapter Boss Challenge

The scenario: the Friday pull request

A teammate opens a pull request titled "Tidy up the project". A pull request is a set of proposed changes. A teammate asks the others to review them before they join the main code. This one makes four changes:

  1. Moves the main class into a new package, com.ecommerce.boot, using the IDE's move refactoring. The IDE updates every import in the tests, so everything compiles.
  2. Adds one line after SpringApplication.run(...) in main: 
    System.out.println("Shop ready at http://localhost:8080");
  3. Adds an exclusion to application.yml, copied from a 2023 blog post titled "Take control of your embedded server": 
    spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.web.servlet.ServletWebServerFactoryAutoConfiguration
  4. Deletes the spring-boot-maven-plugin block from pom.xml, with the comment "mvn compile works fine without it".

What to work out

Reason through each one on paper first, using only this chapter.

  1. The teammate presses the IDE's Run button on main. Does the application start? Is Tomcat running? Does the new line print, and when?
  2. mvn test: how many of the 11 tests pass, which ones fail, and with what message? Does "Shop ready…" appear anywhere in the test output?
  3. They run mvn clean package -DskipTests, then java -jar target/ecommerce-0.0.1-SNAPSHOT.jar. What happens?
  4. A reviewer says: "That exclusion uses a 3.x name. Fix it to the correct Boot 4 class for the Tomcat recipe." If the teammate does exactly that, what happens at startup, and why?
  5. Write the review: for each of the four changes, say keep, change or revert, and why. Then give the commands that prove the project is healthy again, and the output you expect.
Click to reveal the answer

a. Run from the IDE: it starts, Tomcat runs, and the line prints once. Here is why, step by step:

  1. The move does not affect auto-configuration or Tomcat at all.
  2. The exclusion names a class that does not exist in Boot 4. The core spring-boot-autoconfigure JAR no longer holds any web-server recipe.
  3. Boot's exclusion check only complains about a class that is on the classpath but is not a recipe. It quietly ignores a name that is not on the classpath at all. So the exclusion does nothing.
  4. TomcatServletWebServerAutoConfiguration still matches, and Tomcat starts on 8080.
  5. run returns once startup is complete. So "Shop ready at http://localhost:8080" prints once, straight after Started EcommerceApplication in … seconds.
  6. The app then keeps running on Tomcat's non-daemon container-0 thread.

The logger column for our class now reads com.ecommerce.boot.EcommerceApplication.

b. mvn test: 10 pass, 1 fails, BUILD FAILURE.

  • theApplicationPackageIsTheMainClassPackage fails. AssertJ reports that it expected exactly ["com.ecommerce"] and found ["com.ecommerce.boot"]. This is the guard Lesson 03 added for exactly this change.
  • contextLoads() passes. @SpringBootTest searches from com.ecommerce downwards first and finds the one @SpringBootConfiguration in com.ecommerce.boot.
  • The three anatomy tests pass, because the annotation is unchanged. The other three context tests pass, because the bean name and Tomcat do not depend on the package. The three demos pass too. Two of them set their own spring.autoconfigure.exclude on the command line. The command line beats application.yml, so theirs replaces the one in the YAML file. The third sets no exclusion, so the YAML one applies, and it does nothing.
  • "Shop ready…" never appears in the test output. No test calls main. They all call SpringApplication.run directly. So the line after it in main never runs. It is a small reminder: tests only run exactly what they call, and nothing else.

A prediction. AssertJ's exact layout may differ a little. The test name, the two lists, and Failures: 1 will not.

c. java -jar: no main manifest attribute, in target/ecommerce-0.0.1-SNAPSHOT.jar. -DskipTests got past the failing test. That alone should worry a reviewer: the JAR now has no proof behind it.

Without the spring-boot-maven-plugin, there is no repackage step. Maven makes a plain JAR that holds only our own classes. It has no dependency JARs inside. Its manifest (the small file that tells Java which class to start) has no Main-Class line. "mvn compile works fine without it" was true. But compiling was never the plugin's job.

d. The "fixed" exclusion breaks startup. Follow the chain:

  1. Now the exclusion names org.springframework.boot.tomcat.autoconfigure.servlet.TomcatServletWebServerAutoConfiguration.
  2. That is the one recipe that defines a ServletWebServerFactory. Boot removes it before it even checks its conditions.
  3. Spring MVC is still on the classpath, so this is still a servlet web app.
  4. During onRefresh, the context asks for exactly one factory, finds zero, and gives up:
***************************
APPLICATION FAILED TO START
***************************

Description:

Web application could not be started as there was no org.springframework.boot.web.server.servlet.ServletWebServerFactory
bean defined in the context.

That is exactly what our demo test excludingTheTomcatRecipeMeansTheWebApplicationCannotStart checks. "Taking control of the embedded server", as the blog post put it, never meant excluding the recipe. It meant defining your own factory bean, so the recipe steps back through @ConditionalOnMissingBean. That is a Lesson 07 skill. The two versions of this exclusion fail in opposite ways. The old name quietly does nothing. The correct name breaks startup loudly.

e. The review.

ChangeVerdictWhy
Main class to com.ecommerce.bootRevertIt moves the scan boundary, so every future class in com.ecommerce.product, .order and so on becomes invisible. The failing test is right.
println after runRevertHarmless, but startup work does not belong in main. It never runs in tests, and Lesson 10 shows the proper tool. Boot already logs the port.

9Key Words

The most important words from Chapter 1, with a one-line meaning. Each lesson's own Key Words section has the full list.

Framework
Ready-made code that runs your app and calls your code when it is needed.
Embedded server
A web server that lives inside your app as a library, not installed separately.
Classpath
The full list of code a running Java program can use.
Auto-configuration
Boot setting things up for you, using recipes whose conditions pass.
@ConditionalOnMissingBean
"Only if the app has not made one of these already." It lets your choice win.
Maven
The build tool: it fetches libraries, compiles, tests and packages the project.
Starter
One dependency that brings a matching set of libraries for one job.
BOM
Bill of Materials: a list that pins tested versions for a whole set of libraries.
Build lifecycle
Maven's fixed list of phases. Naming one runs all the ones before it.
Fat JAR
One JAR that holds your code and every library it needs.
Bean
An object that Spring creates, keeps and hands out.
Meta-annotation
An annotation placed on another annotation, so using one brings the other.
Component scan
Spring's search for your classes, in the main class's package and below.
ApplicationContext
Spring's container: it holds every bean, owns the settings, and starts and stops everything.
Non-daemon thread
A line of work the JVM must wait for. Tomcat's keeps the app alive.
Graceful shutdown
Stop taking new requests, finish the current ones, then stop.
Pull request
A set of proposed changes that teammates review before they join the main code.
Pipeline
An automatic line that builds, tests and ships the app on every push.

10Quick Recap

  • Spring Boot removes repeated setup. It is a layer on top of Spring Framework, which does the real work.
  • Auto-configuration is a rule engine: recipes with conditions, checked against the classpath, stepping aside when you define your own bean.
  • Maven fetches about forty JARs from two starters, and the parent's BOM picks versions that are tested together.
  • @SpringBootApplication is three annotations in one. Component scanning only covers the main class's package and below.
  • SpringApplication.run builds the ApplicationContext, starts Tomcat, and returns. Tomcat's own thread keeps the app running.
