The Main Application Class

One annotation, taken apart into the three it stands for; the ApplicationContext, the object that runs everything; the embedded Tomcat and where it really comes from; and why your program keeps running after main() has already finished.

1The Problem

Open EcommerceApplication.java. Take away the comments and there are really only two lines that do anything: an annotation, @SpringBootApplication, and a method call, SpringApplication.run(...). Those two lines give you a web server listening on port 8080, a front door that sends every request to the right place, a JSON converter, a default error page, settings read from a file, and roughly a hundred and fifty objects wired together. You wrote none of them.

That should feel a little uncomfortable. When a two-line program does that much, the work is happening somewhere you cannot see. And code you cannot see is code you cannot debug. To show how much is hidden, here is roughly what a main method looked like before Spring Boot existed. It is a simplified sketch, and the real thing was longer:

public class Main {
    public static void main(String[] args) throws Exception {
        // 1. Build Spring's container by hand, and LIST EVERY CLASS it should manage.
        AnnotationConfigWebApplicationContext spring = new AnnotationConfigWebApplicationContext();
        spring.register(WebConfig.class, JsonConfig.class,
                        ProductController.class, OrderService.class,
                        PaymentService.class  /* ...and every new class, forever */);

        // 2. Build a web server by hand.
        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();                  // create the default HTTP connector
        Context web = tomcat.addContext("", new File(".").getAbsolutePath());

        // 3. Build Spring MVC's front door by hand and plug it into the server.
        DispatcherServlet front = new DispatcherServlet(spring);
        Tomcat.addServlet(web, "dispatcher", front);
        web.addServletMappingDecoded("/", "dispatcher");

        // 4. Start everything in the right order, and keep the program alive.
        tomcat.start();
        tomcat.getServer().await();
    }
}

Look at step 1. Every class that Spring should know about had to be written into that list by hand. Add a new ShippingService next month and forget to list it? Nothing complains. The class compiles, and the program starts. The service is simply missing, and the first sign of it is an error somewhere else, much later. Step 2 decides the port with a number written into Java code, so changing it means recompiling. Steps 2 and 3 have to happen in exactly the right order, and getting it wrong gives errors from deep inside Tomcat that do not mention your mistake at all.

Spring Boot replaced all of that with one annotation and one call. So the questions this lesson answers are very concrete. What exactly does that one annotation contain? Where does the Tomcat server come from, if we never wrote new Tomcat()? What is the "container" that step 1 built by hand, and where is ours? And the one that trips up nearly every beginner in their first month: if Spring no longer needs a list of your classes, how does it find them, and why does moving one file to a different folder make an endpoint silently disappear?

2Real World Analogy

Think of opening a new branch of a restaurant chain.

The branch does not invent its own kitchen. Head office sends a founding charter, and it is pinned by the front door. The charter has three clauses. Clause one: "This building is an official branch, and it may write house recipes of its own." Clause two: "Install the chain's standard equipment: ovens, fridges, the till, the front-of-house desk. Only install what this building can support. No gas line means no gas oven, and if the branch already brought its own till, do not fit a second one." Clause three: "Hire every cook whose address is this building, including the floors below it, and nobody from anywhere else."

On opening day, the general manager takes the keys and works through the charter. They install the equipment, take on the staff, tell everyone who they work with, and then open the doors. The manager's office holds the full staff list, and it is the one place that knows every person in the building. The front door and its host desk are part of the building. The restaurant is not renting a table in someone else's food court. And once the doors are open, the manager's setup job is finished and they can go home. The restaurant stays open because the host at the door is still on shift. When the owner calls closing time, the host finishes seating the last guests, locks up, and only then is the building empty.

3The Concept Explained

3.1 First: what is actually inside an annotation?

Lesson 01 described an annotation as a marker written with an at-sign that other code can read. To take @SpringBootApplication apart, we need three more facts about annotations. Each one is small.

Fact 1: an annotation is declared in Java code, like a class. Someone wrote @SpringBootApplication just as someone wrote String. The declaration uses the keyword @interface, and it can list attributes: named settings you can fill in when you use it. You have seen this shape already, @Target(ElementType.TYPE). Here @Target is the annotation and ElementType.TYPE is the value given to its attribute.

Fact 2: an annotation only still exists at run time if its declaration says so. After compiling, the Java compiler can keep an annotation in the .class file or drop it. The declaration decides this with @Retention. @Retention(RetentionPolicy.RUNTIME) means "keep me in the compiled class, and let a running program see me". Every annotation Spring reads at startup has RUNTIME retention. Without it, the marker would be gone before Spring ever looked.

Fact 3: a running program can inspect its own classes. Java can ask a class, while the program runs, "what methods do you have?" or "what annotations are written on you?" This ability for a program to examine its own structure while it runs is called reflection. It is how Spring notices your annotations at all. EcommerceApplication.class.isAnnotationPresent(SpringBootApplication.class) is a reflection question, and the answer is true.

Now the key step. An annotation's declaration can itself carry annotations. Here is the real declaration of @SpringBootApplication, from the Spring Boot 4.1.1 source (checked on 2026-09-30, documentation comments removed):

@Target(ElementType.TYPE)                 // may be written on a class
@Retention(RetentionPolicy.RUNTIME)      // survives into the running program
@Documented                             // shows up in generated API docs
@Inherited                              // a subclass of the main class inherits it
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = { @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
public @interface SpringBootApplication {

    @AliasFor(annotation = EnableAutoConfiguration.class)
    Class<?>[] exclude() default {};

    @AliasFor(annotation = EnableAutoConfiguration.class)
    String[] excludeName() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "basePackages")
    String[] scanBasePackages() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "basePackageClasses")
    Class<?>[] scanBasePackageClasses() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "nameGenerator")
    Class<? extends BeanNameGenerator> nameGenerator() default BeanNameGenerator.class;

    @AliasFor(annotation = Configuration.class)
    boolean proxyBeanMethods() default true;
}

Look at the three highlighted lines. @SpringBootApplication is not a feature of its own. It is a bundle. It exists to carry three other annotations, so you can write one line instead of three. An annotation placed on another annotation's declaration, so that using the outer one brings the inner one along, is called a meta-annotation.

There is a catch, and it tells you something important about Spring. Plain Java does not follow meta-annotations. Ask Java's reflection whether EcommerceApplication has @Configuration and it says no, because @Configuration is not written on the class. It is written on an annotation that is written on an annotation that is written on the class, and Java only looks at the outermost layer. Spring wrote its own annotation reader that opens every layer, like opening a nest of boxes, and merges what it finds. Our new test EcommerceApplicationAnnotationTests checks both sides: plain Java answers false, and Spring's AnnotatedElementUtils answers true.

What about @AliasFor on the attributes? It is how the bundle passes your settings through to the right inner annotation. Write @SpringBootApplication(scanBasePackages = "com.shop"), and Spring's reader treats it exactly as if you had written @ComponentScan(basePackages = "com.shop"). Write exclude = ..., and it reaches @EnableAutoConfiguration. So you keep one line and still control every part of it.

Check yourself: if Java's own reflection says EcommerceApplication does not have @Configuration, how can Spring treat it as a configuration class?

Because Spring does not ask Java's reflection that question directly. Spring's annotation reader starts from the annotations written on the class, then opens each annotation's own declaration and reads the annotations on that, and keeps going until nothing new is found. @SpringBootApplication leads to @SpringBootConfiguration, which leads to @Configuration. The meta-annotation chain is a Spring idea built on top of Java, not a Java feature, and that is why a plain Java tool would miss it.

3.2 The whole thing unpacked, in one picture

Now let us take each of the three in turn, going as deep as each one needs.

3.3 Part one: @SpringBootConfiguration — "this class is a source of setup instructions"

To understand this part we need two words that are central to all of Spring. Lesson 04 gives each of them a full lesson. Here is exactly enough to move forward.

A bean. Normally, when your code needs an object, it creates it itself with new. Spring offers a different arrangement. You describe the objects your application needs, and Spring creates them, keeps them, and hands them to whoever needs them. Think of a hotel cloakroom. You do not carry your coat around all evening; the attendant takes it, keeps it on a numbered hook, and gives it back on request. An object that Spring creates and looks after in this way, instead of your code calling new, is called a bean. Each bean has a name, like the number on a cloakroom hook. In section 6 our test looks up the bean named "dispatcherServlet" by exactly that kind of name.

A configuration class. Some beans need setting up in a particular way before they are useful. For example, a database connection needs an address and a password. A class whose purpose is to hold those setup instructions, written as Java methods that each create and return one bean, is called a configuration class. It is marked with @Configuration, and each such method is marked @Bean. We write our first one in Lesson 07. Before Spring Boot, a typical application had several of them: WebConfig, JsonConfig, DatabaseConfig — the classes step 1 of the old main listed by hand.

With those two words, @SpringBootConfiguration is simple. It carries @Configuration, so it makes our main class a configuration class. That has two consequences you can check today. First, the main class may later hold @Bean methods, although best practice is to keep them in separate classes. Second, because @Configuration itself carries @Component (a marker meaning "Spring should manage this class", covered in Lesson 05), the main class is itself a bean. Spring creates an EcommerceApplication object and keeps it under the name ecommerceApplication. The default name is the class name with a lower-case first letter. Our context test looks it up by that name.

Why a special Boot version, instead of plain @Configuration? Because there is one job only the main configuration class can do. Tests have to find it. In Lesson 02, @SpringBootTest started the whole application without being told which class to start from. It found EcommerceApplication by searching. It starts in the test's own package, looks through that package and every package under it for exactly one class marked @SpringBootConfiguration, and if there is none, it moves up one package and tries again. Plain @Configuration would not work for this search, because an application can have dozens of configuration classes. @SpringBootConfiguration means "the primary one", and there must be exactly one. If the search finds none, you get this message, quoted from the 4.1.1 source:

Unable to find a @SpringBootConfiguration by searching packages upwards from the test.
You can use @ContextConfiguration, @SpringBootTest(classes=...) or other Spring Test
supported mechanisms to explicitly declare the configuration classes to load. Classes
annotated with @TestConfiguration are not considered.

It carries one setting, proxyBeanMethods, which is true by default. It controls a behaviour of @Bean methods that only matters once one of them calls another. We meet it properly in Lesson 07. For now, leave it at the default.

3.4 Part two: @EnableAutoConfiguration — "switch on the recipe engine"

Lesson 01 explained auto-configuration as a rule engine: every jar brings recipes, each recipe has conditions, and the recipes whose conditions pass get applied. What Lesson 01 left open is who turns that engine on. The answer is this annotation, and here is exactly how.

From the 4.1.1 source, @EnableAutoConfiguration carries two meta-annotations:

@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {
    String ENABLED_OVERRIDE_PROPERTY = "spring.boot.enableautoconfiguration";
    Class<?>[] exclude() default {};
    String[] excludeName() default {};
}

@Import is a Spring annotation that says "while you are processing this configuration class, also process that one". It lets one configuration class pull in others. Normally you name a configuration class directly. Here the imported class, AutoConfigurationImportSelector, is special: it is a selector. It does not contain setup instructions itself. Instead, Spring asks it, "which configuration classes should I import?", and it works out the answer while the application starts. That runtime decision is the whole of auto-configuration. Step by step, this is what the selector does:

  1. Collect the candidates. It asks the class loader for every file named exactly META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, in every jar on the classpath. Each one is a plain text file with one class name per line. That is the "recipe list" from Lesson 01, and this file name is its real name, confirmed in the 4.1.1 source. In Boot 4 each technology module brings its own. For example, spring-boot-tomcat's list names five recipes, including TomcatServletWebServerAutoConfiguration. If no such file is found anywhere, startup stops with "No auto configuration classes found in META-INF/spring/…imports".
  2. Remove the exclusions. It gathers everything you asked it to skip, from three places, all merged together: the exclude attribute (classes), the excludeName attribute (class names as text), and the setting spring.autoconfigure.exclude, which can live in application.yml or on the command line. Then it deletes those recipes from the list.
  3. Sanity-check the exclusions. If you excluded a class that is on the classpath but is not an auto-configuration recipe, startup fails with "The following classes could not be excluded because they are not auto-configuration classes". If you excluded a name that is not on the classpath at all, nothing happens. It is silently ignored. Remember that; the Boot 4 callout below turns it into a real trap.
  4. Evaluate the conditions and apply the survivors. Each remaining recipe's @ConditionalOn… checks run, exactly as Lesson 01's simulation modelled. The recipes that pass are processed as configuration classes, and their @Bean methods create beans.

One detail makes the whole design safe. Your own configuration is processed first, and the auto-configuration recipes are deliberately processed last. This is what makes @ConditionalOnMissingBean work. When the Tomcat recipe asks "has anyone already defined a web server factory?", every bean you defined is already registered, so if you brought your own, the recipe steps aside. The order is built into the mechanism, not a matter of luck.

@AutoConfigurationPackage is the second meta-annotation. It records the package of the class carrying it, com.ecommerce, in a small list the context keeps. That list is not used for scanning our components; that is the next part's job. Other features use it later as "where the application's own code lives". The first to use it will be the database layer in Chapter 5, to find our entity classes. Our test asks Spring Boot's AutoConfigurationPackages.get(context) helper and expects exactly ["com.ecommerce"].

Switching recipes off. Occasionally a recipe applies and you do not want it. The classic case is a database library on the classpath while you are not ready to configure a database. You have two equivalent tools:

// 1. In code, on the main class, by class. A typo is a compile error, which is good.
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)

# 2. As a setting, by full name, in application.yml or on the command line:
spring:
  autoconfigure:
    exclude: org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration

Prefer the first where you can. A class reference is checked by the compiler; a name written as text is not checked at all. There is also a master switch, spring.boot.enableautoconfiguration=false, which turns off the whole engine. It exists mostly for unusual test setups. Try it once and you will see exactly the failure in section 4.

Auto-configuration classes moved house, and old exclusions can fail without telling you. Because of the Boot 4 modularization described in Lesson 01, most auto-configuration recipes now live in a new package inside their technology's own module. The one you will copy from Stack Overflow most often:

org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration

What 3.x did: nearly every recipe lived in the single spring-boot-autoconfigure jar, under org.springframework.boot.autoconfigure.<technology>. The Tomcat server was set up by ServletWebServerFactoryAutoConfiguration in org.springframework.boot.autoconfigure.web.servlet.

What 4.x does: each technology module carries its own recipes under org.springframework.boot.<technology>.autoconfigure. Tomcat's is now org.springframework.boot.tomcat.autoconfigure.servlet.TomcatServletWebServerAutoConfiguration. The core spring-boot-autoconfigure jar keeps only about a dozen general recipes. I checked its 4.1.1 recipe list: admin, AOP, availability, configuration properties, lifecycle, messages, placeholders, project info, JMX, SSL, task execution, task scheduling.

Why it changed: it is the same modularization. A recipe belongs with the technology it configures, so a jar you do not have brings no recipes you do not need. A pleasant side effect is that the --debug report (below) gets much shorter. In 3.x it listed well over a hundred negative matches for technologies you never used, because their recipes were always present. In 4.x those recipes are simply not on your classpath, so there is nothing to report.

What this means for you: an old tutorial's exclude = DataSourceAutoConfiguration.class becomes a compile error in Boot 4 (package org.springframework.boot.autoconfigure.jdbc does not exist). That is annoying, but at least it is loud. The dangerous version is the text form: the old name in spring.autoconfigure.exclude or excludeName names a class that no longer exists, and step 3 above means it is silently ignored. The recipe you meant to switch off stays on, and nothing tells you. When you copy an exclusion from anywhere, look up the class's current package first. Our demo test excludingANameThatDoesNotExistIsSilentlyIgnored proves the silence on your own machine.

Add --debug to the command line and Boot prints its conditions evaluation report, which Lesson 01 introduced: every recipe it considered, and why it was applied or skipped. 3.5 Part three: @ComponentScan — "search this package and below"

Step 1 of the old main listed every class by hand. Component scanning replaces that list with a search. Here is the search, step by step.

  1. Decide where to start. @ComponentScan has a basePackages attribute. @SpringBootApplication leaves it empty, and empty does not mean "scan nothing". The rule is: if no base package is given, use the package of the class that carries the annotation. Our main class is in com.ecommerce, so the scan starts there. This one rule is why Lesson 02 said the package of the main class "genuinely matters".
  2. Turn the package into a file search. Dots become slashes, and a pattern is added that means "everything below here": com.ecommerce becomes classpath*:com/ecommerce/**/*.class. The ** means "any number of folders deep". Spring then lists every compiled class file that matches, in target/classes and in every jar.
  3. Read each class file cheaply. Spring does not load every class into memory; that would be slow. It reads the raw class file just enough to see its annotations.
  4. Keep the components. A class is kept if it carries @Component, directly or through a meta-annotation. The family of annotations that carry @Component, such as @Service, @Repository and @RestController, is Lesson 05's topic. Each kept class is registered as a bean definition, a written plan for a bean that will be created later.
  5. Apply the exclude filters. @SpringBootApplication adds two. AutoConfigurationExcludeFilter throws out any auto-configuration recipe that happens to live inside a scanned package, so the recipe cannot sneak in through the scan and skip its conditions. TypeExcludeFilter is a hook other tools can plug into. Spring Boot's test support uses it so that configuration classes meant only for tests are not picked up by the main application.

The consequence is a boundary, and it is strict. Classes in com.ecommerce or any package beneath it are found. Classes anywhere else are not, and nothing tells you. Three details about this boundary catch people out:

  • "Beneath" means beneath by whole segments, not by spelling. com.ecommerceadmin starts with the same letters as com.ecommerce, but it is a different package. It is a sibling, not a child, and it is not scanned. The file pattern com/ecommerce/** needs a slash after ecommerce.
  • Above is invisible too. Move the main class down into com.ecommerce.app, and the scan now starts there. com.ecommerce.product is a sibling of app, so it is not included.
  • Setting the packages yourself replaces the default rather than adding to it. @SpringBootApplication(scanBasePackages = {"com.ecommerce", "com.ecommerceadmin"}) scans exactly those two package trees. If you list only "com.ecommerceadmin", your own main package is no longer scanned. scanBasePackageClasses = SomeClass.class does the same job, but it names a class instead of a package string, so a typo is a compile error rather than a silent miss.

Why is it designed as a search boundary at all, instead of scanning everything? Because "everything" on the classpath is huge. Our forty jars hold tens of thousands of classes, most of them Spring's own and Tomcat's. Scanning all of them would be slow, and worse, it would pick up any class in any library that happens to carry @Component. That class would be created in your application without you asking. A boundary drawn around your own code is fast, predictable, and yours. The price is that you have to keep your code inside it. The convention, followed by nearly every Spring project, is simple: the main class goes in the root package, and every other class goes in that package or below it.

The extreme case: no package at all. A class file with no package line lives in the default package. Put the main class there and the scan's starting point becomes "the root of everything": every class in every jar. Spring Boot detects this at startup and prints a warning much like ** WARNING ** : Your ApplicationContext is unlikely to start due to a @ComponentScan of the default package. (a prediction: the wording has been stable for many versions, but check it against what your machine prints). As the warning says, the application usually fails to start soon afterwards. Always give your classes a package.

3.6 The ApplicationContext — the brain of the application

Every section so far has said "Spring registers…", "Spring keeps…", "the container holds…". It is time to name the object doing all of it. In the old main in section 1 you could see it, because step 1 created it by hand: new AnnotationConfigWebApplicationContext(). In our main it is created inside SpringApplication.run, and run hands it back. The return type is ConfigurableApplicationContext. We just never kept the returned value.

A container in Spring is the object that creates your beans, keeps them, and connects them to each other. Spring's full-featured container is called the ApplicationContext. Calling it the brain is not just a figure of speech. Everything the application knows is stored in it, and everything that happens goes through it. Concretely, it has five jobs:

  1. The registry: it knows every bean. For every bean, it keeps a name, a type, and the plan for creating it. You can ask by name, as in context.getBean("dispatcherServlet"), or by type, as in context.getBean(EcommerceApplication.class). getBeanDefinitionCount() tells you how many beans it knows about. Our project wrote exactly one class, yet the number is well over a hundred. Every other bean came from auto-configuration.
  2. The factory: it creates beans in the right order and connects them. If bean A needs bean B, the context creates B first and hands it to A. Connecting beans this way is called dependency injection, and it is Chapter 2's entire subject.
  3. The settings: it owns the Environment. Every setting from application.yml, from environment variables, and from the command line is merged into one object, the Environment, with a clear priority order: a command-line argument beats application.yml. context.getEnvironment().getProperty("spring.application.name") returns "ecommerce", read from our YAML file. Profiles and the full priority order come in Chapter 6.
  4. The announcements: it publishes events. It announces moments such as "startup finished" and "shutting down", and any bean can listen for them. Lesson 10 uses this.
  5. The lifecycle: it starts and stops everything. The context goes through refresh: reading every configuration, creating every bean, starting everything that needs starting. Later it goes through close: stopping everything and destroying every bean in reverse order. The embedded web server is started and stopped as part of this lifecycle, which is why closing the context shuts Tomcat down.

ApplicationContext is a Java interface. That means a list of promised abilities, with several different classes that fulfil the promise. There is a small ladder of them, and it is worth knowing because you will see every rung in error messages:

TypeWhat it addsWhere you meet it

ApplicationContextEverything above, plus the Environment, events, messages, and loading files. What people mean by "the context".Anywhere you ask Spring for something

Which one does Boot choose? It decides very early, inside the SpringApplication constructor, by looking at the classpath. This choice is called the web application type. The rules, from the official 4.1.1 reference documentation: if Spring MVC is present, it is a servlet web application and the context is AnnotationConfigServletWebServerApplicationContext. If Spring MVC is absent but Spring WebFlux (the reactive web stack, covered in Phase 3) is present, it is reactive. Otherwise it is none: a plain AnnotationConfigApplicationContext with no web server at all. You can override the decision with the setting spring.main.web-application-type (servlet, reactive or none). Our demo test does exactly that, and watches the web server disappear.

3.7 The embedded Tomcat, and why there is no server to install

Lesson 01 showed the big reversal. In the old world, your application was copied into a Tomcat that someone installed separately. With Spring Boot, Tomcat is a library that lives inside your application. Lesson 01 explained why this is better. Here is how it actually happens, now that we have every piece.

  1. The Tomcat server's classes are on the classpath because spring-boot-starter-webmvc pulled in spring-boot-starter-tomcat (Lesson 02). They are just jar files. Nothing has been started yet.
  2. Because Spring MVC is on the classpath, Boot chooses a servlet web application, and so the context is a ServletWebServerApplicationContext.
  3. @EnableAutoConfiguration finds the TomcatServletWebServerAutoConfiguration recipe. Its conditions pass: the Tomcat classes are present, this is a servlet application, and we have defined no web server factory of our own. So it registers a bean named tomcatServletWebServerFactory. A factory is an object whose only job is to build another object. This one knows how to build a configured Tomcat, and it reads server.port and every other server.* setting.
  4. Part-way through refresh, the context reaches a step called onRefresh. ServletWebServerApplicationContext uses that step to call its own createWebServer() method. It asks itself for beans of type ServletWebServerFactory and expects exactly one. If there are none, it throws MissingWebServerFactoryBeanException, which you will meet in section 4. If there are two or more, it throws "Unable to start ServletWebServerApplicationContext due to multiple ServletWebServerFactory beans". Both messages are quoted from the 4.1.1 source.
  5. With exactly one factory, it calls factory.getWebServer(...). Tomcat is built in memory and bound to the port, and the log prints Tomcat initialized with port 8080 (http). Tomcat then starts up its internals and hands control back to Spring for Spring's own setup, and the log prints Root WebApplicationContext: initialization completed in … ms.
  6. The context goes on to create every remaining bean. Only at the very end of refresh does it tell Tomcat to begin accepting requests, and the log prints Tomcat started on port 8080 (http) with context path '/'. The two log lines are separated on purpose. Opening the doors before all the beans were ready would let the first customers arrive at an unfinished application.

So "why is no external server needed?" now has a mechanical answer: the server is just another object built by a factory bean, and a bean created by auto-configuration can be replaced, reconfigured, or switched off like any other. Change server.port and the factory builds Tomcat on a different port. Define your own ServletWebServerFactory bean and the recipe steps aside. Exclude the recipe and there is no factory, so the web application cannot start. Our demo test proves that on your machine.

3.8 Why the program keeps running after main() has finished

A correction to Lesson 02. Lesson 02, and the comments in EcommerceApplication.java, said that SpringApplication.run "does not return while the server is running". That was wrong. I checked the 4.1.1 source of SpringApplication.run: its last line is return context;. It returns as soon as startup is complete. The comments in the main class have been corrected, and so has Lesson 02. This section explains what really keeps the application alive. It is also a small example of why every claim in this course is a prediction you are invited to check.

To see how, we need one new idea. A Java program can do several things at once. Each independent line of work inside a running program is called a thread. Think of the cooks in one kitchen: they share the same kitchen, but each follows their own list of steps. When the Java runtime starts your program, it creates one thread named main and runs your main() method on it. That is why every startup log line so far shows [main]. Code can start more threads, and Tomcat starts several.

Now the rule that decides when a Java program ends. Every thread is either a daemon thread or a non-daemon thread. A daemon thread is background help that the program does not wait for. A non-daemon thread is real work that the program must wait for. The Java runtime exits only when no non-daemon threads remain. The main thread is non-daemon, so an ordinary program ends when main() returns: it was the last one.

Here is what happens in our application:

  1. The main thread calls SpringApplication.run, and all of startup happens on it.
  2. When Tomcat starts, its TomcatWebServer class starts one extra thread named container-0, and it explicitly marks it non-daemon with setDaemon(false). That thread's only job is to wait. (Checked in the 4.1.1 source: the method is startNonDaemonAwaitThread().) Tomcat also runs threads that listen for connections and handle requests.
  3. run returns the context. main() has nothing left to do, so it returns and the main thread ends.
  4. The Java runtime checks for remaining non-daemon threads, finds container-0, and does not exit. The application keeps serving requests on Tomcat's threads. Nothing is "blocked"; the waiting is done by a thread whose whole purpose is to wait.
  5. You press Ctrl+C. The operating system asks the Java runtime to stop. Before exiting, the runtime runs its shutdown hooks, pieces of code registered in advance to run "on the way out". Spring Boot registered one that closes the context.
  6. Closing the context stops Tomcat gracefully: it stops accepting new connections, lets requests already in progress finish, then shuts down. That ends container-0. Now no non-daemon threads remain, and the Java runtime exits.

The official 4.1.1 documentation's sample log shows the last two steps. Notice the thread names: the shutdown runs on a thread whose name, truncated to fit, ends …ionShutdownHook, and the graceful stop on one called tomcat-shutdown:

INFO 18244 --- [ecommerce] [ionShutdownHook] o.s.boot.tomcat.GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
INFO 18244 --- [ecommerce] [tomcat-shutdown] o.s.boot.tomcat.GracefulShutdown : Graceful shutdown complete

This has a practical consequence you can use. Code written after SpringApplication.run(...) in main() does run, once, right after startup finishes, while the application is already serving requests. (It is not the idiomatic place for "do something at startup"; Lesson 10 shows the proper tools.) And it explains the other direction too: with spring.main.web-application-type=none there is no Tomcat, so no container-0, so the program starts, prints Started EcommerceApplication, and exits immediately. That is not a crash. The program simply ran out of work.

Check yourself: you add System.out.println("hello"); on the line after SpringApplication.run(...). When, if ever, does "hello" appear?

Once, immediately after the Started EcommerceApplication in … seconds line. run returns when startup is complete, main carries on to your println, prints "hello", and then returns. The application keeps running afterwards, because Tomcat's non-daemon container-0 thread keeps the Java runtime alive. If run truly blocked, as Lesson 02 wrongly said, "hello" would only appear after you pressed Ctrl+C. Try it and let the machine settle it. Then delete the line.

3.9 The whole of SpringApplication.run, start to finish

Everything in this lesson happens inside one method call. Here it is in order, based on the 4.1.1 source of SpringApplication, with nothing left as "it just happens".

  1. new SpringApplication(EcommerceApplication.class). The static run first builds a SpringApplication object. Its constructor records our class as the primary source, the first configuration class the context will read. It decides the web application type from the classpath (servlet, for us). It loads Boot's own built-in list of startup helpers from the jars. And it works out which class holds the main method, so the log can name it.
  2. Prepare the Environment. application.yml is read, the command-line args are turned into settings (every --name=value becomes a setting that outranks the YAML file), and they are merged into one Environment.
  3. Print the banner, the ASCII-art Spring logo, then log Starting EcommerceApplication using Java 21… and No active profile set….
  4. Create the context of the chosen type, and register the primary source, our main class, as the first bean definition. That is the moment @SpringBootApplication gets noticed. Spring never went looking for it; we handed it over as the first argument to run.
  5. Refresh the context. This is the big one, in order:
    1. Process configuration classes, starting with ours. Reading its annotations triggers @ComponentScan, which finds and registers our components (none yet), and @EnableAutoConfiguration, which reads every recipe list, removes exclusions, evaluates conditions and registers the survivors' beans, all after our own.
    2. Prepare the special beans that post-process other beans (a Chapter 2 topic).
    3. onRefresh: create the web server. Tomcat initialized with port 8080, then Root WebApplicationContext: initialization completed.
    4. Create every remaining bean that is not marked as lazy (created only on first use), in dependency order.
    5. Finish: start everything with a lifecycle, including Tomcat's connector. Tomcat started on port 8080.
  6. Log Started EcommerceApplication in 1.9 seconds, announce "started", run any startup runners (Lesson 10), announce "ready".
  7. Return the context. If anything in steps 1–6 threw, the context is closed instead, a failure report such as APPLICATION FAILED TO START is printed, and the exception is re-thrown out of run. That is exactly how a failing startup fails our contextLoads() test.

"What does @SpringBootApplication do?" is one of the most common Spring interview questions, and "it starts the application" is the answer that ends the interview early. The answer that gets you hired is section 3.2: three annotations, what each one does, and one consequence of each. "The main class is a bean." "Recipes back off if you define your own bean." "Scanning starts at the main class's package, so the main class goes in the root package." On real teams, the scanning boundary causes a whole class of production incidents in multi-module projects. A shared library module is published under com.company.common, the services live in com.company.orders, and a @Component in the library is silently never created until someone adds scanBasePackages. Knowing where the boundary is lets you diagnose that in minutes rather than days.

4The Wrong Way

Wrong approach

Having learned that @SpringBootApplication is "just three annotations", a common and very reasonable instinct is to write them out by hand, to be explicit and to see what is going on. The instinct is fine. The usual way it goes wrong is that one piece gets dropped, often @EnableAutoConfiguration, because it "sounds optional".

package com.ecommerce;

import org.springframework.boot.SpringApplication;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;

@Configuration      // "a source of setup instructions" - fine
@ComponentScan      // "search this package and below" - fine
                    // @EnableAutoConfiguration: forgotten
public class EcommerceApplication {
    public static void main(String[] args) {
        SpringApplication.run(EcommerceApplication.class, args);
    }
}

What goes wrong. Follow the chain from section 3. Spring MVC is still on the classpath, so the SpringApplication constructor still decides this is a servlet web application and still creates a ServletWebServerApplicationContext. That context still reaches onRefresh and still asks for exactly one ServletWebServerFactory bean. But the only thing that ever defined one was the Tomcat auto-configuration recipe, and without @EnableAutoConfiguration no recipe is ever read. There are zero factories. The Tomcat jar is right there on the classpath, and nothing will build it.

There are two more wrong ways, and both are quieter, which makes them worse.

Dropping @ComponentScan instead. Now the application starts perfectly. Tomcat runs, and curl gets its 404. Nothing looks broken today, because we have no components yet. This is the simulation's second button, and it is the most common "my endpoint returns 404 and I don't know why" on Stack Overflow. 5The Right Way

Correct approach

Keep @SpringBootApplication. It is the correct, idiomatic choice, and after this lesson it is no longer a black box. The main class stays exactly as it was in Lesson 02. Only its comments changed, and the full file on disk carries them.

package com.ecommerce;   // the ROOT package: the scan starts here, so everything else goes below it

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;   // did not move in Boot 4

@SpringBootApplication   // = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
public class EcommerceApplication {   // also becomes the bean "ecommerceApplication"

    public static void main(String[] args) {
        // Builds and refreshes the ApplicationContext, starts Tomcat, then RETURNS it.
        // Tomcat's non-daemon thread keeps the program alive after main() ends.
        SpringApplication.run(EcommerceApplication.class, args);
    }
}

Step-by-step walkthrough of what happens when this runs

  1. The JVM calls main on the thread named main.
  2. SpringApplication.run builds a SpringApplication. It records EcommerceApplication as the primary source, sees Spring MVC on the classpath, and chooses a servlet web application.
  3. It reads application.yml (spring.application.name=ecommerce, server.port=8080) and the command-line arguments into the Environment.
  4. It prints the banner and logs Starting EcommerceApplication….
  5. It creates an AnnotationConfigServletWebServerApplicationContext and registers EcommerceApplication in it as the bean ecommerceApplication.
  6. Refresh begins. Spring reads the annotations on EcommerceApplication and opens up @SpringBootApplication into its three parts.
  7. @ComponentScan searches com/ecommerce/**/*.class. It finds only EcommerceApplication, which is already registered. There are no other components yet.
  8. @EnableAutoConfiguration's selector reads every AutoConfiguration.imports file, removes nothing (we excluded nothing), evaluates conditions, and registers the surviving recipes' beans, including tomcatServletWebServerFactory and dispatcherServlet. @AutoConfigurationPackage records com.ecommerce.
  9. onRefresh finds exactly one ServletWebServerFactory, builds Tomcat, and binds port 8080: Tomcat initialized with port 8080 (http). Tomcat starts its engine and runs Spring's web setup: Root WebApplicationContext: initialization completed.
  10. Every remaining bean is created. Then Tomcat's connector starts accepting requests: Tomcat started on port 8080 (http) with context path '/'. The non-daemon thread container-0 is now running.
  11. Started EcommerceApplication in … seconds is logged, and run returns the context. main ends, and the thread named main ends with it.
  12. The program stays alive on Tomcat's threads. A request to / still gets the 404 from Lesson 02, and that is correct.
  13. Ctrl+C runs the shutdown hook. The context closes, Tomcat shuts down gracefully, container-0 ends, and the Java runtime exits.

    void theApplicationPackageIsTheMainClassPackage() {
        assertThat(AutoConfigurationPackages.get(context)).containsExactly("com.ecommerce");
    }

    @Test
    void closingTheContextShutsTheWholeApplicationDown() {
        ConfigurableApplicationContext throwaway = SpringApplication.run(EcommerceApplication.class, "--server.port=0");
        assertThat(throwaway.isActive()).isTrue();
        throwaway.close();                                // what Ctrl+C triggers
        assertThat(throwaway.isActive()).isFalse();
    }
}

@BeforeAll and @AfterAll are JUnit annotations. A method marked @BeforeAll runs once before any test in the class, and @AfterAll once after all of them. Both must be static, because JUnit calls them before any test object exists, much as the JVM calls main. We use them because starting Spring costs a second or two, and four tests can safely share one running application as long as they only read from it. The fourth test needs a context it is allowed to destroy, so it starts its own.

try ( … ) { … } with a value inside the brackets is Java's try-with-resources. Anything declared in the brackets that can be closed is closed automatically when the block ends, whether the block finished normally or threw. It is the tidiest way to guarantee that every context a test starts, it also stops. assertThatThrownBy is AssertJ's way of saying "this code must throw, and here is what the exception must look like". .rootCause() follows the chain of "caused by" exceptions to the bottom and checks that one.

7Gotchas and Common Mistakes

  • Moving the main class into a sub-package "to tidy up". People do it because in most projects the root package is untidy, and a class called …Application looks as if it belongs in a folder of its own. It compiles and starts perfectly, and every class outside the new, narrower boundary silently disappears. Avoid it by: treating the root package as the main class's permanent home. Our test theApplicationPackageIsTheMainClassPackage now enforces this.

  • Copying an exclusion from an old tutorial. excludeName and spring.autoconfigure.exclude take class names as text, and a name that no longer exists, like any 3.x org.springframework.boot.autoconfigure.<tech>.… name for a recipe that moved in Boot 4, is silently ignored. People copy these because the snippet "worked" for someone. Avoid it by: preferring exclude = SomeAutoConfiguration.class, where the compiler checks the name, and checking what actually happened with --debug. Do not rely on the Exclusions: list in the report for this. As far as I recall from Boot's source (not re-checked for 4.1.1), it lists every name you asked to exclude, whether or not that name matched anything. Look for the recipe itself instead. If it still appears under Positive matches, your exclusion did nothing.

  • A second @SpringBootApplication (or @SpringBootConfiguration) somewhere under the root package. This usually comes from copying a sample application into the project, or starting a "quick experiment" class. @SpringBootTest's upward search then finds two candidates and refuses to choose. Expect a message beginning Found multiple @SpringBootConfiguration annotated classes (a prediction: that wording is from my memory of the source, not re-checked for 4.1.1), and every @SpringBootTest in the project fails at once. Avoid it by: keeping exactly one per application. Experiments go in a separate project.

  • Believing SpringApplication.run blocks. Even this course said so, for one lesson. People believe it because the terminal does not come back, and that looks like blocking. The consequence: code after run(...) surprises you by running, once, at startup. Avoid it by: remembering the two lanes in the figure in section 3.9. run returns; Tomcat's non-daemon thread keeps the program alive.

  • Reading "check your dependencies" and only looking at pom.xml. The missing-web-server-factory error is just as often caused by an annotation or an exclusion as by a missing jar, as section 4 showed. Avoid it by: checking in order: @SpringBootApplication is intact, spring.autoconfigure.exclude is empty, spring.main.web-application-type is not forced, and only then the dependencies.

  • Putting any class in the default package. This happens when a file is created at the top of src/main/java by mistake. For the main class it means scanning every jar. Avoid it by: always giving every class a package line. Your IDE warns about the default package; take the warning seriously.

8Tradeoffs and When Not to Use This

Convenience costs visibility. One annotation doing three jobs is wonderful until one of the jobs does something you did not expect. The whole point of this lesson is that the cost is small if you know what is inside. --debug shows every auto-configuration decision, and a single test can confirm the scan boundary. The cost is large for a team that treats the annotation as magic. That is why it is worth having the tests in section 6, and not only knowing the facts.

Scanning costs startup time. Reading every class file under the root package is fast for our project and still fast for a few thousand classes, but it is not free, and it grows with your codebase. Huge applications, and applications that must start in milliseconds, turn to Spring's ahead-of-time processing and native images (Phase 3), which do this work at build time instead of at startup. spring.main.lazy-initialization=true is another lever. It creates beans only when first used, so startup is faster, but mistakes that would have failed at startup now fail on the first request, which is usually a worse time to find them.

When would you not use @SpringBootApplication as-is? Three honest cases. Multi-module projects where shared code lives in a sibling package tree: add scanBasePackages or scanBasePackageClasses, or better, have the shared module provide its own auto-configuration recipe (Phase 3). Libraries meant for other applications to use must never carry @SpringBootApplication, because it would compete with the real application's one. And tests or tools that need only a slice of the machinery can use narrower annotations, such as @ImportAutoConfiguration with a hand-picked list of recipes. The testing chapter's slice tests do exactly this.

When would you not want the embedded server? If your organisation runs a shared, centrally managed application server and requires deployment into it, Boot still supports producing a WAR file (Lesson 01 explained the format), and the server stops being embedded. And for a program that does not answer web requests at all, such as a batch job or a command-line tool, set spring.main.web-application-type=none, or simply do not depend on a web starter. You keep the container and auto-configuration and lose nothing you needed. That is exactly what Spring Batch jobs do in Phase 3.

9Key Takeaways

  • @SpringBootApplication is a bundle of three meta-annotations: @SpringBootConfiguration makes the main class the primary configuration class and a bean, @EnableAutoConfiguration switches on the recipe engine, and @ComponentScan searches for your classes. Plain Java does not see through the bundle, but Spring's annotation reader does.
  • @EnableAutoConfiguration works by importing a selector that reads every META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file, removes your exclusions, and applies the recipes whose conditions pass, after your own configuration, which is what lets a recipe back off when you define your own bean.
  • Component scanning starts at the main class's package and covers only that package and those beneath it, by whole package segments. That is why the main class belongs in the root package, and why a class outside the boundary is silently never created.
  • The ApplicationContext is the container at the centre of every Spring application: it holds and names every bean, creates and connects them, owns the Environment, publishes events, and controls startup and shutdown, including the embedded Tomcat, which is simply built by an auto-configured factory bean during refresh.
  • SpringApplication.run returns the finished context once startup is complete, and main() then ends. The program keeps running only because Tomcat started a non-daemon thread, and in Spring Boot 4 the Tomcat and web-server classes live in new packages (org.springframework.boot.tomcat, org.springframework.boot.web.server.*), which is why our logs and imports differ from every 3.x tutorial.

A teammate "tidies" the project. They move EcommerceApplication.java into a new folder, src/main/java/com/ecommerce/app/, change its first line to package com.ecommerce.app;, and add one line to main:

3. After the imports are fixed: 10 pass, 1 fails.

  • theApplicationPackageIsTheMainClassPackage fails. AssertJ reports that it expected exactly ["com.ecommerce"] but the actual list was ["com.ecommerce.app"]. This is the guard doing its job: it caught the boundary moving before any customer did.
  • The other three context tests and all three demo tests pass. Tomcat, the DispatcherServlet and the main-class bean do not depend on the package. The bean name is still ecommerceApplication.

That is exactly why this lesson added a test that checks the package explicitly.

4. GET /products gives a 404. The scan now starts at com.ecommerce.app, and com.ecommerce.product is a sibling package, not a child. The controller is never found, never created, and never mapped. Startup prints no error at all: the simulation's second button, now for real.

5. Two fixes.

Fix A (the right one): move the class back. Put EcommerceApplication in com.ecommerce, using the IDE's move refactoring, which updates every reference. The convention is restored, the boundary covers everything, and all 11 tests pass. This is the choice to make, because every other developer who opens the project will expect the main class at the root.

Fix B (works, but fights the convention): widen the scan.

@SpringBootApplication(scanBasePackages = "com.ecommerce")
public class EcommerceApplication { ... }

This fixes the controller. But it only widens @ComponentScan. @AutoConfigurationPackage still records com.ecommerce.app, so our package test still fails, and in Chapter 5 the database layer would not find entity classes outside com.ecommerce.app either. You would need further settings to cover that too. Fix B treats a symptom; Fix A removes the cause.
