The Main Application Class

One annotation, taken apart into the three it stands for. The ApplicationContext, the object that runs everything. Where the embedded Tomcat really comes from. And why your program keeps running after main() has finished.

1The Problem

Open EcommerceApplication.java. Take away the comments, and only two lines really do anything. One is an annotation, @SpringBootApplication. The other is a method call, SpringApplication.run(...). Those two lines give you a lot. A web server listening on port 8080. A front door that sends every request to the right place. A JSON converter. A default error page. Settings read from a file. And about a hundred and fifty objects, all connected. You wrote none of them.

That should feel a little uncomfortable. When a two-line program does that much, the work is happening somewhere you cannot see. And code you cannot see is code you cannot fix. To show how much is hidden, here is roughly what a main method looked like before Spring Boot existed. It is a simplified sketch. The real thing was longer:

public class Main {
    public static void main(String[] args) throws Exception {
        // 1. Build Spring's container by hand, and LIST EVERY CLASS it should manage.
        AnnotationConfigWebApplicationContext spring = new AnnotationConfigWebApplicationContext();
        spring.register(WebConfig.class, JsonConfig.class,
                        ProductController.class, OrderService.class,
                        PaymentService.class  /* ...and every new class, forever */);

        // 2. Build a web server by hand.
        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();                  // create the default HTTP connector
        Context web = tomcat.addContext("", new File(".").getAbsolutePath());

        // 3. Build Spring MVC's front door by hand and plug it into the server.
        DispatcherServlet front = new DispatcherServlet(spring);
        Tomcat.addServlet(web, "dispatcher", front);
        web.addServletMappingDecoded("/", "dispatcher");

        // 4. Start everything in the right order, and keep the program alive.
        tomcat.start();
        tomcat.getServer().await();
    }
}

Look at step 1. Every class that Spring should know about had to be written into that list by hand. Add a new ShippingService next month and forget to list it? Nothing complains. The class compiles, and the program starts. The service is simply missing, and the first sign of it is an error somewhere else, much later. Step 2 sets the port with a number written into the Java code, so changing it means compiling again. Steps 2 and 3 must happen in exactly the right order. If you get the order wrong, the errors come from deep inside Tomcat. They do not mention your mistake at all.

Spring Boot replaced all of that with one annotation and one call. So this lesson answers some very concrete questions. What exactly is inside that one annotation? Where does the Tomcat server come from, if we never wrote new Tomcat()? What is the "container" that step 1 built by hand, and where is ours? And one more, which trips up nearly every beginner in their first month. Spring no longer needs a list of your classes. So how does it find them? And why does moving one file to another folder make an endpoint quietly disappear?

2Real World Analogy

Think of opening a new branch of a restaurant chain.

The branch does not invent its own kitchen. Head office sends a founding charter, and it is pinned up by the front door. The charter has three rules.

  • Rule one: "This building is an official branch. It may write house recipes of its own."
  • Rule two: "Install the chain's standard equipment: ovens, fridges, the till, the front desk. Only install what this building can support. No gas pipe means no gas oven. And if the branch already brought its own till, do not fit a second one."
  • Rule three: "Hire every cook whose address is this building, including the floors below it. Hire nobody from anywhere else."

On opening day, the general manager takes the keys and works through the charter. They install the equipment and hire the staff. They tell everyone who they will work with. Then they open the doors. The manager's office holds the full staff list. It is the one place that knows every person in the building. The front door and its host desk are part of the building. The restaurant is not renting a table in someone else's food court. Once the doors are open, the manager's setup job is done, and they can go home. The restaurant stays open because the host at the door is still on shift. At closing time, the host finishes seating the last guests and locks up. Only then is the building empty.

3The Concept Explained

3.1 First: what is actually inside an annotation?

Lesson 01 described an annotation as a marker written with an at-sign that other code can read. To take @SpringBootApplication apart, we need three more facts about annotations. Each one is small.

Fact 1: an annotation is declared in Java code, like a class. Someone wrote @SpringBootApplication just as someone wrote String. The declaration uses the keyword @interface. It can list attributes: named settings you can fill in when you use the annotation. You will see this shape in a moment: @Target(ElementType.TYPE). Here @Target is the annotation, and ElementType.TYPE is the value given to its attribute.

Fact 2: an annotation only exists while the program runs if its declaration says so. When it compiles, the Java compiler can either keep an annotation in the .class file or drop it. The declaration decides, using @Retention. @Retention(RetentionPolicy.RUNTIME) means "keep me in the compiled class, and let a running program see me". Every annotation Spring reads at startup has RUNTIME retention. Without it, the marker would be gone before Spring ever looked.

Fact 3: a running program can look at its own classes. While the program runs, Java can ask a class "what methods do you have?" or "what annotations are written on you?". A program's ability to look at its own structure while it runs is called reflection. It is how Spring notices your annotations at all. EcommerceApplication.class.isAnnotationPresent(SpringBootApplication.class) is a reflection question, and the answer is true.

Now the key step. An annotation's declaration can itself carry annotations. Here is the real declaration of @SpringBootApplication, from the Spring Boot 4.1.1 source (checked on 2026-09-30, documentation comments removed):

@Target(ElementType.TYPE)                 // may be written on a class
@Retention(RetentionPolicy.RUNTIME)      // survives into the running program
@Documented                             // shows up in generated API docs
@Inherited                              // a subclass of the main class inherits it
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = { @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
public @interface SpringBootApplication {

    @AliasFor(annotation = EnableAutoConfiguration.class)
    Class<?>[] exclude() default {};

    @AliasFor(annotation = EnableAutoConfiguration.class)
    String[] excludeName() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "basePackages")
    String[] scanBasePackages() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "basePackageClasses")
    Class<?>[] scanBasePackageClasses() default {};

    @AliasFor(annotation = ComponentScan.class, attribute = "nameGenerator")
    Class<? extends BeanNameGenerator> nameGenerator() default BeanNameGenerator.class;

    @AliasFor(annotation = Configuration.class)
    boolean proxyBeanMethods() default true;
}

Look at the three highlighted lines. @SpringBootApplication is not a feature of its own. It is a bundle. It exists to carry three other annotations, so you can write one line instead of three. Sometimes an annotation is placed on another annotation's declaration. Then using the outer one brings the inner one along too. The inner one is called a meta-annotation.

There is a catch, and it tells you something important about Spring. Plain Java does not follow meta-annotations. Ask Java's reflection whether EcommerceApplication has @Configuration, and it says no. That is because @Configuration is not written on the class. Follow the chain: @Configuration is written on @SpringBootConfiguration, which is written on @SpringBootApplication, which is written on the class. Java only looks at the outermost layer. So Spring wrote its own annotation reader. It opens every layer, like opening a set of boxes inside boxes, and collects what it finds. Our new test EcommerceApplicationAnnotationTests checks both sides. Plain Java answers false. Spring's AnnotatedElementUtils answers true.

What about @AliasFor on the attributes? It is how the bundle passes your settings on to the right inner annotation. Write @SpringBootApplication(scanBasePackages = "com.shop"), and Spring treats it exactly as if you had written @ComponentScan(basePackages = "com.shop"). Write exclude = ..., and that setting reaches @EnableAutoConfiguration. So you keep one line, and still control every part of it.

Check yourself: Java's own reflection says EcommerceApplication does not have @Configuration. So how can Spring treat it as a configuration class?

Because Spring does not ask Java's reflection that question directly. Spring's annotation reader starts with the annotations written on the class. Then it opens each annotation's own declaration and reads the annotations on that. It keeps going until it finds nothing new. @SpringBootApplication leads to @SpringBootConfiguration, which leads to @Configuration. Following this chain is a Spring idea, built on top of Java. It is not a Java feature. That is why a plain Java tool would miss it.

3.2 The whole thing unpacked, in one picture

Now let us take each of the three in turn, going as deep as each one needs.

3.3 Part one: @SpringBootConfiguration — "this class is a source of setup instructions"

To understand this part, we need two words that are central to all of Spring. Lesson 04 gives each of them a full lesson. Here is just enough to move forward.

A bean. Normally, when your code needs an object, it creates it itself with new. Spring offers a different deal. You describe the objects your application needs. Spring creates them, keeps them, and hands them to whoever needs them. Think of a hotel cloakroom. You do not carry your coat around all evening. The attendant takes it, keeps it on a numbered hook, and gives it back when you ask. An object that Spring creates and looks after like this is called a bean. Your code does not call new for it. Each bean has a name, like the number on a cloakroom hook. In section 6, our test looks up the bean named "dispatcherServlet" by exactly that kind of name.

A configuration class. Some beans need to be set up in a certain way before they are useful. For example, a database connection needs an address and a password. A class can hold those setup instructions as Java methods. Each method creates and returns one bean. Such a class is called a configuration class. The class is marked with @Configuration, and each of those methods is marked @Bean. We write our first one in Lesson 07. Before Spring Boot, a typical application had several of them, such as WebConfig, JsonConfig and DatabaseConfig. Those are the classes that step 1 of the old main listed by hand.

With those two words, @SpringBootConfiguration is simple. It carries @Configuration, so it makes our main class a configuration class. That has two results you can check today. First, the main class may later hold @Bean methods. (Good practice is to keep them in separate classes, though.) Second, @Configuration itself carries @Component. That is a marker meaning "Spring should manage this class", covered in Lesson 05. So the main class is itself a bean. Spring creates an EcommerceApplication object and keeps it under the name ecommerceApplication. The default name is the class name with a lower-case first letter. Our context test looks it up by that name.

Why a special Boot version, instead of plain @Configuration? Because there is one job only the main configuration class can do: tests have to find it. In Lesson 02, @SpringBootTest started the whole application without being told which class to start from. It found EcommerceApplication by searching. Here is how the search works:

  1. It starts in the test's own package.
  2. It looks through that package, and every package inside it, for exactly one class marked @SpringBootConfiguration.
  3. If it finds none, it moves up one package and tries again.

Plain @Configuration would not work for this search, because an application can have dozens of configuration classes. @SpringBootConfiguration means "the main one", and there must be exactly one. If the search finds none, you get this message, quoted from the 4.1.1 source:

Unable to find a @SpringBootConfiguration by searching packages upwards from the test.
You can use @ContextConfiguration, @SpringBootTest(classes=...) or other Spring Test
supported mechanisms to explicitly declare the configuration classes to load. Classes
annotated with @TestConfiguration are not considered.

It carries one setting, proxyBeanMethods, which is true by default. It controls a behaviour of @Bean methods that only matters once one of them calls another. We meet it properly in Lesson 07. For now, leave it at the default.

3.4 Part two: @EnableAutoConfiguration — "switch on the recipe engine"

Lesson 01 explained auto-configuration as a rule engine: every jar brings recipes, each recipe has conditions, and the recipes whose conditions pass get applied. What Lesson 01 left open is who turns that engine on. The answer is this annotation, and here is exactly how.

From the 4.1.1 source, @EnableAutoConfiguration carries two meta-annotations:

@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {
    String ENABLED_OVERRIDE_PROPERTY = "spring.boot.enableautoconfiguration";
    Class<?>[] exclude() default {};
    String[] excludeName() default {};
}

@Import is a Spring annotation that says "while you are reading this configuration class, read that one too". It lets one configuration class pull in others. Normally you name a configuration class directly. But the imported class here, AutoConfigurationImportSelector, is special. It is a selector. It holds no setup instructions itself. Instead, Spring asks it: "which configuration classes should I import?". It works out the answer while the application starts. That decision, made at startup, is the whole of auto-configuration. Step by step, here is what the selector does:

  1. Collect the candidates. It looks for every file named exactly META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, in every jar on the classpath. Each one is a plain text file with one class name per line. That is the "recipe list" from Lesson 01, and this is its real file name, confirmed in the 4.1.1 source. In Boot 4, each technology module brings its own list. For example, the list in spring-boot-tomcat names five recipes, including TomcatServletWebServerAutoConfiguration. If no such file is found anywhere, startup stops with "No auto configuration classes found in META-INF/spring/…imports".
  2. Remove the exclusions. It collects everything you asked it to skip. That can come from three places, and it combines them all:
    • the exclude attribute (classes),
    • the excludeName attribute (class names written as text),
    • the setting spring.autoconfigure.exclude, in application.yml or on the command line.
    Then it deletes those recipes from the list.
  3. Check the exclusions make sense. Say you excluded a class that is on the classpath but is not an auto-configuration recipe. Then startup fails with "The following classes could not be excluded because they are not auto-configuration classes". But say you excluded a name that is not on the classpath at all. Then nothing happens. It is quietly ignored. Remember that. The Boot 4 card below turns it into a real trap.
  4. Check the conditions, and use the recipes that pass. Each remaining recipe's @ConditionalOn… checks run, just as Lesson 01's simulation showed. The recipes that pass are read as configuration classes, and their @Bean methods create beans.

One detail makes the whole design safe. Your own configuration is read first. The auto-configuration recipes are read last, on purpose. This is what makes @ConditionalOnMissingBean work. The Tomcat recipe asks: "has anyone already defined a web server factory?". By then, every bean you defined is already registered. So if you brought your own, the recipe steps aside. The order is built into the design. It is not luck.

@AutoConfigurationPackage is the second meta-annotation. It writes down the package of the class carrying it, com.ecommerce, in a small list the context keeps. That list is not used to find our classes; that is the next part's job. Other features use it later, as "the place where the application's own code lives". The first one will be the database layer in Chapter 5, which uses it to find our entity classes. Our test asks Spring Boot's AutoConfigurationPackages.get(context) helper, and expects exactly ["com.ecommerce"].

Switching recipes off. Sometimes a recipe applies and you do not want it. The classic case: a database library is on the classpath, but you are not ready to set up a database yet. You have two tools that do the same thing:

// 1. In code, on the main class, by class. A typo is a compile error, which is good.
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)

# 2. As a setting, by full name, in application.yml or on the command line:
spring:
  autoconfigure:
    exclude: org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration

Use the first one when you can. The compiler checks a class reference. Nobody checks a name written as text. There is also a master switch, spring.boot.enableautoconfiguration=false, which turns off the whole engine. It exists mostly for unusual test setups. Try it once, and you will see exactly the failure in section 4.

Auto-configuration classes moved, and old exclusions can fail without telling you. Lesson 01 described how Boot 4 split things into modules. Because of that split, most auto-configuration recipes now live in a new package, inside their own technology's module. Here is the one you will copy from Stack Overflow most often:

org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration

What 3.x did: nearly every recipe lived in one jar, spring-boot-autoconfigure, under org.springframework.boot.autoconfigure.<technology>. Tomcat was set up by ServletWebServerFactoryAutoConfiguration, in org.springframework.boot.autoconfigure.web.servlet.

What 4.x does: each technology module carries its own recipes, under org.springframework.boot.<technology>.autoconfigure. Tomcat's recipe is now org.springframework.boot.tomcat.autoconfigure.servlet.TomcatServletWebServerAutoConfiguration. The core spring-boot-autoconfigure jar keeps only about a dozen general recipes. I checked its 4.1.1 recipe list: admin, AOP, availability, configuration properties, lifecycle, messages, placeholders, project info, JMX, SSL, task execution and task scheduling.

Why it changed: it is the same split into modules. A recipe belongs with the technology it sets up. So a jar you do not have brings no recipes you do not need. A nice side effect: the --debug report (below) gets much shorter. In 3.x it listed well over a hundred negative matches for technologies you never used, because their recipes were always there. In 4.x those recipes are simply not on your classpath, so there is nothing to report.

What this means for you: in Boot 4, an old tutorial's exclude = DataSourceAutoConfiguration.class becomes a compile error: package org.springframework.boot.autoconfigure.jdbc does not exist. That is annoying, but at least it is loud. The dangerous version is the text form. Put the old name in spring.autoconfigure.exclude or excludeName, and it names a class that no longer exists. Step 3 above means it is then quietly ignored. The recipe you meant to switch off stays on, and nothing tells you. Whenever you copy an exclusion, look up the class's current package first. Our demo test excludingANameThatDoesNotExistIsSilentlyIgnored shows the silence on your own machine.

It lists every recipe Boot considered, and why it was used or skipped. Here is a predicted piece of it for our project. The condition messages follow the pattern Boot has used for years. 3.5 Part three: @ComponentScan — "search this package and below"

Step 1 of the old main listed every class by hand. Component scanning replaces that list with a search. Here is the search, step by step.

  1. Decide where to start. @ComponentScan has a basePackages attribute. @SpringBootApplication leaves it empty. But empty does not mean "search nothing". The rule is: if no starting package is given, use the package of the class that carries the annotation. Our main class is in com.ecommerce, so the search starts there. This one rule is why Lesson 02 said the main class's package "really matters".
  2. Turn the package into a file search. Dots become slashes. Then a pattern is added that means "everything below here". So com.ecommerce becomes classpath*:com/ecommerce/**/*.class. The ** means "any number of folders deep". Spring then lists every compiled class file that matches, in target/classes and in every jar.
  3. Read each class file quickly. Spring does not load every class into memory; that would be slow. It reads just enough of each raw class file to see its annotations.
  4. Keep the components. A class is kept if it carries @Component, either directly or through a meta-annotation. Annotations such as @Service, @Repository and @RestController all carry @Component. That family is Lesson 05's topic. Each kept class is registered as a bean definition: a written plan for a bean that will be created later.
  5. Apply the exclude filters. @SpringBootApplication adds two filters that throw classes back out. AutoConfigurationExcludeFilter throws out any auto-configuration recipe that happens to sit inside a searched package. That stops a recipe from sneaking in through the search and skipping its conditions. TypeExcludeFilter is a hook that other tools can plug into. Spring Boot's test support uses it to keep test-only configuration classes out of the main application.

The result is a boundary, and it is strict. Classes in com.ecommerce, or in any package inside it, are found. Classes anywhere else are not, and nothing tells you. Three details about this boundary catch people out:

  • "Inside" means inside by whole names, not by spelling. com.ecommerceadmin starts with the same letters as com.ecommerce, but it is a different package. It sits next to com.ecommerce, not inside it, so it is not searched. The file pattern com/ecommerce/** needs a slash after ecommerce.
  • Packages above are invisible too. Move the main class down into com.ecommerce.app, and the search now starts there. com.ecommerce.product sits next to app, not inside it, so it is left out.
  • Setting the packages yourself replaces the default. It does not add to it. @SpringBootApplication(scanBasePackages = {"com.ecommerce", "com.ecommerceadmin"}) searches exactly those two package trees. If you list only "com.ecommerceadmin", your own main package is no longer searched. scanBasePackageClasses = SomeClass.class does the same job, but it names a class instead of a package written as text. So a typo is a compile error, instead of a silent miss.

Why have a boundary at all, instead of searching everything? Because "everything" on the classpath is huge. Our forty jars hold tens of thousands of classes, mostly Spring's own and Tomcat's. Searching all of them would be slow. Worse, it would pick up any class in any library that happens to carry @Component. That class would then be created in your application without you asking. A boundary around your own code is fast, predictable, and yours. The price is that you must keep your code inside it. Nearly every Spring project follows one simple habit: the main class goes in the top package, and every other class goes in that package or inside it.

The extreme case: no package at all. A class file with no package line lives in the default package. Put the main class there, and the search starts from "the top of everything": every class in every jar. Spring Boot notices this at startup and prints a warning much like ** WARNING ** : Your ApplicationContext is unlikely to start due to a @ComponentScan of the default package. (This is a prediction. The wording has stayed the same for many versions, but check it against what your machine prints.) As the warning says, the application usually fails to start soon after. Always give your classes a package.

3.6 The ApplicationContext — the brain of the application

Every section so far has said "Spring registers…", "Spring keeps…", "the container holds…". It is time to name the object doing all of it. In the old main in section 1, you could see it. Step 1 created it by hand: new AnnotationConfigWebApplicationContext(). In our main, it is created inside SpringApplication.run, and run hands it back. The return type is ConfigurableApplicationContext. We just never kept the value it returned.

A container in Spring is the object that creates your beans, keeps them, and connects them to each other. Spring's full-featured container is called the ApplicationContext. Calling it the brain is not just a figure of speech. Everything the application knows is stored in it. Everything that happens goes through it. In practice, it has five jobs:

  1. The register: it knows every bean. For every bean, it keeps a name, a type, and the plan for creating it. You can ask for a bean by name, as in context.getBean("dispatcherServlet"). Or you can ask by type, as in context.getBean(EcommerceApplication.class). getBeanDefinitionCount() tells you how many beans it knows about. Our project has exactly one class we wrote, yet the number is well over a hundred. Every other bean came from auto-configuration.
  2. The factory: it creates beans in the right order and connects them. If bean A needs bean B, the context creates B first and hands it to A. Connecting beans like this is called dependency injection. It is the whole subject of Chapter 2.
  3. The settings: it owns the Environment. Settings come from application.yml, from environment variables, and from the command line. They are all combined into one object, the Environment. There is a clear order of priority: a command-line setting beats application.yml. context.getEnvironment().getProperty("spring.application.name") returns "ecommerce", read from our YAML file. Profiles and the full priority order come in Chapter 6.
  4. The announcements: it sends out events. It announces moments such as "startup finished" and "shutting down", and any bean can listen for them. Lesson 10 uses this.
  5. The lifecycle: it starts and stops everything. First the context goes through refresh. It reads every configuration, creates every bean, and starts everything that needs starting. Later it goes through close. It stops everything and destroys every bean, in reverse order. The embedded web server is started and stopped as part of this. That is why closing the context shuts Tomcat down.

ApplicationContext is a Java interface: a list of promised abilities. Several different types keep that promise, and each adds a bit more. They form a small ladder. It is worth knowing, because you will see every step of it in error messages:

TypeWhat it addsWhere you meet it
BeanFactoryThe bare minimum: "give me the bean called X". The original, most basic container.Deep inside stack traces
ApplicationContextEverything above, plus the Environment, events, messages, and loading files. What people mean by "the context".Anywhere you ask Spring for something
ConfigurableApplicationContextEverything above, plus control: refresh(), close(), isActive().What SpringApplication.run returns
ServletWebServerApplicationContextEverything above, plus it owns an embedded web server that it creates during refresh and stops on close.The actual class of our context

Which one does Boot choose? It decides very early, inside the SpringApplication constructor, by looking at the classpath. This choice is called the web application type. Here are the rules, from the official 4.1.1 reference documentation:

  • If Spring MVC is there, it is a servlet web application. The context is an AnnotationConfigServletWebServerApplicationContext.
  • If Spring MVC is missing but Spring WebFlux is there, it is reactive. (WebFlux is the other way of building web apps, covered in Phase 3.)
  • Otherwise it is none: a plain AnnotationConfigApplicationContext, with no web server at all.

You can override this choice with the setting spring.main.web-application-type. Its values are servlet, reactive or none. Our demo test does exactly that, and watches the web server disappear.

3.7 The embedded Tomcat, and why there is no server to install

Lesson 01 showed the big flip. In the old world, your application was copied into a Tomcat that someone installed separately. With Spring Boot, Tomcat is a library that lives inside your application. Lesson 01 explained why this is better. Now that we have every piece, here is how it really happens.

  1. Tomcat's classes are on the classpath because spring-boot-starter-webmvc brought in spring-boot-starter-tomcat (Lesson 02). They are just jar files. Nothing has started yet.
  2. Spring MVC is on the classpath, so Boot chooses a servlet web application. So the context is a ServletWebServerApplicationContext.
  3. @EnableAutoConfiguration finds the TomcatServletWebServerAutoConfiguration recipe. Its conditions pass. The Tomcat classes are there, this is a servlet application, and we have not defined a web server factory of our own. So it registers a bean named tomcatServletWebServerFactory. A factory is an object whose only job is to build another object. This one knows how to build a Tomcat with the right settings. It reads server.port and every other server.* setting.
  4. Partway through refresh, the context reaches a step called onRefresh. In that step, ServletWebServerApplicationContext calls its own createWebServer() method. It asks itself for beans of type ServletWebServerFactory, and it expects exactly one. If there are none, it throws MissingWebServerFactoryBeanException, which you will meet in section 4. If there are two or more, it throws "Unable to start ServletWebServerApplicationContext due to multiple ServletWebServerFactory beans". Both messages are quoted from the 4.1.1 source.
  5. With exactly one factory, it calls factory.getWebServer(...). Tomcat is built in memory and claims the port. The log prints Tomcat initialized with port 8080 (http). Tomcat then starts its own insides, and hands control back to Spring for Spring's web setup. The log prints Root WebApplicationContext: initialization completed in … ms.
  6. The context goes on to create every remaining bean. Only at the very end of refresh does it tell Tomcat to start accepting requests. Then the log prints Tomcat started on port 8080 (http) with context path '/'. The two log lines are kept apart on purpose. Opening the doors before all the beans were ready would let the first customers into an unfinished application.

So "why is no separate server needed?" now has a clear, mechanical answer. The server is just another object, built by a factory bean. And like any bean created by auto-configuration, it can be replaced, set up differently, or switched off. Change server.port, and the factory builds Tomcat on a different port. Define your own ServletWebServerFactory bean, and the recipe steps aside. Exclude the recipe, and there is no factory, so the web application cannot start. Our demo test proves that on your machine.

The web-server classes moved to new packages, so your log lines and imports look different from every older tutorial.

What 3.x did: all embedded-server support lived inside the main spring-boot jar: Tomcat under org.springframework.boot.web.embedded.tomcat, the servlet web context under org.springframework.boot.web.servlet.context, and WebServerApplicationContext under org.springframework.boot.web.context.

3.8 Why the program keeps running after main() has finished

A correction to Lesson 02. An earlier version of Lesson 02, and the comments in EcommerceApplication.java, said that SpringApplication.run "does not return while the server is running". That was wrong. I checked the 4.1.1 source of SpringApplication.run. Its last line is return context;. It returns as soon as startup is complete. The comments in the main class have been fixed, and so has Lesson 02. This section explains what really keeps the application alive. It is also a small example of why every claim in this course is a prediction you are invited to check.

To see how, we need one new idea. A Java program can do several things at once. Each separate line of work inside a running program is called a thread. Think of the cooks in one kitchen. They share the same kitchen, but each follows their own list of steps. When the Java runtime starts your program, it creates one thread named main, and runs your main() method on it. That is why every startup log line so far shows [main]. Code can start more threads, and Tomcat starts several.

Now for the rule that decides when a Java program ends. Every thread is either a daemon thread or a non-daemon thread. A daemon thread is background help that the program does not wait for. A non-daemon thread is real work that the program must wait for. The Java runtime only exits when no non-daemon threads are left. The main thread is non-daemon. So an ordinary program ends when main() returns, because main was the last one.

Here is what happens in our application:

  1. The main thread calls SpringApplication.run, and all of startup happens on it.
  2. When Tomcat starts, its TomcatWebServer class starts one extra thread, named container-0. It marks that thread as non-daemon on purpose, with setDaemon(false). The thread's only job is to wait. (Checked in the 4.1.1 source: the method is startNonDaemonAwaitThread().) Tomcat also runs other threads that listen for connections and handle requests.
  3. run returns the context. main() has nothing left to do, so it returns, and the main thread ends.
  4. The Java runtime checks for non-daemon threads that are still running. It finds container-0, so it does not exit. The application keeps answering requests on Tomcat's threads. Nothing is "stuck". The waiting is done by a thread whose whole purpose is to wait.
  5. You press Ctrl+C. The operating system asks the Java runtime to stop. Before it exits, the runtime runs its shutdown hooks. These are pieces of code registered in advance, to run "on the way out". Spring Boot registered one that closes the context.
  6. Closing the context stops Tomcat gracefully. Tomcat stops accepting new connections, lets the requests already in progress finish, and then shuts down. That ends container-0. Now no non-daemon threads are left, and the Java runtime exits.

The sample log in the official 4.1.1 documentation shows the last two steps. Look at the thread names. The shutdown runs on a thread whose name, cut short to fit, ends in …ionShutdownHook. The graceful stop runs on one called tomcat-shutdown:

INFO 18244 --- [ecommerce] [ionShutdownHook] o.s.boot.tomcat.GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
INFO 18244 --- [ecommerce] [tomcat-shutdown] o.s.boot.tomcat.GracefulShutdown : Graceful shutdown complete

This has a practical result you can use. Code written after SpringApplication.run(...) in main() does run. It runs once, right after startup finishes, while the application is already answering requests. (It is not the usual place for "do something at startup". Lesson 10 shows the proper tools.) It also explains the opposite case. With spring.main.web-application-type=none, there is no Tomcat, so there is no container-0. So the program starts, prints Started EcommerceApplication, and exits straight away. That is not a crash. The program simply ran out of work.

Check yourself: you add System.out.println("hello"); on the line after SpringApplication.run(...). When, if ever, does "hello" appear?

Once, right after the Started EcommerceApplication in … seconds line. run returns when startup is complete. main carries on to your println, prints "hello", and then returns. The application keeps running after that, because Tomcat's non-daemon container-0 thread keeps the Java runtime alive. If run really waited forever, as Lesson 02 once wrongly said, "hello" would only appear after you pressed Ctrl+C. Try it, and let the machine settle it. Then delete the line.

3.9 The whole of SpringApplication.run, start to finish

Everything in this lesson happens inside one method call. Here it is in order, based on the 4.1.1 source of SpringApplication. Nothing is left as "it just happens".

  1. new SpringApplication(EcommerceApplication.class). The static run first builds a SpringApplication object. Its constructor does four things. It records our class as the primary source: the first configuration class the context will read. It decides the web application type from the classpath (servlet, for us). It loads Boot's own built-in list of startup helpers from the jars. And it works out which class holds the main method, so the log can name it.
  2. Prepare the Environment. application.yml is read. The command-line args are turned into settings: every --name=value becomes a setting that beats the YAML file. Then they are all combined into one Environment.
  3. Print the banner, the Spring logo drawn in text characters. Then log Starting EcommerceApplication using Java 21… and No active profile set….
  4. Create the context of the chosen type. Then register the primary source, our main class, as the first bean definition. That is the moment @SpringBootApplication gets noticed. Spring never went looking for it. We handed it over, as the first argument to run.
  5. Refresh the context. This is the big one. In order:
    1. Read the configuration classes, starting with ours. Reading its annotations sets off two things. @ComponentScan finds and registers our components (none yet). @EnableAutoConfiguration reads every recipe list, removes exclusions, checks conditions, and registers the beans of the recipes that pass. All of that happens after our own configuration.
    2. Prepare the special beans that adjust other beans (a Chapter 2 topic).
    3. onRefresh: create the web server. Tomcat initialized with port 8080, then Root WebApplicationContext: initialization completed.
    4. Create every remaining bean, in the order their dependencies need. (Beans marked "lazy" are skipped here. They are created only when first used.)
    5. Finish: start everything that has a start step, including Tomcat's connector. Tomcat started on port 8080.
  6. Log Started EcommerceApplication in 1.9 seconds. Announce "started". Run any startup runners (Lesson 10). Announce "ready".
  7. Return the context. If anything in steps 1–6 threw an error, the context is closed instead. A failure report such as APPLICATION FAILED TO START is printed, and the error is thrown on out of run. That is exactly how a failing startup fails our contextLoads() test.

"What does @SpringBootApplication do?" is one of the most common Spring interview questions. If you answer "it starts the application", the interview ends early. The answer that gets you hired is section 3.2: three annotations, what each one does, and one result of each. "The main class is a bean." "Recipes step back if you define your own bean." "Scanning starts at the main class's package, so the main class goes in the top package." On real teams, the scanning boundary causes a whole family of live incidents in projects built from several modules. Here is a typical one. A shared library module is published under com.company.common. The services live in com.company.orders. So a @Component in the library is quietly never created, until someone adds scanBasePackages. If you know where the boundary is, you can find that in minutes instead of days.

4The Wrong Way

Wrong approach

Now you know @SpringBootApplication is "just three annotations". So a very natural idea is to write the three out by hand, to be clear and to see what is going on. That idea is fine. It usually goes wrong when one piece gets left out. Often it is @EnableAutoConfiguration, because it "sounds optional".

package com.ecommerce;

import org.springframework.boot.SpringApplication;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;

@Configuration      // "a source of setup instructions" - fine
@ComponentScan      // "search this package and below" - fine
                    // @EnableAutoConfiguration: forgotten
public class EcommerceApplication {
    public static void main(String[] args) {
        SpringApplication.run(EcommerceApplication.class, args);

}

What goes wrong. Follow the chain from section 3. Spring MVC is still on the classpath. So the SpringApplication constructor still decides this is a servlet web application, and still creates a ServletWebServerApplicationContext. That context still reaches onRefresh, and still asks for exactly one ServletWebServerFactory bean. But the only thing that ever defined one was the Tomcat auto-configuration recipe. Without @EnableAutoConfiguration, no recipe is ever read. So there are zero factories. The Tomcat jar is right there on the classpath, and nothing will build it.

Correct approach

Keep @SpringBootApplication. It is the correct, standard choice, and after this lesson it is no longer a mystery. The main class stays exactly as it was in Lesson 02. Only its comments changed. The full file on disk has them.

Step-by-step walkthrough of what happens when this runs

  1. The JVM calls main on the thread named main.
  2. SpringApplication.run builds a SpringApplication. It records EcommerceApplication as the primary source, sees Spring MVC on the classpath, and chooses a servlet web application.
  3. It reads application.yml (spring.application.name=ecommerce, server.port=8080) and the command-line arguments into the Environment.
  4. It prints the banner and logs Starting EcommerceApplication….
  5. It creates an AnnotationConfigServletWebServerApplicationContext and registers EcommerceApplication in it as the bean ecommerceApplication.
  6. Refresh begins. Spring reads the annotations on EcommerceApplication and opens up @SpringBootApplication into its three parts.
  7. @ComponentScan searches com/ecommerce/**/*.class. It finds only EcommerceApplication, which is already registered. There are no other components yet.
  8. @EnableAutoConfiguration's selector reads every AutoConfiguration.imports file. It removes nothing, because we excluded nothing. It checks the conditions, and registers the beans of the recipes that pass. Those include tomcatServletWebServerFactory and dispatcherServlet. @AutoConfigurationPackage records com.ecommerce.
  9. onRefresh finds exactly one ServletWebServerFactory. It builds Tomcat and claims port 8080: Tomcat initialized with port 8080 (http). Tomcat starts its engine and runs Spring's web setup: Root WebApplicationContext: initialization completed.
  10. Every remaining bean is created. Then Tomcat's connector starts accepting requests: Tomcat started on port 8080 (http) with context path '/'. The non-daemon thread container-0 is now running.
  11. Started EcommerceApplication in … seconds is logged, and run returns the context. main ends, and the thread named main ends with it.
  12. The program stays alive on Tomcat's threads. A request to / still gets the 404 from Lesson 02, and that is correct.
  13. Ctrl+C runs the shutdown hook. The context closes, Tomcat shuts down gracefully, container-0 ends, and the Java runtime exits.

    void runReturnsALiveContextThatHoldsOurMainClassAsAManagedObject() {
        assertThat(context.isActive()).isTrue();                          // run() RETURNED, and the context is live
        assertThat(context.containsBean("ecommerceApplication")).isTrue();   // the main class is a bean
        assertThat(context.getBean(EcommerceApplication.class)).isNotNull();
        assertThat(context.getBeanDefinitionCount()).isGreaterThan(10);    // we wrote ONE class
        assertThat(context.getEnvironment().getProperty("spring.application.name")).isEqualTo("ecommerce");
    }

    @Test
    void autoConfigurationStartedARealEmbeddedTomcat() {
        assertThat(context).isInstanceOf(WebServerApplicationContext.class);
        WebServerApplicationContext webContext = (WebServerApplicationContext) context;
        assertThat(webContext.getWebServer()).isInstanceOf(TomcatWebServer.class);   // org.springframework.boot.tomcat in Boot 4
        assertThat(webContext.getWebServer().getPort()).isGreaterThan(0);             // the real port it was given
        assertThat(context.getBean("dispatcherServlet")).isInstanceOf(DispatcherServlet.class);
    }

    @Test
    void theApplicationPackageIsTheMainClassPackage() {
        assertThat(AutoConfigurationPackages.get(context)).containsExactly("com.ecommerce");
    }

    @Test
    void closingTheContextShutsTheWholeApplicationDown() {
        ConfigurableApplicationContext throwaway = SpringApplication.run(EcommerceApplication.class, "--server.port=0");
        assertThat(throwaway.isActive()).isTrue();
        throwaway.close();                                // what Ctrl+C triggers
        assertThat(throwaway.isActive()).isFalse();
    }
}

@BeforeAll and @AfterAll are JUnit annotations. A method marked @BeforeAll runs once, before any test in the class. A method marked @AfterAll runs once, after all of them. Both must be static. JUnit calls them outside any single test object, much as the JVM calls main before any object exists. We use them because starting Spring takes a second or two. The first three tests only read from the running application, so they can safely share one. The fourth test needs a context it is allowed to destroy, so it starts its own.

try ( … ) { … } with something inside the brackets is Java's try-with-resources. Anything declared in the brackets that can be closed is closed automatically when the block ends. That happens whether the block finished normally or threw an error. It is the tidiest way to make sure that every context a test starts, it also stops. assertThatThrownBy is AssertJ's way of saying "this code must throw an error, and here is what the error must look like". One error can be caused by another, which was caused by another. .rootCause() follows that chain of "caused by" errors to the bottom, and checks that one.

7Gotchas and Common Mistakes

  • Moving the main class into a sub-package "to tidy up". People do this because the top package is often messy, and a class called …Application looks as if it deserves its own folder. It compiles and starts perfectly. But every class outside the new, smaller boundary quietly disappears. Avoid it by: treating the top package as the main class's permanent home. Our test theApplicationPackageIsTheMainClassPackage now makes sure of this.

  • Copying an exclusion from an old tutorial. excludeName and spring.autoconfigure.exclude take class names written as text. A name that no longer exists is quietly ignored. That includes any 3.x org.springframework.boot.autoconfigure.<tech>.… name for a recipe that moved in Boot 4. People copy these because the snippet "worked" for someone else. Avoid it by: using exclude = SomeAutoConfiguration.class when you can, because the compiler checks the name. And check what really happened with --debug. Do not trust the report's Exclusions: list for this. As far as I recall from Boot's source (not re-checked for 4.1.1), it lists every name you asked to exclude, even names that matched nothing. Look for the recipe itself instead. If it still appears under Positive matches, your exclusion did nothing.

  • A second @SpringBootApplication (or @SpringBootConfiguration) somewhere under the top package. This usually comes from copying a sample application into the project, or starting a "quick experiment" class. @SpringBootTest's search then finds two candidates, and refuses to choose. Expect a message beginning Found multiple @SpringBootConfiguration annotated classes. (A prediction: that wording is from my memory of the source, not re-checked for 4.1.1.) Every @SpringBootTest in the project fails at once. Avoid it by: keeping exactly one per application. Experiments go in a separate project.

  • Believing SpringApplication.run waits forever. Even this course said so, for one lesson. People believe it because the terminal prompt does not come back, and that looks like waiting. The result: code after run(...) surprises you by running, once, at startup. Avoid it by: remembering the two lanes in the figure in section 3.9. run returns. Tomcat's non-daemon thread keeps the program alive.

  • Reading "check your dependencies" and only looking at pom.xml. As section 4 showed, the missing-web-server-factory error is just as often caused by an annotation or an exclusion as by a missing jar. Avoid it by: checking in this order. Is @SpringBootApplication still whole? Is spring.autoconfigure.exclude empty? Is spring.main.web-application-type left at its default? Only then, check the dependencies.

  • Putting any class in the default package. This happens when a file is created at the top of src/main/java by mistake. For the main class, it means searching every jar. Avoid it by: always giving every class a package line. Your IDE warns about the default package. Take the warning seriously.

8Tradeoffs and When Not to Use This

Convenience hides things. One annotation doing three jobs is wonderful, until one of the jobs does something you did not expect. The whole point of this lesson is that the cost is small if you know what is inside. --debug shows every auto-configuration decision, and one test can check the search boundary. The cost is large for a team that treats the annotation as magic. That is why the tests in section 6 are worth having. Knowing the facts is not enough on its own.

Scanning costs startup time. Reading every class file under the top package is fast for our project. It is still fast for a few thousand classes. But it is not free, and it grows as your code grows. Huge applications, and apps that must start in milliseconds, use Spring's ahead-of-time processing and native images (Phase 3). These do the work while building, instead of at startup. spring.main.lazy-initialization=true is another option. It creates beans only when they are first used, so startup is faster. But mistakes that would have failed at startup now fail on the first request instead. That is usually a worse time to find them.

When would you not use @SpringBootApplication as it is? Three honest cases. First, projects made of several modules, where shared code lives in a package tree next to yours. Add scanBasePackages or scanBasePackageClasses. Or better, have the shared module provide its own auto-configuration recipe (Phase 3). Second, libraries meant for other applications to use. They must never carry @SpringBootApplication, because it would compete with the real application's one. Third, tests or tools that need only part of the machinery. They can use narrower annotations, such as @ImportAutoConfiguration with a hand-picked list of recipes. The testing chapter's "slice" tests do exactly this.

When would you not want the embedded server? Some companies run one shared, centrally managed server, and require every app to be deployed into it. Boot can still produce a WAR file for that (Lesson 01 explained the format). Then the server is no longer embedded. And some programs do not answer web requests at all, such as a batch job or a command-line tool. For those, set spring.main.web-application-type=none, or simply do not use a web starter. You keep the container and auto-configuration, and lose nothing you needed. That is exactly what Spring Batch jobs do in Phase 3.

9Key Takeaways

  • @SpringBootApplication is a bundle of three meta-annotations. @SpringBootConfiguration makes the main class the main configuration class, and a bean. @EnableAutoConfiguration switches on the recipe engine. @ComponentScan searches for your classes. Plain Java cannot see inside the bundle, but Spring's annotation reader can.
  • @EnableAutoConfiguration imports a selector. The selector reads every META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file, removes your exclusions, and uses the recipes whose conditions pass. It does this after your own configuration, and that is what lets a recipe step back when you define your own bean.
  • Component scanning starts at the main class's package. It covers only that package and the packages inside it, matching whole package names. That is why the main class belongs in the top package, and why a class outside the boundary is quietly never created.
  • The ApplicationContext is the container at the centre of every Spring application. It holds and names every bean, creates and connects them, owns the Environment, sends out events, and controls startup and shutdown. That includes the embedded Tomcat, which is just built by an auto-configured factory bean during refresh.
  • SpringApplication.run returns the finished context once startup is complete, and then main() ends. The program keeps running only because Tomcat started a non-daemon thread. In Spring Boot 4, the Tomcat and web-server classes live in new packages (org.springframework.boot.tomcat, org.springframework.boot.web.server.*). That is why our logs and imports differ from every 3.x tutorial.

A teammate "tidies" the project. They move EcommerceApplication.java into a new folder, src/main/java/com/ecommerce/app/. They change its first line to package com.ecommerce.app;. And they add one line to main:

3. After the imports are fixed: 10 pass, 1 fails.

  • All three anatomy tests pass. The class still carries @SpringBootApplication, and basePackages is still empty. The rule did not change. Only the package it points to changed.
  • theApplicationPackageIsTheMainClassPackage fails. AssertJ reports that it expected exactly ["com.ecommerce"], but the real list was ["com.ecommerce.app"]. This is the guard doing its job. It caught the boundary moving before any customer did.
  • The other three context tests and all three demo tests pass. Tomcat, the DispatcherServlet and the main-class bean do not depend on the package. The bean name is still ecommerceApplication.

That is exactly why this lesson added a test that checks the package directly.

4. GET /products gives a 404. The search now starts at com.ecommerce.app. com.ecommerce.product sits next to app, not inside it. So the controller is never found, never created, and never connected to its address. Startup prints no error at all. It is the simulation's second button, now for real.

5. Two fixes.

Fix A (the right one): move the class back. Put EcommerceApplication back in com.ecommerce, using the IDE's move refactoring, which updates every reference. The usual layout is back, the boundary covers everything, and all 11 tests pass. This is the choice to make. Every other developer who opens the project will expect the main class in the top package.

Fix B (it works, but it fights the usual layout): widen the search.

@SpringBootApplication(scanBasePackages = "com.ecommerce")
public class EcommerceApplication { ... }

This fixes the controller. But it only widens @ComponentScan. @AutoConfigurationPackage still records com.ecommerce.app. So our package test still fails. And in Chapter 5, the database layer would not find entity classes outside com.ecommerce.app either. You would need more settings to cover that too. Fix B treats a symptom. Fix A removes the cause.
